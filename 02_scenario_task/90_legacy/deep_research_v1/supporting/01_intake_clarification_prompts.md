# 01 附录2：澄清追问写法

对照金标：`04_context_state/03_workspace/03_回归/02_memory-cycle-formal-pack/01-存储芯片周期投研需求说明-20260715-1.md`。

## 1. 为什么要问

只问会改变 **02 任务结构** 的歧义。不问不会改结构的措辞偏好、格式或下游细节。

**先定齐、再一次问完**：识别出全部结构性歧义后，把 2–4 条（最多 5 条）待答问题一次登记齐，用户一次答完；不要拆成多轮“一次只问一条”。

典型必须追问：

| 歧义类型 | 不问会怎样 | 金标例子 |
|---|---|---|
| 对象层级可拆可合 | 02 不知按整体还是分产品建单元 | 是否把 HBM、非 HBM DRAM 与 NAND 分开判断 |
| 时间口语未落到三件套 | 03/04 不知“当前/结束”如何取数与表达 | “当前”和“本轮周期结束”如何落到时间范围 |
| 交付落点不清 | 05 不知行业判断还是个股建议 | 是否输出行业周期判断并排除个股投资建议 |

能从输入直接提取的不要问。

## 2. 问什么：人话、短句、绑本题

`clarifications[].question` 必须是用户可直接回答的**一句中文**，并满足：

1. **锚定原问题里的含糊词**（如「存储芯片」「目前」「什么时候结束」），不要抽象问「研究对象是什么」；
2. **给出可操作的选择或落法**（分/合、时间怎么落、交什么/不交什么）；
3. **短**：通常一行，约 15–40 字；不要「当前理解是…请确认…不同选择会改变…」套话；
4. **禁止**内部代号：`UC-01`、`core_object`、`structural_ambiguity`、`Stage01`、`topic` 等。

`topic` 只给机器用（如 `core_object` / `event_scope_and_time_window` / `delivery_landing`）；界面与 `question` 正文不得依赖这些词。

## 3. 金标写法（照这个气质写，勿照抄无关对象）

原始输入：`存储芯片目前处于什么周期，本轮周期什么时候结束`

```yaml
clarifications:
  - question_id: UC-01
    topic: core_object
    question: 是否把 HBM、非 HBM DRAM 与 NAND 分开判断
  - question_id: UC-02
    topic: event_scope_and_time_window
    question: “当前”和“本轮周期结束”如何落到时间范围
  - question_id: UC-03
    topic: delivery_landing
    question: 是否输出行业周期判断并排除个股投资建议
```

对比（错误）：

- `UC · structural_ambiguity`
- `请回答当前结构性歧义问题`
- `当前理解的研究对象是「存储芯片」。请确认本次要判断的核心对象是什么……`

## 4. 待澄清时对用户说什么

有结构性歧义时**不生成正式 01 终稿**。界面一次展示全部待答问题，并交代：

1. 一共要确认几件事；
2. 每条问题是什么（人话短句）；
3. 它大致会改变什么（对象拆分 / 时间口径 / 交付形态等）；
4. 全部答完后如何继续（写入澄清记录后重新收敛）。

## 5. 可回滚假设 vs 追问

不改结构的规范化 → 可回滚假设，不问。  
会改主对象 / 主类型 / 主通道 / 关键范围 / 用途 → 必须追问，不得默认。
