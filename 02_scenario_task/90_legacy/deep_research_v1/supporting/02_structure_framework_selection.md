### 5.7 框架选择与裁剪规则

#### 先用一句话说清这套规则

**不是「整次任务只能用一个框架」**，也不是「先随便挂三个再各裁一点」。

更贴合实际的做法是：

1. **想的时候可以多看**：索引推荐、近邻候选，对照看 2—3 个都没关系；
2. **写进 02 时必须收敛**：每个关键判断单元只定 **1 个直接框架**（回答本单元那句可证伪判断的主机制）；
3. **需要时再叠一层**：行业特有变量用行业增强；产品/事件特有误判用场景卡；
4. **前后可以串起来**：门槛要求的前置、明确要做的下游，按链往下接——多几个不算出越界。

一句话：**限制的是「同一个判断里并列好几个主机制」；不限制「顺着一条链把前置和下游接清楚」。**

裁剪裁的是：**主路线、模块、变量**，不是把三个直接框架各留一点继续并列。

#### 三层分别管什么

不要把任务级、判断单元级、路径级混成一套「主框架 / 辅助框架」来数：

| 层级 | 你在这一层决定什么 |
| --- | --- |
| 任务级 | 这次核心要验证什么；拆成 2—3 个关键判断单元；单元之间谁先谁后、谁并列、谁竞争、谁该停 |
| 判断单元级 | 这个单元判什么类型、那句可证伪观点、**一个**直接框架；要不要加行业增强 / 场景卡 |
| 路径级 | 为了写出目标结论，还需要哪些前置；以及这次明确要求接到公司 / 预测 / 市场时，下游接谁 |

口头可以说「主线框架 / 辅助框架」：把各单元的直接框架汇总成主线说明即可。落盘时请用下面五类调用角色，方便系统和校验对齐。

#### 选用顺序（从「这次要写出什么」倒推）

```text
01 已明确的研究问题与边界
→ 核心待验证命题（任务主线）
→ 2—3 个关键判断单元（写清前置 / 并列 / 竞争 / 停止）
→ 【探索，可选】对照看 2—3 个候选框架，记下为何不用谁
→ 每个判断单元：主判断类型 + 一句可证伪观点
→ 每个判断单元：目标输出（要写成哪一级结论 / 输出门槛）
→ 收敛：定 1 个直接框架 + 登记表要求的必要前置
→ 必要时加 0—1 个行业增强、0—1 张场景卡
→ 裁剪：保留真正改变判断的路线、模块、变量
→ 检查有没有重复输出、没有出口的内容
→ 映射正式本体
```

任务先有主线和关键判断单元；每个单元再选判断类型和直接框架。不要在「先定命题」和「先定判断类型」之间二选一。

只有满足下面至少一条，框架才该进本次任务；只是「主题相关」不够：

1. 它负责本单元必须写出的那级结论（输出门槛）；
2. 它是这级结论的必要前置；
3. 它会改变对象怎么拆、主路径或竞争解释；
4. 它会改变最低证据、反证或停止条件；
5. 它承接本次明确要求的下游输出（公司、预测、预期差、估值等）。

任务里总共引用了好几个框架，只要调用链说得清楚，**不必**因此退回 01。

#### 五类调用角色（按本次作用定，不按库名定主辅）

不要因为「它是基础框架」就默认只能当检查点，也不要因为「它是行业主框架」就默认一定是主框架。看它在本单元里干什么：

| 调用角色 | 落盘字段 | 人话含义 | 每个关键判断单元怎么控量 |
| --- | --- | --- | --- |
| 直接框架 | `direct` | 直接产出本单元那句核心判断的主机制 | 原则上 **1 个** |
| 前置框架 | `prerequisite` | 没有它的结论，直接框架的门槛过不去 | 按门槛串行接；**不计入**并行宽度 |
| 行业增强 | `industry_overlay` | 在主机制上叠行业特有对象、时钟、变量、失效条件（通常就是一张行业主框架） | **0—1 个** |
| 下游承接 | `downstream` | 本单元结论继续接到公司兑现、预测、预期差或估值 | 仅当本次明确要求；串行接续不计入并行宽度 |
| 场景卡 | 挂在 `scenarios[]` | 某产品 / 技术 / 事件相对主框架的增量：特殊约束、易误判点、路由提示；**不是正式框架** | **最多 1 张**主要场景卡 |

补充说明：

- **基础框架**可以当本单元的直接框架（例如通用供需、价格、预期差）。
- **行业主框架**经常是对基础机制的增强，也可以在行业机制本身就是核心分歧时当直接框架。二者是**叠加**，不是二选一。
- **行业增强 ≈ 把行业主框架按增强角色挂上**；库里没有单独一类叫「行业增强」的文件。
- **场景卡**不能代替机制判断。没用场景卡**不必**专门解释。场景卡正文应写清默认主框架、何时再拉辅助、默认排除什么；不要默认并列多个主框架。
- 若同一单元需要**并列**三个以上不同机制都当直接框架，通常说明单元过宽——应**拆成多个判断单元**，而不是堆框架。

#### 数量规则（对照上面三层）

**任务级**

- 1 条核心待验证命题；
- 原则上 2—3 个关键判断单元，并写清单元关系；
- **不限定**任务总引用框架个数，但必须有一条说得清的调用链。

**判断单元级**（每个关键判断单元原则上）

- 1 个主判断类型；
- 1 条可证伪的待验证观点；
- 1 个直接框架；
- 0—1 个行业增强；
- 0—1 张主要场景卡；
- 最多 1 条主要竞争路线；
- 通常 3—5 个决定性变量。

**路径级**

- 可按输出门槛串行接前置与下游；
- 串行链上的框架**不计入**并行宽度；
- 只有同一单元上「并列争当直接框架」的，才算并行过宽。

#### 排除记什么、不记什么

排除记录不要把库里相关框架扫一遍。只记：

1. 索引推荐了但本次没用的；
2. 与最终选择最接近的 1—3 个候选（探索时看过、落盘前淘汰的）；
3. 看似相关、但很容易写越界的近邻框架。

排除理由写清：它为什么**不改变**本次主路径、反证、最低验证条件、停止条件、输出门槛或本体映射。

#### 用完框架后，02 要交代清楚

1. 核心研究主线与 2—3 个关键判断单元是什么；
2. 每个单元的目标输出门槛是什么，为什么直接框架是它（而不是探索时的其他候选）；
3. 调用链里哪些是前置、行业增强、下游，各自服务哪个单元或门槛；
4. 若用了场景卡：它补了哪些特殊变量、证据、误判或停止条件，挂在哪个单元上；
5. 哪些路线 / 模块 / 变量真正进了本次问题树、主路径、反证或最低验证条件；
6. 按上面收窄范围写的排除理由；
7. 框架内容与 01 边界不一致时怎么裁；
8. 框架里有、正式本体还接不住的内容，是任务候选、本体缺口，还是本次不纳入。

#### 什么时候该返工

真正该返工的，**不是**「这次一共用了超过 3 个框架」，而是：

1. 一个判断单元里，多个框架在回答不同的核心问题（应拆单元）；
2. 同时展开多条主路线，却分不出主次；
3. 增强 / 辅助没有带来独立输出、区分信号或停止条件（挂了等于没挂）；
4. 同一变量、路径或证据要求被多个框架重复生成；
5. 场景卡开始替代正式机制判断；
6. 启用的模块对不上任何关键判断单元、路径节点、证据要求或输出门槛；
7. 调用链说不清为什么必须经过这一层。

最终进入 02 的不是框架全集，而是围绕核心待验证命题、按判断单元与输出门槛裁过的**最小可用调用链**。框架库帮你识别机制、变量、证据和反证；**主轴仍由研究员确认**。
