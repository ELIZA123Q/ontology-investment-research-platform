# 00-投研本体框架概述

## 1. 本体为什么存在

投研判断容易出现四类问题：同一对象有多种叫法，稳定关系与短期变化混在一起，材料说法被直接当成事实，结论无法回到证据和推理过程。

本体用一套可复用的业务语言解决这些问题：

- **对象**：研究世界中有什么（公司、产品、环节等）。
- **关系**：对象如何连接（例如公司生产某产品、产品属于某环节）。
- **动作**：允许发生什么业务行为（例如形成判断、评价证据）。
- **计算、流程与约束**（系统名 Function、Logic、Rule）：为动作及推理提供计算、步骤和限制条件。
- **证据**：依据来自哪里、属于何种说法、当前是否可用。

证据层里，单项证据在本次任务中能不能用，记在 `EvidenceAssessment`；一个核心判断的整体证据能不能进入推理，记在 `EvidenceReadinessAssessment`。推理层里，`RuleEvaluation`（规则评价）、`Judgment`（判断）、`ReasoningTrace`（推理留痕）、`ExpectationGap`（预期差）、`AssetImpact`（资产影响）和 `ValidationRecord`（事后验证）串成可留痕、可验证、可复盘的完整判断链。研究报告、本体诊断摘要等给人看或给下游系统看的展示格式，不属于本体定义，由运行要求另行约定。

本体不是数据库表设计、材料全文仓库、任务调度系统、报告模板库或投资建议系统。它不保存某个行业的具体实例，也不把一次运行的临时信息写成通用定义。

## 2. 三层结构

### 2.1 语义层

语义层回答“我们在研究什么”。它保存稳定对象、对象边界及相对稳定的业务关系，为证据和推理提供共同锚点。通用对象包括概念、产业、环节、公司、产品、材料、工序、资产、金融工具、识别码、交易场所、上市挂牌、角色承担、地区与应用。

### 2.2 证据层

证据层回答“依据是什么，以及在本次范围内是否可用”。它区分来源文档、材料中的最小主张、归一后的事实候选和任务相关的证据使用评价，并保留冲突、替代和失效关系。

### 2.3 推理层

推理层回答“发生了什么变化，规则如何执行，如何形成判断，以及后来是否兑现”。它保存关键变量、观测、事件、假设、信号、规则评价、判断、市场预期、预期差、资产影响、情景、推理留痕和事后验证。

### 2.4 职责边界与对象族

三个域在职责上互斥：稳定身份不进入证据域，材料说法不进入语义域，动态判断不进入前两域。跨域关系是必要的数据流，不表示职责重叠；层间依赖固定为 `common → semantic → evidence → reasoning`。

下面按推理角色分组列出类型名（英文是系统稳定标识，前面的中文是读法）。它们不是同一种并列业务实体：

- **稳定语义对象**：概念 `Concept`、组织 `Organization`、公司 `Company`、产业 `Industry`、环节 `Segment`、产品 `Product`、材料 `Material`、工序 `ProcessStep`、资产 `Asset`、金融工具 `FinancialInstrument`、识别码 `Identifier`、识别体系 `IdentificationScheme`、交易场所 `TradingVenue`、上市挂牌 `Listing`、角色承担 `RoleAssignment`、地区 `Region`、应用 `Application`、政策工具 `PolicyInstrument`。
- **证据对象**：来源文档 `SourceDocument`、证据主张 `EvidenceClaim`、证据事实 `EvidenceFact`、单项证据评价 `EvidenceAssessment`、判断就绪评价 `EvidenceReadinessAssessment`。
- **状态与事实对象**：关键变量 `StateVariable`、观测 `Observation`、事件 `Event`。
- **假设与判断对象**：假设 `Hypothesis`、信号 `Signal`、判断 `Judgment`。
- **定价比较对象**：市场预期 `MarketExpectation`、预期差 `ExpectationGap`、资产影响 `AssetImpact`。
- **情景与记录对象**：情景 `Scenario`、规则评价 `RuleEvaluation`、推理留痕 `ReasoningTrace`、事后验证 `ValidationRecord`。

对象、关系、动作、函数、逻辑、规则是元模型资源，不与上述业务对象族并列。

## 3. 对象（Object）

对象表示具有独立身份、需要被反复引用、可以连接其他对象或具有生命周期的业务名词。

对象类型定义一类对象共同具备的属性；对象实例是该类型下的具体成员。核心规范只定义类型，不写具体行业、公司、产品、事件、日期和数值实例。

对象字段主要解决三个问题：

- **能识别**：`id`、`name` 等字段保证对象可以被稳定引用。
- **能定边界**：`description`、口径或范围字段说明对象是什么、不是什么。
- **能连接**：必要属性使对象能够被关系、证据、动作和推理引用。

只有当一项内容需要独立身份、关系连接或生命周期时才建成对象。仅用于描述对象的内容应保留为属性。

### 3.1 一级通用对象准入

对象进入一级通用层还必须同时满足：跨行业反复使用、边界能与现有对象区分、无法只靠属性或行业扩展稳定表达、增加后不会迫使下游大量填充无关字段。`Region`、`Application`、`Organization`、`PolicyInstrument` 和 `ValidationRecord` 满足该标准。

- `Organization` 是通用父类型，`Company` 继承它；同一公司只保留 Company 实例，不重复创建 Organization 实例。
- `PolicyInstrument` 表示稳定政策身份；政策原文属于 `SourceDocument`，发布、修订、执行、延期和失效属于 `Event`。
- `FinancialInstrument` 继承 `Asset`，用于承载证券、基金份额、衍生品等金融工具身份；识别码、上市挂牌和发行/管理/担保等角色拆成独立对象或精确关系，价格、估值和交易动作仍在推理或运行边界之外。
- 人物、技术、设施和项目先进入行业扩展，形成稳定跨行业需求后再申请升级。

## 4. 关系（Relation）

关系表示两个对象之间可以查询和解释的语义连接。关系必须说明起点、终点、方向、基数和业务含义。

普通关系只保存少量必要信息，例如角色、适用范围、有效期和证据引用。若一条关系需要独立身份、丰富属性、独立生命周期或被其他对象引用，应将它提升为对象。

关系只表达“存在怎样的连接”。“在什么条件下会造成何种结果”属于 Rule 或 Logic；某一时点的变化属于推理对象，不能夹在稳定关系里。

## 5. 动作（Action）

动作表示本体允许发生的领域行为。它不是裸露的增删改命令，而是对业务意图、输入、前置条件、执行路径和允许效果的完整说明。

一个动作至少要回答：

- 作用于哪些对象或关系。
- 调用时需要哪些输入。
- 执行前必须满足哪些 Rule。
- 是否进入某个 Logic。
- 是否调用 Function 完成计算。
- 最终可以创建或修改哪些对象和关系。
- 条件不满足时如何拒绝或降级。

创建、修改或失效对象只是动作的效果。所有正式写入都必须通过 Action 的 `write_scope` 约束。

## 6. 函数（Function）

Function 是可调用的计算、查询、归一或复杂执行能力，适合处理无法用简单条件表达的过程，例如实体消歧、指标计算、证据冲突检测和多跳影响传播。

Function 必须声明输入、输出、读取范围、写入范围、副作用和版本。普通 Function 默认只读；需要写入正式对象或关系时，必须由 Action 调用，且写入范围不得超过 Action 的授权。

Function 不决定业务语义。业务上“为什么执行、何时允许、结果写到哪里”仍由 Action、Logic 和 Rule 共同约束。

## 7. 逻辑（Logic）

Logic 是可声明、可测试和可复用的处理流程。它把对象读取、关系遍历、Rule 检查和 Function 调用组织成有顺序的步骤。

每条 Logic 必须说明：

- 谁是入口 Action。
- 读取哪些对象和关系。
- 按什么顺序应用 Rule 和 Function。
- 产生什么输出。
- 失败、缺证或冲突时如何降级。

Logic 只保存公开、可检查、可复现的业务处理结构，不表示模型内部思维过程，也不直接绕过 Action 写入正式对象。

## 8. 规则（Rule）

Rule 是原子化、声明式的条件和约束，用于表达“满足什么条件时，允许、禁止或推导什么”。

本规范使用四类 Rule：

- **校验规则**（`validation`）：检查输入、端点和字段是否符合定义。
- **推理规则**（`inference`）：把明确前提转化为可复用推论。
- **评分规则**（`scoring`）：形成可信度、强度或结论等级。
- **逻辑失效规则**（`blocking`）：条件命中时阻止动作或结论升级。

Rule 可以由 Action 在执行前直接调用，也可以由 Logic 在某个步骤调用。简单条件使用 Rule，复杂计算使用 Function，多步过程使用 Logic。

推理规则属于支撑资源，不另建成 `InferenceRule` 对象。规则的版本、输入输出、所需证据和反面证据条件由 YAML 完整定义。

## 9. 六类资源如何协作

统一调用方向为：

```text
Action
→ 检查前置 Rule
→ 进入 Logic
→ Logic 读取 Object / Relation
→ Logic 调用 Rule / Function
→ Action effect 写入 Object / Relation
→ 形成输出或降级结果
```

调用方保存正向引用：

- Action 通过 `rule_refs`、`logic_refs` 和 `function_ref` 声明调用。
- Logic 的步骤通过 `rule_refs`、`function_ref` 和 `uses` 声明依赖。
- Function 和 Rule 的“由谁调用”从上述正向引用反向解析，不重复维护第二套清单。

同一效果只能有一个权威实现：要么由声明式 Action effect 和 Rule 表达，要么由 Function-backed Action 实现，不能两边重复定义。

## 10. 字段设置原则

字段只保留完成本域职责所必需的信息。

### 10.1 能识别

对象、关系和证据必须能被稳定引用。没有唯一标识或清晰名称的内容，不应成为正式对象。

### 10.2 能定边界

字段要帮助判断一项内容是什么、不是什么。定义、口径、适用范围和排除条件比展示字段更重要。

### 10.3 能追溯

动态内容必须能够回到业务时间、来源、证据或明确前提。没有时间和依据的数值、事件和判断只能作为候选线索。

### 10.4 能防误用

字段必须帮助区分稳定对象、材料主张、事实候选、分析假设和判断结论，避免不同层次相互污染。

### 10.5 字段分级

- **最小字段**：缺少后对象、关系或动作无法成立。
- **推荐字段**：用于补充边界、时间、证据和可复核性。
- **扩展字段**：行业包或具体工程阶段需要时再增加，不在通用正文中展开。

不为展示方便、临时任务或存储便利增加核心字段。完整类型、枚举、必填性和扩展字段以 YAML 为准。

## 11. 中文与系统名

正文使用中文名称，英文只作为稳定系统标识：

- 关键变量（`StateVariable`）
- 变量传导（`variableInfluencesVariable`）
- 形成判断（`FormJudgment`）

字段首次出现时写成“业务时间（`businessTime`）”。后续说明优先使用中文，避免中英混杂影响阅读。

## 12. 建模粒度

1. 类型与实例分离：核心规范只定义通用类型。
2. 核心与行业扩展分离：跨行业稳定内容进入核心。
3. 对象与属性分离：需要身份和连接时建对象。
4. 对象与关系分离：复杂关系需要独立身份时对象化。
5. 稳定结构与动态变化分离：动态内容进入推理层。
6. 主张、事实与判断分离：三者不能互相替代。
7. 关系与规则分离：连接和条件推论分别建模。
8. 动作与函数分离：业务意图和执行实现分别建模。
9. 避免重复权威：同一语义或效果只保留一处正式定义。
10. 保持可追溯：推理输出必须能回到输入和处理路径。

一个字段进入主文档前，应能通过以下检查：

1. 是否直接服务本域职责。
2. 删除后是否会导致无法识别、追溯、降级或复盘。
3. 是否会把动态数据误放进稳定语义。
4. 是否会让主张、事实和判断混在一起。
5. 是否能帮助后续复核。
6. 是否跨行业通用。
7. 行业特有内容是否应进入扩展。
8. 纯工程运行字段是否只需保留在 YAML。

## 13. 判断结果与展示边界

本体内的正式判断结果以推理层对象表达：

- **`Judgment`**：结论陈述、结论等级、置信度和时间尺度。
- **`ReasoningTrace`**：可复核的推理步骤、规则与证据引用。
- **`ExpectationGap`** 与 **`AssetImpact`**：基本面与市场预期、资产影响之间的结构化结果。
- **`ValidationRecord`**：使用后续结果验证原判断是否兑现，并保留偏差、下一验证点和修订建议。

面向研究员的可读报告、面向本体维护者的缺口诊断，以及面向系统留痕的序列化格式，应引用上述对象，但不在本体 YAML 中另建报告模板或输出契约。展示层不得把字符串说明替代为新的本体事实，也不得提升 `Judgment` 已有的结论等级。

## 14. Markdown 与 YAML

Markdown 负责解释为什么这样建模、关键字段解决什么问题以及各资源的边界。YAML 负责完整字段、类型、枚举、关系端点、调用引用和机器校验。

- `common.yaml`：公共元模型、调用方向、层间约束和粒度原则。
- `semantic.yaml`：语义域完整定义。
- `evidence.yaml`：证据域完整定义。
- `reasoning.yaml`：推理域完整定义。
