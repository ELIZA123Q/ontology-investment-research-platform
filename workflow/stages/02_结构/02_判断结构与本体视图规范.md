# 02_判断结构与本体视图规范

## 研究员先看什么

02 回答：**这个问题应该怎样拆、怎样验证；现有概念体系能不能承接。**

**阶段定位：** 02 是本体约束下的判断结构设计，不是固定推理流程。它确定主判断轴、判断单元与依赖关系，并在统一的 `method_applications` 中登记 `candidate` 方法（设计态），不得把候选伪装为已执行。

| 你要交什么 | 业务说法 |
|---|---|
| 研究逻辑（Markdown） | 核心矛盾、问题拆解、对象差异、主路径、反证与竞争解释、最低验证条件 |
| 任务本体视图（YAML） | 同一套结构如何被正式概念承接；缺口与候选（机器侧，研究员可不深读） |

**怎样算完成：** 有一句清晰的核心待验证命题（不是方向性结论）；2—3 个能分别验证的关键判断；主路径与反证齐备；03 知道该收什么证据；本体缺口已扫描并写清限制。

**常见失败：** 拼贴框架库当研究框架；关键词套框架；把待验证命题写成已支持的结论；掩盖对象差异去迁就本体；在 02 查数据或下方向结论。

上游继承 01 的问题与边界；下游 03 按路径与证据要求取证。质量见本文质量章与 [`00A`](../../../governance/03_校验/00A_高质量产出判别标准.md)。附录与模板：[`02_附录1`](02_附录1_框架裁剪与选用细则.md)、[`02_附录2`](02_附录2_本体缺口扫描矩阵与处理细则.md)、[`研究逻辑模板`](模板/02_研究逻辑模板.md)、[`视图模板`](模板/02_任务本体视图模板.yaml)。

结构变化（新变量/路径/竞争假设/范围拆分）须新开完整 02 波次；仅映射到既有结构的证据更新保持当前 02。

## 1. 本阶段负责什么、不负责什么

### 1.1 负责

1. 继承 01 的研究问题、对象范围、时间口径、用途和不研究事项；
2. 识别核心矛盾，写成一句**核心待验证命题**；
3. 拆成最小问题树（前置、并列、竞争、停止）；
4. 确定需要拆分的对象、产品、环节、地区或公司差异；
5. 组织主路径、削弱/阻断条件、反证和竞争解释；
6. 为每个核心判断定义最低验证条件、降级与停止规则，并标清优先级与在总判断中的角色；
7. 按核心矛盾与目标输出裁剪框架库，记录调用链；
8. 选择正式本体中能承接的对象、关系、变量、规则与证据要求；
9. 生成研究逻辑与任务本体视图，二者一致；
10. 强制缺口扫描（直接覆盖 / 上位覆盖 / 弱覆盖 / 缺失），写清使用限制；
11. 判定草稿、最低通过或正式交付质量。

### 1.2 不负责

1. 不改变 01 已记录的意图、对象、比较范围、时间、前提、用途与交付深度；
2. 不查询现实材料，不创建公司/产品/价格等实例，不判断证据是否已满足；
3. 不输出方向性结论；核心待验证命题不得写成已被证据支持的看法，也不得诱导 03「去找支持该结论的证据」；
4. 不为迁就本体而掩盖对象差异；不把一次性事实写成正式本体定义。

03 做证据准备，04 做路径推理与判断定稿。02 只定义「应该如何判断」和「概念体系如何承接」。

## 2. 完成后应能回答什么

1. **核心待验证命题**：主矛盾与主导机制（待验证主线，不是结论）；
2. **最小问题树**：子问题及前置/并列/竞争/停止关系；
3. **结构分化**：哪些不能合并判断，为什么；
4. **主路径**与**反证 / 竞争解释**；
5. **最低验证条件**与**降级规则**（每个核心判断）；
6. **框架使用**：直接框架、前置、增强、下游、场景卡；裁剪与排除理由；
7. **本体承接与缺口**：正式项、候选、缺口及对 03/04 的限制；
8. **交给 03 什么**：可直接取证的需求 vs 仅能作限制条件的项。

只纳入会影响本次判断的内容。「可能相关」但不能改变路径或结论强弱的，不进入本次框架。

## 3. 如何承接 01 的研究需求

01 给出的是研究意图和边界，不是现成的分析框架。02 应保留 01 的核心问题，同时重新判断这个问题应如何拆解。

| 01 提供的内容 | 02 需要作出的判断 |
|---------------|-------------------|
| 核心问题 | 真正需要辨别的机制和矛盾是什么 |
| 研究对象 | 是否需要按产品、角色、环节或公司分别讨论 |
| 判断起点 | 应从事件、状态、假设还是历史事实开始 |
| 观察维度 | 哪些变化是原因、过程、结果或验证信号 |
| 关系提示 | 哪些传导需要验证，哪些只是初步设想 |
| 时间与对象范围 | 哪些边界必须保持，哪些内部差异需要进一步拆分 |
| 初步验证和反面证据方向 | 如何转化为传导环节、支持条件、判断不再成立的条件和替代解释 |

02 可以补充严谨分析不可缺少的结构，但不能借“完善框架”改变 01 的问题、主要对象或研究边界。发现这些内容仍有关键歧义时，应退回 01。

01 中的相对时间和动态对象选择应保持原意。02 只说明这些规则会怎样影响研究框架，不把它们固化为文档生成日对应的绝对日期或临时对象名单。

## 4. 如何独立搭建研究框架

研究框架应从当前问题本身出发独立形成。框架库可以帮助更快地想到常见机制、证据和反面证据，但不能代替本次判断，也不能把库中某个模板拆出几项就当作研究框架。

### 5.1 先形成核心待验证命题

先判断表面问题背后真正要区分什么，并写成一句核心待验证命题。例如，“价格上涨能否持续”可能需要区分：

- 需求真实增长，还是补库、抢单或重复下单；
- 名义产能不足，还是良率、认证、材料或封装限制导致有效供给不足；
- 基本面改善，还是预期、估值和资金推动；
- 总量变化，还是产品结构或客户结构迁移。

只有核心矛盾明确，后面的对象拆分、路径和证据要求才有依据。核心待验证命题回答“真正的核心矛盾是什么”，不回答“当前应看多/看空/看中性”；方向性结论留给 03 取证之后的 04。

### 5.2 再搭最小问题树和分析顺序

把总问题拆成若干能够分别验证的子问题，并说明它们之间的关系：

- 哪些问题是前置条件；
- 哪些问题需要并列比较；
- 哪些问题代表其他可能解释；
- 哪个节点失败后，后续传导应停止。

问题树应服务于判断，而不是追求覆盖所有相关主题。每个子问题都应能够被证据增强、削弱或否定。

### 5.2A 核心判断与优先级

问题树中的每个子问题不自动等于一个核心判断。只有当它能够形成独立的待验证观点（系统字段 `CandidateClaim`），并具有独立证据要求和降级结果时，才建立核心判断记录（`JudgmentUnit`）。

每个核心判断必须包含：

| 字段 | 作用 |
|---|---|
| judgment_unit_id | 02—复盘全链稳定主键，后续不得重编号；格式 `JU-nn` |
| candidate_claim | 04 预期回答的可证伪命题，不是来源主张 |
| judgment_type | 必须使用公共合同十类原子判断：`state_measurement` / `trend_direction` / `cycle_phase` / `mechanism_validation` / `causal_attribution` / `transmission_path` / `object_differentiation` / `impact_realization` / `expectation_gap` / `valuation_impact`；风险重估属于复合任务意图，必须拆成原子 JU |
| content_hash | 由完整 JU 语义对象稳定计算；03、04 必须原样继承，发现类型或拆分错误只能返回 02 修改 |
| priority_tier | critical / important / supporting / background |
| decision_weight | 1—5，仅表示对总判断的相对重要性 |
| decision_role | 决定方向、决定强度、解释分化、验证机制或提供背景 |
| priority_rationale | 为什么它会改变总判断 |
| linked_questions / linked_paths | 对应问题树和路径 |
| evidence_requirement_refs | 对应的取证要求 |

优先级不是装饰性星级，也不参与证据可信度计算。建议每次任务只保留 2—3 个 critical 单元；critical 单元中任一被阻断或出现重大反证，都必须触发整体判断重算。background 单元不得因为材料易得而抢占取证预算，也不得单独升级整体结论。

研究逻辑正文应先说明 critical 单元，再说明 important 和 supporting 单元。若所有单元权重相同，02 应视为尚未识别决定性变量并返工。

### 5.3 确定对象、范围和必要差异

对象是否拆分，取决于不同子对象是否具有不同机制、证据口径或反面证据条件。

例如，研究存储芯片周期时，DRAM、NAND 和 HBM 是否分别分析，应由它们的需求、供给、库存和价格机制是否不同决定；不能因为都属于存储芯片就合并，也不能因为彼此相关就全部展开。

时间、地域、产业链和公司范围同样遵循“足以回答问题”的原则。范围过小会漏掉关键传导，范围过大会稀释核心待验证命题。

### 5.4 组织主路径、反面证据和替代解释

主路径说明本次最需要验证的传导，例如：

```text
终端需求变化
→ 订单与库存变化
→ 有效供给松紧
→ 价格与交期变化
→ 公司收入和利润影响
```

同时说明：

- 哪些条件会削弱或逻辑失效主路径；
- 是否存在能够解释同一现象的其他路径；
- 不同解释需要用什么信息区分；
- 哪些前置节点不成立时，不能继续向后推导。

反面证据不是附加清单，而是研究框架的一部分。

### 5.5 明确最低验证条件

对每个关键判断说明：

- 需要确认哪些现实对象和关系；
- 需要观察哪些变化、数值或时点；
- 什么证据会增强判断；
- 什么证据会削弱、逻辑失效或支持替代解释；
- 最低需要看到什么，才值得继续验证下一层路径。

02 只定义这些验证需要，不提前判断现实中是否已经具备。

### 5.6 用框架库检查和完善

独立形成基本研究框架后，可以参考 [`methods/02_判断结构/README.md`](../../../methods/02_判断结构/README.md) 及相关框架，检查是否遗漏常见机制、对象差异、传导环节、最低证据或反证条件。

框架库的作用是启发、加速和校验，不是替代本次判断。最终保留什么、删去什么、增加什么，仍由本次问题决定。即使库中没有合适框架，02 也应根据问题本身形成完整的研究逻辑；即使库中存在高度相似的框架，也要重新判断其是否适用于本次对象、范围和目标。

使用框架库时，应特别避免两类错误：

1. **关键词套框架**：看到 HBM、AI、车规、国产替代等词，就直接引用对应框架，而没有先判断本次核心矛盾；
2. **平铺堆框架**：为了显得完整，把所有相关框架都搬入 02，导致问题树变宽、主路径失焦。

### 5.7 框架选择与裁剪规则

02 **不按任务总框架数量**组织研究，而按**核心研究主线 → 关键判断单元 → 输出门槛倒推调用链**组织研究。任务级、判断单元级、路径级必须分开。

研究员口径：探索阶段可以对照看 2—3 个候选框架；写入 02 时，每个关键判断单元只收敛为 **1 个直接框架**，需要时再叠 0—1 个行业增强、0—1 张场景卡。限制的是「同一单元并列多个主机制」，不是「整次任务只能用一个框架」。前置与下游可按门槛串行接续。

任务先形成核心待验证命题与 2—3 个关键判断单元；每个判断单元再选择一个主判断类型、一条可证伪观点、一个直接框架，并按目标输出门槛倒推必要前置。场景卡挂在判断单元上，不得当作正式框架。

三层原则：

1. **任务级**：1 条核心待验证命题；原则上 2—3 个关键判断单元；不限定任务总引用框架数，但必须形成清楚的调用链；
2. **判断单元级**：每个关键判断单元原则上 1 个直接框架、0—1 个行业增强、0—1 张主要场景卡；限制的是并行宽度，不是串行深度；
3. **路径级**：可为输出门槛串行调用前置与下游承接框架；串行接续不计入并行宽度；
4. **纳入与排除**：框架须至少改变输出门槛、必要前置、主路径 / 反证 / 停止条件或明确下游输出之一；否则排除并按收窄范围记录理由（可含探索时淘汰的近邻候选）。

不得把“任务总调用 ≥3 个正式框架”自动等同于范围未收敛。真正需要返工的是：判断单元过宽、多主线无主次、增强无边际价值、重复生成、场景卡替代机制判断，或调用链无法说明为何经过某一层。详细选用顺序、五类调用角色、串并行口径、排除范围与使用后必须说明项见 [`02_附录1_框架裁剪与选用细则.md`](02_附录1_框架裁剪与选用细则.md)；问题—框架索引只在 [`methods/02_判断结构/README.md`](../../../methods/02_判断结构/README.md#5-框架选择索引) 维护。

最终进入 02 的不是“框架全集”，而是围绕本次核心待验证命题、按判断单元与输出门槛裁剪后的最小可用调用链。

## 5. 如何形成任务本体视图

研究逻辑讲清“这个问题应该怎样分析”，任务本体视图说明“这套分析如何由本体承接”。二者先后有别：先把研究逻辑想清楚，再匹配本体；二者表达的是同一套判断，但面向不同读者。

### 6.1 两个文件的分工

02 输出两份配套文件：研究逻辑 Markdown 和本体视图 YAML。二者表达同一套判断任务，但用途不同。

研究逻辑 Markdown 面向研究员，负责说明“这个问题应该怎么分析”，包括核心矛盾、问题拆解、对象差异、主逻辑、相反证据、其他可能解释和证据要求。

本体视图 YAML 面向 03 和系统处理，负责说明“这套分析如何被本体承接”，包括正式本体引用、框架使用记录、路径节点、实例需求、观测需求、证据要求、反证要求、任务候选和本体缺口。

| 文件            | 负责什么            | 不负责什么                             |
| ------------- | --------------- | --------------------------------- |
| 研究逻辑 Markdown | 讲清研究框架和分析理由     | 不承载 judgment_unit_id、路径 ID、证据要求 ID 等机器表 |
| 本体视图 YAML     | 承接本体、路径、实例和证据需求 | 不重复面向研究员的大段分析正文                   |

**Markdown 正文章节用语（内部逻辑能力不变，仅输出层改名）：**

| 内部能力 / YAML 字段 | 研究逻辑正文章节或表述 |
|---|---|
| `judgment_landing` | 要回答的问题类型 |
| `judgment_spine` | 核心待验证命题 |
| 最小问题树 | 问题拆解与分析顺序 → 子问题清单 |
| 主路径 / 反面证据 / 竞争解释 | 主逻辑与其他可能 |
| 结构分化 | 细分差异与比较口径 |
| `judgment_units` | 关键结论与证据要求（正文不写 ID 表） |
| `handoff_to_03` | 证据准备说明（正文不写 YAML 路径表） |

Markdown 应能独立阅读；YAML 应能直接交给 03 使用。正文不得把 YAML 中的 statement 原句贴入；完整技术表达以 YAML 与 CSV 为准。

### 6.2 正式本体引用原则

任务本体视图不是重新定义本体，而是在正式本体中切出本次任务需要的最小结构。

写入 `semantic_view`、`reasoning_view`、`evidence_view` 的对象类型、关系类型、事件类型、关键变量、传导模板、推理规则和证据要求，都必须来自正式本体规范，不得临时编造。

引用顺序如下：

1. 先查[ontology/01_通用/](../../../ontology/01_通用)；
2. 再查本任务所属领域本体规范（例如半导体任务参考 [ontology/02_领域/semiconductor/](../../../ontology/02_领域/semiconductor)）；
3. 领域规范是一级规范之上的扩展，二者边界不一致时，以领域规范为准，并在 YAML 中记录来源；
4. 正式规范未覆盖的内容，不得冒充正式本体，应记录为任务候选或本体缺口。

YAML 中应通过 `ontology_sources`、`source_ref`、`source_version` 记录本次引用了哪些规范和定义。

如果缺的是现实公司、产品、事件、数值或材料，交给 03 作为实例、观测或证据需求；如果缺的是稳定的对象类型、关系类型、关键变量、事件类型、规则或证据结构，才记录为本体缺口。

证据要求也必须沿用正式本体。状态变量与证据画像的绑定、画像正文从 `business_instances.yaml` 读取；质量维度、商业化阶段与事件分类从 `semiconductor_extension.yaml` 的 `domain_guides` / `event_taxonomy` 读取。02 负责选择本次需要的证据画像，并把画像引用和任务特定的最低要求写入 `evidence_view`；03 据此寻找材料和判断质量，不重新设计证据标准。

`semiconductor_extension.yaml` 的领域指南不是数据源。一次任务缺少材料或来源时，应交给 03 记录为数据或证据缺口；只有缺少可长期复用的证据画像、质量规则或正式绑定时，才记录为本体缺口。

任务候选只用于本次研究临时承接尚未正式入库、但又不可缺少的结构。它不得混入正式本体，并应说明使用理由、边界和风险。

公司盈利承接不得在任务视图中另造“兑现率”“盈利弹性分”等自由参数。需要从行业结论落到公司时，应选择或补充正式 StateVariable，并用 `variableInfluencesVariable` 组织“产业状态 → 公司暴露 → 量/价/结构/成本 → 收入/利润/现金流”的条件路径；现实值交给 03 的 Observation，规则命中与判断交给 04 的 RuleEvaluation、Judgment 和 ReasoningTrace。高价值行业任务默认可把 JU 落到公共合同已有的 `impact_realization`；只有任务确实要求预期或估值比较时才使用 `expectation_gap` / `valuation_impact`。

### 6.2A 证据回环与结构修订

每个 2.2 任务视图必须声明 `iteration_contract`，并满足：

1. 证据触发单位是冻结批次，不是单条来源；
2. 已有结构内的证据更新返回 03，不重建 02；
3. 新 StateVariable、Hypothesis、Scenario、结构关系、路径、竞争解释或范围拆分返回 02；
4. 根问题、根范围、任务类型或判断落点改变返回 01；
5. 结构修订只使用公共合同约定的 `supersedes_trace` 与 `runtime_revision_operation`；
6. `task_context.view_hash` 绑定排除自证字段和纯审计生成时间后的完整视图内容；
7. 新 attempt 不覆盖旧 attempt，必须记录 `supersedes_attempt`。

### 6.3 本体映射不得用上位概念冒充充分覆盖

02 在匹配正式本体时，不允许仅凭“存在上位对象、上位变量或通用路径”判定已经覆盖。本体承接必须同时通过三项测试：

1. **结构可映射**：能映射到明确对象、状态变量、关系、路径、规则或证据画像；
2. **证据可收集**：03 能据此设计实例、观测、证据和反证需求；
3. **推理可使用**：04 能据此判断路径成立程度、削弱条件、阻断条件、竞争解释或结论强度。

覆盖状态分为四类：

| 覆盖状态 | 判定标准 | 后续使用 |
|---|---|---|
| `direct_cover` | 已有正式本体项能够直接承接，且能指导 03 收证据、支撑 04 推理 | 可进入正式 03 和 04 |
| `upper_cover` | 只有明确上位类能够承接，但缺少本次问题需要的细分对象、变量、路径或规则 | 可进入 03，但必须记录候选补丁或限制 |
| `weak_cover` | 能做概念描述，但不能形成可执行证据需求或推理规则 | 只能作为观察或缺口说明，不支撑强判断 |
| `missing` | 正式本体没有可用承接项 | 必须记录本体缺口，必要时阻断进入 03 |

例如，研究地缘冲击对半导体的影响时，`SupplyRisk`、`CostImpact`、`ExternalShock` 等上位概念只能提供初步承接。若本次判断依赖航运中断、能源成本、关键材料安全库存、区域产能暴露或军事订单拉动，就必须继续判断这些内容是 `direct_cover`、`upper_cover`、`weak_cover` 还是 `missing`，不能用“风险”“影响”“变化”等泛词替代。

### 6.4 本体视图怎样承接研究逻辑

任务本体视图不是整份本体，也不是研究结论，而是为本次问题切出的一块最小充分结构。研究逻辑中的对象差异、框架使用、关系、事件/状态变量、主路径与验证需求，应分别落入对象类型、`framework_usage`、关系类型、事件/关键变量、传导模板/路径，以及实例需求与证据画像。

YAML 中应单独保留 `framework_usage`，用于记录框架选择与裁剪，不得把框架 ID 直接混入正式本体定义。状态变量还必须满足完整出口链：

```text
reasoning_view.state_variables
→ candidate_paths.nodes[].ontology_refs.state_variables
→ instance_requirements.state_bindings
→ instance_requirements.observations
→ instance_requirements.evidence_bindings
→ evidence_view.evidence_profiles
```

`validation.checks.state_variable_chain_complete` 为 `false` 时不得进入 03。字段示例与完整映射表以 [`模板/02_任务本体视图模板.yaml`](模板/02_任务本体视图模板.yaml) 为准。

关键变量可以由 03 准备直接观测、事件或代理信号，但 03 不得由此计算变量方向或执行变量间传导。只有 04 可以在证据是否够用确认后应用 02 选定的规则。若概念无法稳定定义，应先澄清逻辑，再决定是否记录本体缺口。

### 6.5 核心判断的取证交接边界

02 的 `judgment_units` 只说明“这个判断是什么类型、需要什么证据角色”，不得把 03 采用的最低证据组合、必要证据完成状态、本次证据归档或“证据是否够用”评价塞回核心判断。

每个核心判断至少交接：

| 字段 | 说明 |
|---|---|
| candidate_claim | 04 预期形成的可证伪命题；不得与 EvidenceClaim 混用 |
| priority_tier / decision_weight | 对总判断的优先级与相对权重 |
| decision_role / priority_rationale | 对总判断起什么作用、为什么重要 |
| `judgment_type` | 用于 03 匹配取证策略或配方标签 |
| `required_evidence_roles` | 主证据、交叉验证、反证、阻断条件、代理和背景材料的要求状态 |
| `required_evidence_categories` | 价格、需求、供给、库存、订单、政策、估值、财务、暴露等证据类别 |
| `required_counter_categories` | 必须主动检查的反证和竞争解释类别 |
| `candidate_evidence_recipe_tags` | 推荐 03 优先匹配的最低证据组合标签，不等同于已经采用的组合 |
| `minimum_validation_conditions` | 进入 04 对应观点前的最低验证条件 |
| `forbidden_shortcuts` | 禁止使用的偷换证据方式 |
| `proxy_policy` | 是否允许代理指标以及使用边界 |
| `evidence_gap_policy` | 缺证时 04 应如何降级、停止或返工 |

02 的 `evidence_requirements` 只表达“本次必须取得什么证据”。它可以写目标核心判断、路径节点、状态变量、证据角色、证据类别、内容域、对象范围、时间范围、最低质量、来源层级、独立来源数、必需篮子引用、反证篮子引用、代理许可、首选来源画像、允许取数通道、禁用来源、时效、追溯、可比口径、停止条件、缺失策略和 04 降级方式。

证据要求主键使用 `ER-nn`。每个 `critical` / `important` 判断单元必须至少被一条 `ER-nn` 的 `linked_judgment_units` 覆盖。跨阶段 ID 约定见 [`../governance/02_合同/public_contract.yaml`](../../../governance/02_合同/public_contract.yaml) 的 `cross_stage_references`；03 必须继承全部 `ER-nn`，不得只保留按单元汇总的 `ER-JU-*`。

完整取证方法属于 03 取证策略库；必要证据组合实际满足情况、来源画像、取数通道、代理指标登记和“证据是否够用”评价属于 03 本次证据归档。02 不得预填这些运行结果。

### 6.6 两个文件的一致性要求

研究逻辑 Markdown 和本体视图 YAML 必须表达同一个判断任务。
Markdown 中的关键对象、变量、路径、证据和反面证据，应在 YAML 中找到对应结构；YAML 中的路径、节点、实例需求和证据需求，也应能回到 Markdown 中找到分析依据。
如果任一文件的核心逻辑发生变化，另一份文件必须同步更新。YAML 中不得出现不服务正文判断的孤立结构。Markdown 附录只提供快速定位，不能代替 YAML 的完整技术表达。

## 6. 本体缺口强制扫描与处理规则

02 必须把本体缺口扫描作为固定质量门槛，而不是生成失败时的异常兜底。每次 02 都必须完成缺口扫描；只有扫描通过，才允许标记为 `minimum_pass` 并进入正式 03。

### 7.1 缺口扫描先于本体视图定稿

02 不应先生成一套看似完整的本体视图，再简单判断“是否有缺口”。正确顺序是：

```text
01 研究问题与边界
→ 必要本体项清单
→ 正式本体映射
→ 覆盖状态判定
→ 下游压力测试
→ 本体视图定稿 / 缺口说明 / 退回返工
```

必要本体项至少包括：

1. 本次必须分析的对象、对象类型、对象分层和对象差异；
2. 本次必须观察的状态变量；
3. 影响路径所需的关系、事件类型和传导模板；
4. 核心判断所需的推理规则；
5. 削弱、阻断、反证和竞争解释条件；
6. 03 可执行的实例需求、观测需求、证据画像和反证画像；
7. 04 和 05 预期输出所需的判断口径。

### 7.2 缺口扫描矩阵与处理细则

每次 02 必须在 YAML 或配套扫描文件中形成缺口扫描矩阵，并完成下游压力测试、必须记录条件检查、缺口分级与缺口说明生成。字段矩阵、压力测试问题、必须记录情形、分级表与缺口说明生成规则见 [`02_附录2_本体缺口扫描矩阵与处理细则.md`](02_附录2_本体缺口扫描矩阵与处理细则.md)。

`coverage_status` 必须区分 `direct_cover` / `upper_cover` / `weak_cover` / `missing`；`gap_severity` 使用 `none` / `minor` / `major` / `blocking`。阶段扫描结果写入：

```yaml
ontology_gap_scan:
  status: no_gap | minor_gap | major_gap | blocking_gap
  can_enter_03: true | false
  limitation_for_03: []
  limitation_for_04: []
```

`blocking_gap` 不得进入正式 03；`major_gap` 原则上返工 02。缺口说明只记录缺失能力、影响与下游限制，不直接决定正式本体如何修改。

## 7. 质量门槛与返工规则

本节是 02 阶段质量要求和返工条件的唯一权威。全局质量定义和正式发布规则见 `../governance/03_校验/00A_高质量产出判别标准.md`。

### 8.1 进入 03 的最低条件

满足以下条件时，02 可以标记为 `minimum_pass`，并进入 03：

1. 研究问题、对象、范围、时间和用途与 01 一致；
2. 已形成核心待验证命题，且没有把 01 的问题偷换为更容易回答的问题；
3. 已形成最小问题树，并说明前置、并列、竞争和停止关系；
4. 已说明对象是否需要拆分，以及拆分依据；
5. 已列出主路径、削弱条件、阻断条件、反证和竞争解释；
6. 每个核心判断都有最低验证条件和不满足时的降级规则；
7. 已说明框架库使用情况，包括调用角色与调用链、场景卡归属判断单元、裁剪模块和排除理由；
8. 研究逻辑 Markdown 与本体视图 YAML 表达同一套判断；
9. 每个选中状态变量都有路径节点、状态绑定、观测需求和证据画像出口链；
10. 已完成本体缺口扫描，且每个必要本体项都有覆盖状态、证据可收集性和推理可使用性判断；
11. 正式本体、任务候选和本体缺口的边界清楚；
12. 不存在未处理的 `major` 或 `blocking` 缺口；
13. 已明确传递给 03 的实例、观测、证据、反证需求和使用限制；
14. 每个核心判断具备 `judgment_type`、必需证据角色、证据类别、反证类别、最低验证条件、禁止捷径和代理边界。
15. 每个核心判断具备待验证观点、优先级、决策权重、决策角色和优先级理由，且最高优先级的判断原则上不超过 3 个。

`minimum_pass` 只表示可以进入 03，不代表本阶段输出已经达到正式交付质量。

### 8.2 高质量语义门槛

满足以下条件时，02 才能标记为 `high_quality_pass`：

1. 核心待验证命题足够清晰，研究员读完能知道本次真正要辨别什么；
2. 问题树是“最小可判断结构”，没有无关扩展或框架拼贴；
3. 框架选择能够解释为什么这样组合，而不是按标题、热点词或行业标签机械匹配；
4. 主逻辑、反证逻辑和竞争解释都能落到可执行验证；
5. 停止条件不是“材料足够多”，而是核心判断达到最低验证条件；
6. 降级规则能明确约束 04 不能越权输出；
7. 本体映射服务研究逻辑，而不是用技术字段掩盖逻辑不清；
8. Markdown 对研究员可读，YAML 对 03 可执行；
9. 缺口扫描没有停留在自评层面，而是完成必要本体项映射、下游压力测试和必须记录情形检查；
10. 使用任务候选或存在本体缺口时，已经说明对后续证据准备和推理输出的限制。
11. 证据交接没有把 03 的配方执行、必要证据组合状态、本次证据归档或“证据是否够用”评价提前写入 02 核心判断。
12. critical 单元确实决定总判断，important、supporting 和 background 未被写成同等优先。

### 8.3 本阶段不得出现

02 不得出现以下问题：

1. 只讲行业常识，没有核心待验证命题；
2. 只列变量，没有最小问题树；
3. 只有主线，没有反面证据和其他可能解释；
4. 把框架库内容拼贴成分析结构；
5. 为了完整，把所有相关对象、变量和路径都纳入；
6. 每个节点都写“需要证据验证”，但没有最低验证条件；
7. 停止条件是“继续收集更多资料”；
8. 本体视图靠自填字段通过，但关键变量出口链无法被 03 使用；
9. Markdown 和 YAML 的对象、路径、变量或证据要求不一致；
10. 在 02 中提前形成现实结论或业务方向判断；
11. 未说明调用角色、判断单元归属与目标输出门槛，或调用链角色不清；
12. 同一判断单元并列多个直接框架，或同一判断单元挂多张主要场景卡，导致并行过宽；
13. 将场景卡、热点问题或案例复盘误当作正式框架；
14. 只因关键词相似而引用框架，未检查对象、范围、机制、输出门槛和证据条件是否适配；
15. 未按收窄范围说明排除理由，或对启用调用无法解释为何必须经过这一层；
16. 用上位概念、泛化变量或抽象风险词冒充本体充分覆盖；
17. 只写“无明显缺口”，但没有必要本体项清单、覆盖状态和下游压力测试；
18. 明明需要 03 临时补对象、变量、路径或证据画像，却仍将 02 标记为无缺口通过。
19. 把单值 `evidence_role` 当作核心判断全部证据要求，未区分主证据、交叉验证、反证、阻断条件和代理指标。
20. 所有核心判断权重相同，或 critical 项过多，导致证据预算与报告篇幅失焦。

### 8.4 返工规则

出现以下任一情况，02 不得进入 03：

| 问题表现 | 处理 |
|---|---|
| 发现 01 的问题、对象、用途或范围仍有关键歧义 | 退回 01 |
| 核心待验证命题不清，无法说明本次真正要辨别什么 | 返工 02 |
| 最小问题树缺失或过宽 | 返工 02 |
| 判断单元并行过宽、调用链无法解释，或仅按关键词匹配导致核心待验证命题失焦 | 返工 02 |
| 主路径、反证和竞争解释无法区分 | 返工 02 |
| 核心判断没有最低验证条件 | 返工 02 |
| 本体无法承接关键机制，且未记录任务候选或本体缺口 | 返工 02 或进入本体优化 |
| 缺口扫描矩阵缺失，或只做主观自评 | 返工 02 |
| 必要本体项大量停留在 `upper_cover` 或 `weak_cover`，但仍判定无缺口 | 返工 02 |
| 出现 `major` 或 `blocking` 缺口，但未生成缺口说明 | 返工 02 或进入本体优化 |
| 研究逻辑 Markdown 与本体视图 YAML 不一致 | 返工 02 |
| 证据需求无法被 03 执行 | 返工 02 |

返工说明必须写清：问题发生在哪个核心问题、影响哪个路径或变量、需要修改什么，以及修改后如何重新校验。

## 8. 输出及与 03 的交接

### 8.1 输出文件

02 每次生成一组同主题、同日期、同序号的配套文件：

```text
02-<核心主题>研究逻辑-<YYYYMMDD>-<当日序号>.md
02-<核心主题>本体视图-<YYYYMMDD>-<当日序号>.yaml
```

例如：

```text
02-存储芯片周期研究逻辑-20260611-1.md
02-存储芯片周期本体视图-20260611-1.yaml
```

如存在会影响本次研究的本体缺口，可另行生成：

```text
02-存储芯片周期本体缺口说明-20260611-1.md
```

本体缺口不改变已经明确的 01 用户意图。如果缺口不阻断当前任务，可以不单独生成说明，但必须在本体视图的候选与缺口部分写清限制。

命名要求：

1. 正式产出必须以阶段前缀 `02-` 开头；
2. 核心主题使用能够识别研究对象和核心待验证命题的简短业务表述；
3. 日期使用文件实际生成日期；
4. 序号从 `1` 开始，同日同主题依次递增；
5. 配套文件必须使用相同的核心主题、日期和序号；
6. 文件日期只用于审计，不作为滚动时间范围的锚点。

研究逻辑 Markdown 和任务本体视图 YAML 的 front matter / `quality_control` 应同时保留阶段状态和产出质量。字段与章节以 `模板/02_研究逻辑模板.md`、`模板/02_任务本体视图模板.yaml` 为准；可选缺口说明见 `模板/02_本体缺口说明模板.md`。

研究逻辑 Markdown front matter 至少应包含：

```yaml
stage_status: not_started | in_progress | complete | blocked | returned
quality_status: draft | minimum_pass | high_quality_pass | return_required
ontology_gap_scan_status: no_gap | minor_gap | major_gap | blocking_gap
can_enter_03: true | false
framework_usage_ref: "<如在 YAML 中记录 framework_usage，写明对应字段或摘要>"
```

具体正文和结构化字段见 `模板/02_研究逻辑模板.md`、`模板/02_任务本体视图模板.yaml` 和可选的 `模板/02_本体缺口说明模板.md`。


### 8.2 进入 03 前应确认什么

交给 03 前，应确认：

1. 研究问题、对象和边界与 01 一致；
2. 研究逻辑已经讲清核心矛盾、问题拆解、主路径、反证和替代解释；
3. 已记录框架库使用情况，包括调用角色与调用链、场景卡归属、裁剪模块和排除理由；
4. 关键对象、关系、变化和路径已在 YAML 中被正式本体、任务候选或缺口记录承接；
5. 每个关键判断都有对应的实例、观测、证据或反证需求；
6. 每项证据和反证要求都绑定了可解析的证据要求；
7. 研究逻辑文件与本体视图文件编号、路径和含义一致；
8. 已完成本体缺口扫描，并明确每个必要项能否指导取证、能否支撑推理；
9. 不存在未处理的重大缺口或阻断性缺口；
10. 使用任务候选或存在本体缺口时，相关限制已明确传给 03 和 04；
11. 选中的状态变量已形成完整绑定与观测/证据出口；
12. 缺口扫描完成且允许进入 03；
13. 02 至少达到最低通过；作为正式交付物则须高质量通过。

如果 03 发现缺的是数据、实例或证据，由 03 继续处理；如果发现研究路径、本体承接或对象拆分有误，应退回 02；如果问题边界仍不清楚，应退回 01。
