# 本体约束的投研判断工作台

以本体提供语义与约束、以证据与确定性计算提供事实基础、以 LLM 完成受约束判断。把投研问题收成可核对、可反证、可复盘的判断：依据是什么、能说到多强、什么情况下要改。

阶段分工：`02` 搭结构，`03` 备事实与计算，`04` 做判断；本体贯穿三者，但不替代任一阶段。

当前完整样例主要在**半导体**（存储周期、管制与国产设备替代）。不是全行业自动投研产品。

## 你怎么用

1. 提出问题（对象、时间、你要回答什么）。
2. 按 01—05 做一次研究（可分步，也可一次出齐）。
3. 先读研报（05），再读判断简报（04）。

| 适合问 | 不适合问 |
|--------|----------|
| 供需/趋势会不会变、事件有没有影响、冲击怎么传导、某个假设还成不成立 | 查数、买卖建议、必须给出确定价格或涨跌 |

对照样例：[`memory-cycle-run-002`](instances/02_V3样例/01_memory-cycle-run-002) · [`us-controls-localization-run-002`](instances/02_V3样例/02_us-controls-localization-run-002)。

## 最终结果怎么读

对外主要看两份：

| 文件 | 里面有什么 |
|------|------------|
| **研报（05）** | 当前判断、主要依据、适用范围、还要跟踪什么 |
| **判断简报（04）** | 每条结论能说到多强、最大限制、出现什么信号需要改判 |

前面的需求说明、研究逻辑、证据材料是过程底稿；核对「问题有没有被偷换、证据够不够」时再翻。

读结果时看四件事：

- 现在的判断是什么；
- 凭什么（关键依据，不是材料堆砌）；
- 边界在哪；
- 证据不够时有没有硬撑——说不清就应写「暂不可判断」并标明缺什么。

## 可用金融数据源

**工作台可以走 MCP 取数**：Stage03 模型生成 / 补证时，worker 会优先调用已接入的一手通道（巨潮 `cninfo`、通联财务 `datayes-stock-finoper-mcp`、中央政策 `china-policy`），失败再回退 Bing / 公开网页。实现见 `runtime/adapters/mcp_evidence.ts`。

这不等于「页面上有个 MCP 按钮」：
- **模型自动取证**：后台调 MCP（需本机配置 `~/.workbuddy/mcp.json` 且 `npm run worker` 在跑）
- **研究员手动补证**：在证据编辑页贴公开 URL 抓取核验

核心原则不变：**MCP 是获取通道，不是来源生产者**——返回的是线索/摘录，写正式证据前仍须核验可核对原文。B03 注册表里其余通道（行情、基金、华泰研报等）目前主要给外部 Agent 用，尚未全部接到 Runtime。

| 类别 | 覆盖 | 入口文件 |
|------|------|----------|
| 法定披露 | A股公告、政策原文 | `methods/03_取证/B03_MCP通道注册.md` |
| 行情与财务 | A股 K 线、三表、持仓、宏观、指数、基金 | `methods/03_取证/OPS_MCP查询快速参考.md` |
| 研报与资讯 | 华泰研报、财新新闻 | `methods/03_取证/03_registry.yaml`（acquisition_channels 节点） |
| Web 回退 | 网页提取 | `methods/03_取证/OPS_*` 手册 |

MCP 不可用时回退链：`OPS_MCP` → `OPS_通用` / `OPS_半导体` / `OPS_地缘` 手册的 Web 路径。

## 数据与来源限制

本项目**不自带数据库**，也不保证能拿到所有行业数据。能用的只有当时有权限、可核对原文的材料。缺数据时，合格结果往往是「边界清楚的弱判断或缺口说明」，而不是编一个方向。

## 五层职责（概念）

项目按五层分工，层间可引用、职责不重复。完整上位表述见 [`governance/01_架构/00_项目定位与边界.md`](governance/01_架构/00_项目定位与边界.md) 第 0 节三段式总纲。

| 层 | 目录 | 管什么 |
|----|------|--------|
| 语义本体 | `ontology/` | 稳定对象、关系、状态与约束 |
| 方法资产 | `methods/` | 怎样判断、要什么证据、能裁到哪 |
| AI 运行时 | `runtime/` | 本次怎样选方法、绑证据、应用规则 |
| 研究记录 | `instances/` | 本次实际做了什么、得出什么判断 |
| 表达交付 | `delivery/` | 结果怎样写给不同读者 |

`workflow/` 是阶段合同，`governance/` 是上位约束，二者是这五层的执行边界与治理框架。

**三层公式：** 可靠判断 = 确定性计算（取证与统计） + 语义与约束（本体） + 受约束的开放推理（LLM）。**推理发生在 04 与 `runtime/`，不是本体自动推出结论；01—05 是研究阶段合同，不是本体推理链。** 本体是运行时语义与约束基础设施（统一概念、限定关系、约束 I/O、帮助选上下文），不是专业词典，也不是推理引擎。

## 仓库怎么找东西

按研究员日常用法编号；顶层目录名保持简短英文，方便工具引用。

| 编号 | 目录 | 你什么时候打开 |
|------|------|----------------|
| 1 | [`workflow/`](workflow) | 做研究：01—05 每一步写什么、交什么 |
| 2 | [`methods/`](methods) | 选用框架、取证方法、裁决方法 |
| 3 | [`ontology/`](ontology) | 查对象/关系/变量的稳定定义（少翻） |
| 4 | [`instances/`](instances) | 看语义黄金样例（`semantic_fixture`）；本机运行数据也在这里 |
| 5 | [`delivery/`](delivery) | 研报模板与表达标准（写 05 时用） |
| 6 | [`evaluation/`](evaluation) | 评测这套流程有没有用（可选） |
| — | [`runtime/`](runtime) | 本机工作台（产品界面） |
| — | [`governance/`](governance) | 定位边界、质量标准、校验（维护用） |

一次研究的主链：

```text
01 受理 → 02 结构 → 03 证据 → 04 判断 → 05 表达
```

## 校验（可选）

开发环境与提交前检查见 [`CONTRIBUTING.md`](CONTRIBUTING.md)。

三类运行包不要混用入口（定义见 [`governance/02_合同/package_kinds.yaml`](governance/02_合同/package_kinds.yaml)）：

| 包类型 | 是什么 | 校验 |
|--------|--------|------|

| `workbench_export` | 工作台导出（紧凑文件名） | `validate_workbench_package.py` |

```bash
python3 governance/03_校验/validate_project.py
python3 governance/03_校验/validate_v3_samples.py
```

校验通过只说明写法与引用合规，**不代替**你对数据真伪和研究价值的判断。
