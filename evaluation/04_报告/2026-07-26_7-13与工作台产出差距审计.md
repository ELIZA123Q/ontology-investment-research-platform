# 7/13 与重构工作台产出差距审计

日期：2026-07-26  
对比基准：`7:13/` 存储芯片周期完整产物  
Runtime 样本：`ac9e6a56-46fc-4f32-88a8-71cb22540d9c`

## 一、结论先行

差距不是单一模型问题。便宜模型会放大退化，但本次最主要的损失发生在工程链路：

1. 核心 Markdown 的确没有完整落到 prompt。旧加载器把每个文件正文里的第一个 `##` 错认成“下一个文件”的边界；一旦总上下文超预算，每份规范只剩标题和导语，却仍登记为已加载。
2. Stage03 把“联网取证、工具调用、来源登记、证据结构化、方法执行”压成一个超大任务。样本输入一度达到 236,943 字，先后遇到 Zod 不兼容、工具调用上限、取消，最终用全缺口 fallback 代替研究。
3. Stage04 输入已经没有事实，只能生成全 J0 fallback。Stage05 此时不可能凭写作恢复洞见，只能把缺口改写成报告。
4. 同一方法正文曾同时经 knowledge 与 selected method guidance 注入，02/03/04 上下文重复、注意力稀释，并增加超时概率。
5. 质量门偏重固定章节、字段、表格和字数，研究价值审查没有成为 Stage05 的直接放行条件。因此“合规形态”可能盖过“研究员是否能用”。
6. MCP 曾被当作 Stage03 high-quality 的必要条件。这混淆了获取通道与来源质量：公司 IR、监管/政府官网等公开原文可以是一手来源；MCP 不是证据等级。
7. 产物的 `knowledge_version` 过去只覆盖知识文件，没有覆盖 ontology 切片和 method guidance。三库虽被维护，治理版本不能证明它们实际影响了本次运行。

因此，本次差距的实质是：研究过程在 03 断裂，04/05 继续完成了流程形态。它不是“同一方法论换了模型后文风变差”，而是方法论的关键动作没有被可靠执行。

## 二、逐阶段对比

| 阶段 | 7/13 基准 | Runtime 样本 | 判断 |
|---|---:|---:|---|
| 01 受理 | 8,681 字 | 3,008 字 | Runtime 边界更短，尚不是主要断点；需要保留真正的增量问题与决策用途 |
| 02 结构 | 4,241 字 | 7,565 字 | Runtime 更长但不代表更好；输入 225,771 字，结构复杂度与上下文重复显著 |
| 03 证据 | 10,119 字 | 169 字 | 决定性断点：0 条非 gap 事实、26 条 gap、0 个来源，使用 deterministic gap fallback |
| 04 判断 | 3,363 字 | 148 字 | 上游无事实，7 个判断全部为 J0，使用 deterministic J0 fallback |
| 05 表达 | 8,164 字 | 1,916 字 | 只有缺口转述；缺少可形成 Research Edge 的证据—机制—含义链 |

长度只是症状，不是单独的质量标准。更关键的是：

- 7/13 的 05 对 HBM、通用 DRAM、企业级 NAND 和消费端 NAND 做了对象分化；
- 有明确数字、来源交叉验证、主导机制、竞争解释、投资含义、证伪条件和跟踪信号；
- Runtime 05 的信息上限已由 03 的“全缺口”锁死，无法形成上述研究增量。

## 三、运行证据

完整 Runtime 样本的失败序列：

- Stage03 v1：结构化接口不支持 `optional` Zod 字段；
- Stage03 v3/v4：在工具调用上限内没有提交合法结构化结果；
- Stage03 v6：人工确认了 `runtime-deterministic-gap-fallback`；
- Stage04 v2：模型第 3 轮超时；
- Stage04 v3：人工确认了 `runtime-deterministic-j0-fallback`；
- Stage05 v2：在 183,692 字输入上生成 1,916 字缺口型正文。

这说明 fallback 被当作“流程继续”的出口，而不是“研究暂停并返工”的边界。对研究员而言，全 gap 和全 J0 可以是诚实的内部缺口报告，但不能被包装成已经完成的高质量行业研究。

## 四、已落地的修复

### 1. 修复核心 Markdown 实际未加载

- `loadKnowledge` 保留逐文件正文，不再从拼接字符串猜文件边界；
- 预算截断后，`files` 只记录真正进入 prompt 的文件；
- 新增 `files_omitted_by_budget`，不再把预算省略伪装成已加载；
- 每文件截断优先保留方法、质量门槛、停止条件和边界章节，而不是只截文件开头；
- 增加回归测试，明确验证文件第一个 H2 之后的“质量门槛与返工规则”仍进入 prompt。

### 2. 让 ontology / methods / workflow 成为真实治理输入

- 02 注入通用与半导体语义、判断本体规范；
- 03 注入通用与半导体证据域规范，以及完整的通用、半导体、地缘真实来源操作手册；
- 04 注入通用与半导体判断规范及裁决附录；
- 方法正文只经 selected method guidance 按任务路由，移除 knowledge 重复注入；
- 每次运行记录 knowledge、ontology、method guidance、scenario card 和 structured keys；
- `knowledge_version` 升级为组合治理版本：维护 ontology / methods / workflow 任一有效输入，运行版本都会变化。

### 3. 把“来源质量”与“调用通道”分开

- 取消“没有 MCP 调用就不能 high-quality”的硬门；
- MCP、Web、公开网页抓取只记录获取通道；
- 来源质量由生产者权威性、正文抓取、hash、逐字引用、时间口径和独立来源组决定；
- 公司 IR、监管、政府官网等公开原文不再因不是 MCP 返回而被降级。

### 4. 把研究价值变成 Stage05 放行门

- 00A 五项从布尔打勾升级为 0–4 分，总分至少 16/20；
- 检查问题是否偷换、是否有差异化观点与机制链、是否证据越权、是否可直接用于更新判断、是否在证据不足时硬撑；
- “有 Research Edge 表格”不再自动等于“有判断价值”；
- 由 reviewer 模型审查，不再让生产模型单独自评；
- 任一研究价值失败直接 `return_required`，Stage05 不能 `high_quality_pass`；
- 论点章最低密度由 280 字提高到 500 字；7/13 基准最短论点章为 889 字。

### 5. 模型按研究价值分层

- 支持 01–05 独立模型路由；
- 当前本机配置为 Stage01 使用 `deepseek-v4-flash`，Stage02–05 使用 `deepseek-v4-pro`；
- 便宜模型负责受理整理，核心结构、取证、裁决和表达使用更强模型。

### 6. 增加研究质量回归审计

新增 `npm run audit:research-quality -- --run=<run_id>`，离线检查：

- 每阶段相对 7/13 的正文密度；
- deterministic fallback；
- Stage03 非 gap 事实、gap 和来源数；
- Stage04 是否全 J0；
- Stage05 是否过薄及研究价值审查是否通过。

旧样本会被明确判为失败，不再因为五个阶段都有 approved 记录而显示“流程成功”。

## 五、质量定义：什么才算对研究员有价值

Stage05 的目标不是把字段翻译成自然语言，而是让研究员能够：

1. 一眼知道当前判断与市场常见判断有什么不同；
2. 知道差异来自哪个主导机制，而不是材料数量；
3. 看清不同产品、公司或环节为何不同；
4. 区分事实、解释和仍未解决的竞争解释；
5. 知道哪些信号出现时应上调、下调或推翻判断；
6. 知道判断对标的筛选、盈利预期、估值或风险监测意味着什么；
7. 不读 YAML 和审计字段也能直接使用正文。

合规字段和追溯链是必要的安全底座，但只证明“没有明显越权”；研究价值门证明“这份东西值得研究员花时间读”。两者不能互相替代。

## 六、仍需通过新运行验证的风险

本轮已经堵住“03 失败仍一路包装成高质量 05”的假绿路径，但离线修改不能证明外部模型和真实来源在下一次运行中一定成功。下一次端到端验收必须满足：

- Stage03 没有 deterministic fallback，且存在可核验的非 gap 事实和独立来源；
- Stage04 至少形成与证据强度一致的实质判断，或形成真正有决策价值的高质量缺口边界；
- Stage05 研究价值得分至少 16/20，并通过固定结构、论点密度、来源 grounding 与 Research Edge 检查；
- 回归审计通过；
- 研究员盲看时，能指出至少一个相对市场共识的增量判断、一个主导机制和一组改判信号。

若 Stage03 仍频繁触发工具上限，下一步不应继续提高一轮的上下文或工具次数，而应把 26 个证据要求拆成按判断单元/证据篮子的可恢复微任务，再由确定性程序汇总。这是后续可靠性优化，不应再用 fallback 05 掩盖。

## 七、2026-07-27 付费验证补充：03 的问题比“拆批”更深一层

本轮新建付费 run `f19c7d94-d6ea-4796-acbb-61d63c41257c`，没有重复创建完整研究任务。

- Stage01 已用 `deepseek-v4-flash` 生成并通过；
- Stage02 已用 `deepseek-v4-pro` 生成并通过，共形成 5 个判断单元、10 个证据要求和 17 个实际方法应用；这说明 ontology / method / workflow 的结构层落地已明显改善；
- Stage03 首次真实运行按 3 个判断单元批次执行，但 3 批全部失败，最终诚实保留 10 个 gap、0 个来源、0 条可用事实，没有批准。

Stage03 新暴露的失败不是“批次还不够小”，而是三个运行合同没有形成闭环：

1. 模型没有调用 search、fetch 或证据 MCP，却提交了类似事实的草稿；Runtime 过去只在抓取后降级，但在抓取前就先跑完整 schema，导致整批失败。
2. 模型提交的事实缺少 source binding、subject/scope/time 元数据，`semiconductor_measurement` 也缺 nullable 字段；这些近似稿没有被分为“可抓取候选”和“只能是 gap”。
3. MethodApplication 返回了合同外状态；Runtime 没有按证据可用性保守归并。

因此新增了四层工程约束：

- **取证调用门**：补证调用在至少完成一次 search/fetch/证据 MCP 前，不暴露最终 submit 工具；如果供应商仍绕过工具，Runtime 只接受 gap。
- **抓取前事实资格门**：非 gap 必须绑定一个字段完整的候选来源；否则在 schema precheck 前降为 gap，模型记忆不得进入事实层。
- **抓取后核验门**：只有正文抓取成功、quote_verified 且来源可用的绑定，才保留为事实；否则再次降为 gap。
- **补证也分批**：工作台“按缺口补证”不再把全量问题重新压成一次大调用，而是只选择覆盖不足的判断单元，按 1–2 个单元执行可恢复批次。

这次验证进一步确认：低价模型确实会放大工具不调用、字段越界和研究压缩，但决定工作台能否稳定产出研究价值的，是 Runtime 是否把“调用过工具”“拥有可核验来源”“形成可用事实”“完成方法执行”区分成四个独立状态。任何一个状态都不能由表格完整或合规字段替代。
