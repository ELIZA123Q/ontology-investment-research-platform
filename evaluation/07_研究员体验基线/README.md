# 07 · 研究员体验前瞻基线

本目录把 Goal 6 的“至少 8—12 个真实任务”变成可执行的前瞻队列。它与 `02_案例` 的研究价值评测互补：前者测研究员完成任务所付出的时间与操作，后者用 R/U/delta/S/C 检查研究质量和相对同证据基线的增益。

## 当前结论

- 两条已闭环真实链只能作为历史锚点，因为它们早于 `research-experience-metrics-v1` 的追加式事件台账。
- 主队列包含 10 个半导体任务，覆盖正常成功、冲突停止、证据不足停止、增量改判和来源失效。
- 当前 10 题均为 `planned`，所以这里只能声称“队列与测量协议就绪”，不能声称真实体验基线已经形成。
- 在至少 8 个主队列任务完成以前，不设置 TTFC、操作次数、返工率或一次完成率目标。

## 什么任务能进入主分母

一个任务必须同时满足：

1. 来自真实研究 backlog，而不是 UI、归档或合成测试；
2. 在创建时已经写入唯一 `run_created` 事件，不允许事后猜测或回填操作历史；
3. 问题、信息截止日和证据快照在运行前冻结；
4. 工作台方案与同证据直接生成使用相同证据、截止日、生产模型族和生成预算；
5. 质量盲评看不到方案标签，并受现有 R/U/delta/S/C 契约约束；
6. 任务完成、正确停止或被排除都有可审计原因。

历史任务可以帮助检查结论边界，但不得进入人工操作、返工和一次完成率的前瞻分母。

## 单题执行顺序

1. 在 `cohort.yaml` 冻结问题、截止日和场景标签。
2. 创建全新 run，将案例状态改为 `enrolled` 并登记 `run_id`。
3. 冻结证据快照；若两方案输入不能保持一致，将案例标为 `excluded`。
4. 运行工作台方案到 Stage05 或正确停止终点，保留所有体验事件。
5. 用同证据直接生成基线产生配对产物；质量评测器只看到盲化候选。
6. 记录 R/U/delta/S/C、首次可用结论时间、人工动作、返工、补证和成本。
7. 完成至少 8 题后先看分布和异常值，再冻结目标；不以 10 题均值包装为系统可靠率。

队列页自动汇总 TTFC、研究员操作、一次完成率、返工、补证、AI 时间和 Token，并把独立审阅与工作台同证据盲评作为护栏。默认展示中位数及最小—最大，不把进行中任务算作失败。质量失败案例保留在样本内，不允许通过排除失败项得到更好结果。

## 校验

只检查静态队列与分母规则：

```bash
python3 evaluation/03_执行/validate_experience_cohort.py
```

同时检查本机数据库中已经登记的 run：

```bash
python3 evaluation/03_执行/validate_experience_cohort.py \
  --db instances/00_本机运行/workbench.sqlite
```

当需要把“基线已形成”作为硬门时增加 `--require-ready`。在至少 8 个合格任务完成前，该命令必须失败；普通合同校验仍会通过并明确输出 `EXPERIENCE_BASELINE_NOT_READY`。

## 分析纪律

- 主结果只看 1—3 个决策指标：TTFC、研究员动作负担、一次完成率。
- 返工、补证命中率和重试用于解释主结果，不单独追求好看。
- R/U/delta 与硬错误是质量护栏；Token、金额和 AI 时间是成本护栏。
- 不用对象数、关系数、页面数或模型生成轮数替代研究员任务成功。
- 不用于个人绩效评价，也不跨领域外推；第二领域压力测试单独分层。
