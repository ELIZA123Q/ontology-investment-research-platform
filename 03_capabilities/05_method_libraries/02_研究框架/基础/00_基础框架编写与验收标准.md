# 基础框架编写与验收标准

## 核心原则：固定判断纪律，不固定现实答案

基础框架先服务研究判断，再服务系统登记。它应帮助研究员快速看清：真正的分歧是什么，哪些前提不能跳过，常见研究路线有哪些，什么信号能够区分，以及什么情况下必须停止继续外推。

基础框架不是现实事实库，不是单次任务的完整问题清单，也不是必须逐项填写的报告模板。它不能预先规定某个行业、公司或时期一定由哪个变量主导，也不能用固定权重、统一阈值或唯一决策树替代具体研究。

> 写死必须遵守的判断纪律，不写死现实必然命中哪条路径；  
> 写清必须区分什么，不规定所有任务都用同一个指标区分；  
> 写清禁止怎样跳步，不要求每次研究走完所有模块。

框架若只有变量清单、通用问题树和完整章节目录，不算有深度。合格框架应帮助单次 02 从完整知识中裁出一条最小、可验证、可反证的研究主线。

## 1. 文件定位与职责边界

基础框架回答：

> 一类投研问题通常有哪些稳定的判断难点、研究前提、可能路径、区分信号和停止条件？

基础框架负责：

1. 固定跨任务仍然成立的判断纪律；
2. 提供若干常见研究路线或诊断视角，而不是唯一标准流程；
3. 提供可供 02 选择的变量、信号、竞争解释、反证和输出对象；
4. 说明各级输出需要的研究前提和最低证据；
5. 记录框架适用边界、常见误判和真实任务验证状态。

基础框架不负责：

1. 判断当前现实处于什么状态；
2. 填写现实观测值或证据状态；
3. 在静态框架中确定单次任务的决定性变量及权重；
4. 预先裁决主解释、竞争解释或情景是否成立；
5. 把一次任务经验直接提升为通用规则；
6. 越过本框架判断权，直接形成公司、预期、估值或资产结论。

具体对象、业务时间、现实观测、证据充分性、路径裁决和最终结论，由 01—04 的任务流程处理。

## 2. 基础框架的三层结构

每个基础框架必须区分三层，不能混写为一张固定问题清单。

### 2.1 稳定框架内核

稳定内核保存跨任务仍然成立的研究纪律，通常只包括：

- 本框架拥有什么判断权；
- 必须区分的核心概念或机制；
- 不允许跳过的研究前提；
- 最重要的停止条件；
- 可以输出什么，不能直接推出什么。

稳定内核应简洁，通常用一段说明加 3—6 项规则即可。

可以固定的例子：

- 订单需求不能直接等同终端消耗；
- 名义产能不能直接等同有效供给；
- 报价不能直接等同成交价或公司实现价；
- 行业受益不能直接等同公司兑现；
- 没有事前预期基线不能判断预期差。

不应固定的例子：

- 所有行业都以库存为第一变量；
- 所有任务都使用同一指标和同一阈值；
- 某个变量在所有时期都拥有最高权重；
- 所有任务都按同一顺序走完全部模块。

### 2.2 可选研究路线或诊断视角

基础框架应提供 2—4 条常见研究路线或诊断视角，供 02 根据本次分歧选择。

每条路线至少说明：

| 要素 | 要求 |
|---|---|
| 核心分歧 | 这条路线主要区分什么 |
| 适用条件 | 出现什么问题或线索时启用 |
| 最少必答问题 | 为走通路线必须回答的 2—4 个问题 |
| 候选区分变量 | 哪些变量可能最有辨识力 |
| 竞争路线 | 哪条其他解释可能产生不同预测 |
| 退出或停止条件 | 何时不再沿该路线继续 |
| 输出边界 | 通过后允许进入什么，不能直接推出什么 |

只是换一种措辞、但不会改变证据要求、可观察预测或后续判断的内容，不应拆成独立路线。

### 2.3 单次任务动态实例化

单次任务的重点由 02 根据问题、对象、时间、用途和现实分歧动态确定。

02 调用框架时应：

1. 选择一个主要研究路线；
2. 最多保留一个主要竞争路线；
3. 确定 2—3 个决定总体判断的关键判断单元；
4. 从候选变量中选择本次真正有判别力的变量；
5. 明确本次不启用的模块及排除理由；
6. 将对象、业务时间、证据要求和停止条件写入任务本体视图。

因此，框架库提供的是“可选择的研究能力”，不是单次任务的默认展开目录。

## 3. 正式框架必须包含的语义

正式框架必须包含“研究员先看什么”、框架输出声明，以及以下语义。标题名称和章节数量可以不同，但语义不得缺失。

1. **适用边界与判断权**：适用于什么问题，能够形成什么输出，不能替代什么判断；
2. **稳定框架内核**：必须区分什么、禁止怎样跳步、什么情况下停止；
3. **常见研究路线或诊断视角**：不同分歧下可以怎样展开，不要求全部执行；
4. **核心、条件与扩展模块**：哪些通常需要，哪些满足条件才启动；
5. **候选变量、区分信号与关键时钟**：变量怎样参与判断，但不固定跨任务权重；
6. **竞争解释、反证与路径失效条件**：什么会削弱、替代或叫停原路径；
7. **可写到哪一层与职责交接**：输出如何对回登记表，较高层判断交给谁；
8. **真实任务验证与维护状态**：使用过什么任务，出现过什么失效或过度展开。

既有基础框架可以保留更细分节；新写或结构性重写时，优先采用紧凑结构。不得为了形式完整重复展开通用来源、本体字段和自检内容。

## 4. 稳定内核的编写要求

### 4.1 先写判断权，不先写变量全集

每个框架先回答：

- 本框架最终能够判断什么；
- 为形成该判断，至少要区分什么；
- 哪些问题不属于本框架。

例如，价格框架可以判断价格状态、驱动和实现价路径，但不能直接判断公司利润；公司业绩弹性框架可以判断产业变化能否兑现为收入、利润和现金，但不能替代长期商业模式判断。

### 4.2 固定概念区分，不固定指标权重

框架应固定长期稳定的概念区分，例如：

- 终端消耗与订单表象；
- 名义供给与有效供给；
- 报价与成交价；
- 行业受益与公司兑现；
- 利润增长与现金兑现；
- 政策目标与执行结果；
- 市场预期基线与研究员观点。

框架不得固定脱离情境的变量排序、统一权重和统一阈值。

### 4.3 明确禁止跳步

例如：

- 不能从政策发布直接推出公司受益；
- 不能从订单增长直接推出终端需求增长；
- 不能从行业涨价直接推出公司利润改善；
- 不能从盈利增长直接推出盈利质量提高；
- 不能从基本面改善直接推出形成预期差；
- 不能从预期差直接推出资产价格必然上涨。

禁止跳步属于硬约束，不因任务不同而取消。

### 4.4 停止条件必须可执行

停止条件必须说明：什么前提缺失或什么证据冲突，会禁止形成哪一级输出。

合格示例：

- 对象、规格、地域和业务时间无法对齐；
- 没有事件前可追溯的预期基线；
- 产业链关系只有概念邻近，没有真实关系证据；
- 历史财务基线不可信，无法支持精确预测；
- 关键路径被有效替代或缓冲完全吸收。

“证据不足”“存在不确定性”“持续观察”不是充分停止条件，除非同时说明缺少什么以及因此禁止什么输出。

## 5. 研究路线与模块设计

### 5.1 不使用唯一固定决策树

除非存在不可绕过的硬门，基础框架不得把所有任务写成一条唯一流程。

可以固定：

- 不可跳过的研究前提；
- 写到更高一层所需的最低前提；
- 关键概念区分；
- 路径失效后的停止要求。

不应固定：

- 所有任务都使用同一先后顺序；
- 所有对象都由同一变量主导；
- 所有行业使用同一阈值；
- 所有竞争解释按同一优先级处理。

### 5.2 路线围绕真实分歧组织

推荐写法：

```text
路线名称
→ 适用分歧
→ 最少必答问题
→ 区分变量与信号
→ 主要竞争路线
→ 退出或停止条件
→ 输出边界
```

不推荐把“需求、供给、库存、价格、公司、估值”等全部模块并列，作为每次任务都要执行的目录。

### 5.3 模块标记启动属性

框架中的分析模块分为三类：

| 模块类型 | 含义 | 使用要求 |
|---|---|---|
| 核心模块 | 使用该框架时通常不能缺少 | 只有明确说明不适用时才能裁掉 |
| 条件模块 | 满足特定条件时才启动 | 必须写明启动和退出条件 |
| 扩展模块 | 深度研究、比较研究或特殊用途才需要 | 默认不进入单次 02 主路径 |

“按需使用”不是合格启动条件。应写成：出现明显库存干扰时启动库存路线；行业改善与公司兑现不一致时启动兑现桥；出现资产定价问题时先启动预期差，再判断是否进入估值。

### 5.4 不同类型框架允许不同结构

| 类型 | 典型框架 | 编写重点 |
|---|---|---|
| 强前置型 | 预期差、估值、财务基线、精确预测 | 可以固定较强的前置要求 |
| 链路型 | 政策、产业链、宏观、业绩弹性 | 固定必要节点，开放具体路线、时滞和主导变量 |
| 开放诊断型 | 商业模式、竞争、治理、资本配置、风险 | 提供诊断视角和启动条件，不写统一决策树 |

## 6. 问题树、变量和信号

### 6.1 问题树区分不同层级

每个框架应区分：

1. **最小必答问题**：通常都要回答的 2—4 个问题；
2. **路线问题**：选择某条路线后才必须回答；
3. **条件启动问题**：出现特定信号、异常或输出要求时才回答；
4. **扩展问题**：仅用于深度研究或后续框架。

问题只有在满足以下至少一项时，才进入核心问题树：

- 决定是否继续下一步；
- 区分两条竞争解释；
- 改变判断方向或强度；
- 决定是否拆分对象；
- 决定是否允许升级输出；
- 触发停止、降级或转交其他框架。

只是提供背景、容易获得或与主题相关，但不会改变任何判断的问题，不进入核心问题树。

### 6.2 候选变量不是默认必选项

`state_variable_candidates` 表示常用观察维度，不表示每次任务都必须实例化和取证。

候选变量可以承担：

- 前提变量：失败后不能继续形成某级输出；
- 路线区分变量：区分不同解释或路径；
- 方向变量：在特定路线中改变总体方向；
- 强度变量：影响幅度、持续期或范围；
- 监测变量：暂不决定结论，但可触发更新。

同一变量在不同任务中可以承担不同作用。基础框架不得为候选变量设置跨任务通用权重。

### 6.3 变量和代理口径要求

候选变量应尽量满足：

- 可持续观察；
- 可跨时间比较；
- 有明确业务时间和适用范围；
- 能参与状态、方向或传导判断；
- 能与竞争解释形成不同预测。

一次性事实、某期数值、公司表态或单篇材料观点，不应登记为稳定变量，而应在具体任务中作为事件、观测或证据处理。

直接变量难以获得时，可以提供代理变量，但必须说明代理逻辑、失效条件，以及使用代理后如何降低结论强度。

### 6.4 信号必须对应判断动作

每个信号至少承担一种作用：

- 支持或削弱某条路线；
- 区分主解释与竞争解释；
- 触发路线切换；
- 触发停止或输出降级；
- 提示进入其他框架。

仅仅“值得关注”但不会改变判断动作的指标，不应列为核心信号。

## 7. 文首元信息、输出声明与职责交接

文首元信息固定保留：

```yaml
framework_id: <既有框架编号>
name: <框架名称>
library: base
version: <版本号>
```

既有框架编号不因改写而改变。结构性重写升级主版本号；仅修订表述、示例或来源时升级次版本号。

每份框架必须保留可供系统核对的输出声明：

```yaml
framework_layer: mechanism | company_realization | market_pricing
output_gate_refs: []
judgment_types: []
state_variable_candidates: []
signal_candidates: []
output_objects: []
evidence_requirements: []
falsification_conditions: []
scenarios: []
```

其中：

- 候选变量、信号和情景不代表单次任务全部使用；
- `falsification_conditions` 应能叫停或改写路径，而不是一般风险提示；
- 单次任务的待验证观点、决定性变量、具体分支和权重由 02 生成；
- `00_framework_dependency_registry.yaml` 是进入条件、可写到哪一层、质量要求、失败边界和下游可接续内容的登记表（维护依赖关系时以根目录 YAML 为准）；
- 正文只引用系统登记中的输出项并说明业务边界，不重复抄写静态依赖清单。

组合方式见框架库 README「怎样选用」；系统核对见文末登记说明。需要核对进入条件与可写到哪一层时，见根目录依赖说明。

以下职责边界为强制验收项：

1. 供需解释有效供需；价格解释价格状态、驱动和实现价；利润由公司业绩弹性承接；
2. 商业模式描述长期经济结构；公司业绩弹性描述短中期兑现；
3. 财务质量判断历史数字能否作为基线；经营预测推演未来；
4. 预期差判断新信息相对事前基线的差异；估值判断哪些价值输入发生变化；
5. 风险可以检查任一层的脆弱点，但不能代替该层主框架形成正常状态结论。

高层输出失败时，不应抹去已经成立的低层状态结论。

## 8. 证据、本体与来源边界

### 8.1 框架方法依据与现实证据分开

| 等级 | 使用条件 | 允许表述 |
|---|---|---|
| 单来源方法论候选 | 仅一个可追溯来源 | 只作研究线索 |
| 多来源方法论候选 | 至少两个独立机构或原始来源支持相近方法 | 可作为基础框架参考 |
| 历史支持模板候选 | 多来源方法论加历史样本、反例、窗口和失效边界 | 可申请沉淀为历史支持模板候选 |

基础框架默认按“多来源方法论候选”管理。权威来源不等于已经完成本项目的历史回放。

具体任务中：关键事实优先官方文件、公司公告、审计财报和原始数据；机制判断至少需要两个独立来源，或一个核心来源加一种不同类型的交叉验证；预测、公司指引和观点不得冒充现实观测。

来源优先级、证据组合和现实证据验收统一由 [`03_capabilities/05_method_libraries/03_取证`](../../03_取证/README.md) 管理。基础框架只说明其特有输出需要什么证据，不复制通用来源清单。

### 8.2 本体映射分三层

1. **一级正式本体**：引用一级通用本体已定义内容；
2. **领域扩展可选项**：只在领域本体已正式定义时引用；
3. **任务候选或本体缺口**：尚无正式定义但任务不可缺少，不得冒充正式本体。

候选变量、信号、路径和输出对象不会因写进框架正文自动成为正式本体定义。具体任务仍须查询正式本体，再决定复用、受限使用候选结构或登记缺口。

## 9. 实践反馈与框架演化

实践中新发现的变量、路径或经验，默认先进入场景卡、案例复盘、失败案例、经验说明或优化任务单。

只有同时满足以下条件，才考虑写回稳定框架内核：

1. 在多个独立任务中重复出现；
2. 能解释原框架无法稳定解释的问题；
3. 能形成不同的可观察预测；
4. 有反例或明确失效边界；
5. 不只是某个行业、公司、时期或口径的特殊现象；
6. 写入后不会迫使所有任务增加无必要的分析负担。

每个框架应记录：

- 已使用任务和覆盖的问题类型；
- 实际使用过的路线和模块；
- 长期未使用或经常被裁掉的内容；
- 出现过的误导、遗漏、过度展开和失效情形；
- 待补的外部研报、历史案例和反例。

框架更新不追求越来越长。更新应优先删除不改变判断的变量、将特殊经验下沉到场景卡、合并重复路线、补充停止条件和修正职责越界。

新增内容必须说明它改变了哪条路线、哪个区分信号、哪一级输出或哪个停止条件。仅仅“可能相关”的内容不写入主框架。
