# 00-投研判断框架概述

本文是 `references/` 下的领域框架概述，负责解释投研判断框架如何把研究对象、证据、变量、信号、反证、预期差和复盘沉淀成可复用资产。

本文不是项目总入口。项目总体定位、平台主线和根目录阅读路径见 `README.md`；平台如何接收问题、路由和编排见 `PLATFORM.md`；任务执行链路见 `PIPELINE.md`；目录和读写边界见 `PROJECT_ARCHITECTURE.md`。

后文出现的英文名称大多是系统内部字段或对象代号。概述只帮助建立图景；完整机器约束以 `schemas/` 下 YAML 和各域规范为准。

这套框架想解决一件事：把行业里反复可用的变量、传导逻辑、信号、反证和判断边界沉淀成正式行业 Bundle，让 AI 在具体场景中结合实时证据形成可验证、可降级的判断。

人的判断、研报、纪要和复盘是框架的生产输入，不是正式本体本身。只有稳定、可复用、可被验证并通过治理门禁的内容，才能进入正式行业 Bundle。

```text
用户请求进入系统
→ 形成按次研究任务与路由
→ 真实判断或材料进入对应任务
→ 形成候选证据、候选假设、候选判断
→ 持续追踪与复盘
→ 识别有效信号、失效模式、被忽视反证和可复用链路
→ 通过治理门禁沉淀进本体包
→ 下次判断时按需加载和复用
```

因此，本框架的核心定位是：**场景驱动的行业判断框架是主线，人的判断记录是本体生产与复盘机制。**

## 1. 先看一个最小例子

以研究员的一条随手判断为例：

```text
“我觉得这次磷化铟出口管制，可能会推高光模块上游材料价格，
但不一定马上反映到中际旭创的估值里。”
```

这句话不会直接变成正式结论，而是先被拆成一组候选资产：

| 拆出来的东西 | 示例 |
|---|---|
| 研究对象 | 磷化铟、光模块、光通信、上游材料、中际旭创 |
| 候选主张 | 出口管制可能影响材料供给 |
| 候选状态假设 | 材料价格可能上涨、交期可能拉长 |
| 候选判断 | 对光模块产业链有扰动，但短期不一定体现在标的估值中 |
| 待验证信号 | 价格上涨、交期拉长、公司回应、订单变化、库存缓冲 |
| 反证或阻断 | 替代材料、库存充足、审批放松、下游需求转弱 |
| 预期差问题 | 市场是否已经提前交易？价格是否已反映？ |
| 后续复盘 | 材料价格是否变动？相关标的是否反应？判断在哪个时间尺度上成立？ |

复盘之后，系统再决定哪些内容值得沉淀：

| 可沉淀内容 | 进入哪里 |
|---|---|
| 单次聊天判断原文 | 留在 `team workspace` 或证据记录中 |
| “磷化铟”作为材料对象 | 有来源且后续常用时，进入正式本体包 |
| “出口管制 → 材料供给 → 价格/交期”的链路 | 多次验证后，进入传导模板 |
| “库存缓冲 / 替代材料 / 审批放松” | 作为反证或阻断条件沉淀 |
| 从复盘提炼出的有效信号或失效模式 | 进入复用资产 |

接下来第 2 节先给阅读路径，第 3 至第 6 节解释这条判断如何进入系统、如何流转、由哪些职责层承接，以及最终怎样沉淀为本体包和复用资产。

## 3. 这套框架到底在管什么

它的核心叫做**行业判断框架**：明确哪些变量重要、事件如何传导、哪些信号支持逻辑、哪些反证使逻辑失效，以及证据不足时应如何降级。

一条做扎实的投研判断，事后应该能回答这些问题：

| 要回答的问题 | 框架里靠什么回答 |
|---|---|
| 讨论的是哪个对象 | 行业、产业链环节、公司、产品、原材料、资产标的等研究对象 |
| 证据从哪来、可不可信 | 来源文档、材料摄入记录、最小主张、归并后的事实 |
| 怎么从证据走到判断 | 状态变量、事件、状态假设、信号、推理规则、推理步骤 |
| 相对什么预期 | 市场预期、管理层预期、卖方预期、价格隐含预期，以及与判断之间的预期差 |
| 对资产有什么影响 | 判断输出、资产影响、投资命题 |
| 后来结果如何 | 复盘记录、实际结果、有效证据、被忽视的反证 |
| 下次哪些能复用 | 对象、状态变量、信号、反证、推理规则、传导模板、情景路径和复盘提炼结论 |

v1 先跑通一个可消费的明确场景，再提供低摩擦判断入口。判断入口负责把研究员的原话、假设、候选变量、所需数据和反证条件写入 `JudgmentRecord`，不负责直接修改本体。

这些内容先进入 `team_workspaces/<workspace_id>/`，仍然只是工作流记录。只有经过筛选后，才在 `bundle_workbenches/<bundle_id>/` 生成候选资产或 `PatchRequest`；满足聚合门槛也不得自动进入正式 bundle。

判断记录与复盘流的默认链路是：

```text
manual_input
→ JudgmentRecord(workspace workflow record)
→ record_only / retrospect_pool / ontology_candidate 筛选
→ bundle workbench candidate asset / PatchRequest
→ ReviewRecord / owner admission
→ InferenceRule / ConductionTemplate / ScenarioPath / formal industry bundle
```

关键约束只有一条：

> JudgmentRecord 不参与正式 runtime 默认加载；普通问题不自动创建长期记录。达到聚合门槛只允许生成候选资产或 PatchRequest，不得自动晋升正式资产。

第一条验收标准是：`fixtures/minimal_bundle` 跑通判断链校验；`fixtures/minimal_industry_bundle` 跑通行业包目录结构校验。前者覆盖语义锚点、证据、状态假设、信号、预期差、资产影响到复盘任务的最小链。

## 4. 一条判断如何流转

从一个研究念头到沉淀成可复用资产，可以先理解成五步：

| 步骤 | 做什么 | 主要产物 |
|---|---|---|
| 记录 | 低摩擦接收问题、材料、事件、异常数据或随手判断 | 候选对象、候选主张、候选判断 |
| 锚定 | 明确讨论对象和概念边界 | 行业、环节、公司、产品、材料、资产等语义锚点 |
| 验证 | 补齐来源、事实、变量观测、反证和竞争解释 | 来源、主张、事实、状态变量、信号 |
| 推理 | 把证据、状态、预期差和规则连成判断 | 判断输出、资产影响、投资命题、推理步骤 |
| 复盘沉淀 | 对照后验结果，提炼可复用内容 | 复盘记录、补丁、失效模式、规则修正、传导模板 |

更完整的生命周期在各域规范中展开。概述里只需要记住这条主线：

| 层 | 职责 |
|---|---|
| `team workspace` | 接住真实判断，不要求完整 |
| `research_memory` | 整理材料、矛盾和候选链路 |
| staging（候选层） | 承接结构化候选资产 |
| `governance` | 审核、复盘、补丁和审计 |
| `industry_bundle` | 发布经过校验的可复用资产 |

> 这三层分工是第 5 节「本体包与复用资产」的核心背景。

## 5. 五个职责层各管什么

整套框架分成五个职责层，各管研究链条的一段：

| 组成部分 | 负责什么 | 主要产出 |
|---|---|---|
| 语义结构域 | 定义“我们在研究什么”：对象、概念边界和业务关系，提供研究锚点。 | 概念体系、对象骨架、业务关系 |
| 证据域 | 把原始材料变成可追溯、可校验、可引用的证据。 | 来源、摄入记录、主张、事实、冲突记录 |
| 判断推理域 | 把证据和锚点变成判断：状态、假设、信号、预期差、资产影响、规则和情景。 | 判断、资产影响、投资命题、推理规则、传导模板、情景路径 |
| 治理域 | 管准入、审核、消费门禁、复盘、补丁、动作提案和审计。 | 复盘、补丁、运行轨迹、审计、消费门禁 |
| 工程交付与Bundle契约 | 管 bundle 目录、manifest、registry、scenario pack、校验脚本和发布加载规则。 | 本体包、目录契约、加载规则、校验结果 |

一句话概括协作关系：

```text
语义结构域定义语言
证据域提供事实
判断推理域生成判断
治理域保证演化
工程交付与Bundle契约保证发布和加载
```

## 6. 本体包与复用资产

三个写入面的最高层边界见根目录 `PROJECT_ARCHITECTURE.md`。本文只说明判断资产如何在三层之间流转。

本体包不是原始材料仓库，也不是所有历史判断和运行日志的全集。它只承接经过整理、校验、复盘或治理确认后，可被后续判断复用的正式资产。

```text
workspace 负责按次运行与判断记录
workbench 负责候选生产与整理
industry_bundle 负责正式发布与推理消费
```

v1 的正式沉淀单元是 `industry_bundle`（物理目录 `industry_bundles/<bundle_id>/`）。核心规范定义类型和公共结构，正式行业 Bundle 承载已审核实例，研究记忆负责整理候选；需要改公共结构时，通过治理流程提补丁。

## 7. 概述级设计原则

本框架吸收面向对象分析、独立规则建模和事件驱动架构的核心思想，但概述层只保留几条会影响理解的原则：

| 原则 | 一句话说明 |
|---|---|
| 判断先进入，资产后沉淀 | 真实判断可以低门槛进入系统，但只有经过验证和治理的内容才能进入正式本体包。 |
| 语义先行 | 任何要讨论的对象，都要尽量登记成可引用的研究锚点。 |
| 证据可追溯 | 每条事实、主张、判断都留下材料、位置、时间和可信度。 |
| 推理可回放 | 判断怎么来的，包括假设、信号、规则和步骤，事后能重走一遍。 |
| 预期显式化 | 谈资产影响必须说清楚：相对什么基准，差在哪，是否已被价格反映。 |
| 反证不能省略 | 正式判断必须记录削弱条件、阻断条件、竞争解释或后续验证任务。 |
| 治理可审计 | 创建、修改、审核、复盘、补丁都要留痕。 |
| 资产可复用 | 验证过的对象、变量、规则、模板、案例进入复用池。 |
| 按需加载 | 具体任务只加载必要契约和资产，不全文吞下所有定义。 |
| 输出边界统一 | 研究输出边界由 `schemas/common.yaml.global_research_output_boundary` 统一声明。 |

更细的对象建模、规则建模、事件驱动、保密标记、跨包引用、模拟归档和回放时点要求，分别放到 `01` 至 `06` 的专项规范中展开。

## 8. 三组关键区分

### 8.1 contract 和 policy

| 类型 | 含义 | 例子 |
|---|---|---|
| `contract` | 稳定接口和不变量 | ID、必填字段、manifest、输出边界、关系公共字段、兼容版本 |
| `policy` | 运行策略和裁决方式 | 证据新鲜度、候选晋升、阻断、缺证降级、review queue、production-ready 准入、LLM 编排边界 |

物理上它们可以放在同一个 YAML 里，逻辑上必须保持职责清楚。

### 8.2 研究 Event 与动作后续信号（ActionFollowup）

研究材料中的政策、订单、价格、技术、公司等外部事实，进入判断推理域 `Event`。Action 执行后的系统侧结果，不另建「运行事件」概念，统一记为治理域 `ActionFollowup`（动作后续信号）。

```text
外部研究事实 → Event → 状态理解 / 判断推理
Action 执行结果 → ActionFollowup → 监控 / 补证 / 审核 / 补丁 / 下游 Action
```

新的 `StateVariableObservation`、证据新鲜度变化、runtime data requirement 越界，优先发出 `ActionFollowup`，再触发监控、补证、重跑推理或审核。`ontology_feedback` 只用于对象、变量、关系、规则等结构缺口，不用于普通数据变新、变旧或缺当期数据。

**怎么区分研究 Event 与 ActionFollowup：**

| 问题 | 研究 `Event` | `ActionFollowup` |
|---|---|---|
| 描述的是外部世界还是系统行为？ | 外部已发生/材料声称发生的事实 | Action 或 trigger rule 执行后的系统事实 |
| 典型例子 | 出口管制、订单变化、价格异动 | `EvidenceClaimValidated`、`JudgmentOutputDrafted` |
| 谁消费 | 假设、信号、判断、传导推理 | 监控、补证、审核、下游 Action、AutomateFlow |
| 能否直接改正式资产 | 不能；经动作和门禁间接影响 | 不能；只能作触发线索，见治理域 permission 规则 |

**ActionFollowup 公共约定**（各域 `actions_*.yaml` 的 `side_effects(type=trigger_followup)` 共用，域文档只写差异字段）：

| 项 | 约定 |
|---|---|
| 必填载荷 | `triggeringActionAuditId`、`targetObjectIds`、`payloadSummary` |
| 禁止载荷 | 外部研究事件原文、`ontology_feedback` 结构缺口（除非事件类型明确允许） |
| 记录动作 | 治理域 `RecordActionFollowup` 落库；不替代 `ActionAudit` |
| 下游路由 | 受 `governance.trigger.followup_to_next_action` 约束 |
| 与 Automate | `Monitor` / 新鲜度变化可经 `AutomateFlow` 异步触发 `LogicFunction` 或 `ActionProposal` |

### 8.3 Rules、Policies 与 Action 执行契约

| 类型 | 回答什么 | 典型载体 | 平台对齐 |
|---|---|---|---|
| `contract` | 稳定接口和不变量 | `common.yaml`、manifest | ObjectType / LinkType schema |
| `policy` | 运行策略和裁决方式 | `policies_*.yaml` | 消费门禁、新鲜度、晋升策略 |
| `rules` | 可复用、可测试的声明式门槛 | 各域 `rules.yaml` | ActionType validation rules（**复用库**，非平行逻辑层） |
| `actions` | 受治理的写回事务入口 | `actions_*.yaml` | ActionType（参数 + 校验 + side effects） |
| `functions` | 可执行逻辑 | `LogicFunction` | Function / function-backed action |

**Rule Registry 定位（P4）：** 各域 `rules.yaml` 是 **Action 校验规则的复用库与索引**，不是与 Action、Policy、Function 平行的第四套逻辑。执行路径始终是 `Action → rule_refs / inference_consumer_rule_refs → 状态变更 → ActionFollowup`。

**Rule Registry 按 `rule_binding` 分型（P1）：**

| `rule_binding` | 绑谁 | Action 字段 |
|---|---|---|
| `action` | validation / blocking / promotion / permission / action_precondition | `rule_refs`（双向绑定） |
| `inference_asset` | InferenceRule / LogicFunction / InferenceRun | `inference_consumer_rule_refs`（双向绑定） |
| `automate_flow` | AutomateFlow + scenario policy | 不进 Action；见 `automate_binding` |

域 reference 中的 **Action 执行契约**按统一路径组织，而不是把 Rules 和 Events 拆成两张孤立清单：

```text
Action → rule_refs（action 型门禁）/ inference_consumer_rule_refs（推理资产索引）
      → 状态/对象变更 → ActionFollowup（side effect）→ 下游 Action / AutomateFlow
```

**文档门禁动作（P4，`action_rule_binding_gate.documented_gate_actions`）：** `AddSignal`、`UpgradeJudgmentToActive`、`ValidateEvidenceFact` 必须声明 `rule_refs` 与完整执行契约；`CreateJudgmentOutput` 必须声明 `inference_consumer_rule_refs`（消费 `confidence_composition` 评分规则）。

读规则时除 `condition` 外，还应看 **enforcement_contract**（谁保证）和 **failure_handling**（失败后怎么办）。推荐等级见 `references/06_能力暴露与运行消费规范.md` 第 7 节：`schema_enforced`、`policy_gate`、`skill_must_check`、`human_review_required`、`reference_only`。

**Function 边界（P2）：**

| 场景 | 载体 | 说明 |
|---|---|---|
| Action 简单门禁 | `rule_refs` | 声明式；双向绑定 `rule_binding=action` 规则 |
| Action 复杂校验 | `validation_checks[].function_ref` | `mode=function`；不进 `rule_refs` |
| Action 执行逻辑 | 顶层 `function_ref` | 仅白名单 function_backed Action |
| 推理资产 | `InferenceRule.functionRef` | `rules.yaml` 只做索引；`inference_binding.function_refs` / `canonical_inference_rule_ids` 指向 canonical 资产 |
| 场景编排 | `ScenarioModel.invoke_function` | 经 `loading_rules` 调用 LogicFunction |

```text
Action 校验：rule_refs（声明式） / validation_checks（复杂）
Action 执行：function_ref（白名单）
推理消费：InferenceRule.functionRef ← inference_binding 索引
场景编排：ScenarioModel → invoke_function
```

避免同一业务逻辑在 `rules.yaml.condition` 与 `InferenceRule` 各写一套实现；`execution=declarative_with_optional_function_ref` 的规则以资产化 InferenceRule 为 canonical 实现。

### 8.4 workspace、memory 和 bundle

| 层级 | 关键词 | 边界 |
|---|---|---|
| `team workspace` | 接住真实判断 | 不承诺完整、稳定、可复用 |
| `research_memory` | 整理材料、矛盾和候选链路 | 不替代正式来源、主张、事实、规则或补丁 |
| `industry_bundle` | 发布正式资产 | 只收稳定、可追溯、过门禁的内容 |

## 9. 公共契约与 schema 入口

五个职责层共用一份公共机器契约 `schemas/common.yaml`。各部分可以扩展自己的字段，但 ID、时间、枚举、治理层级、关系抽取、动作审计、输出边界和按需加载规则都沿用公共定义。

各业务域 reference 的主体结构默认跟随同域 schema 桶:先解释 `objects`,再解释 `relations`、`actions`,再解释 **Action 执行契约**（合并 `rules` 与 `trigger_followup` side effect）和 `policies`。工程交付域没有独立 objects/actions,因此以 engineering / validation policies 组织。研究 Event 与 ActionFollowup 分工见 §8.2–8.3。

日常阅读只需要知道公共契约覆盖五类内容：

| 公共契约类别 | 作用 | 关键位置 |
|---|---|---|
| 身份与版本 | 管 ID、namespace、版本、归属包、对象状态和兼容规则 | `identity_and_governance` |
| 证据与来源 | 管 source、claim、fact、可靠性、保密级别和来源追溯 | `classification_markings`、`as_of_reconstruction` |
| 关系与动作 | 管关系端点、关系公共字段、状态变更入口和动作审计 | `relation_defaults`、`audit_policy` |
| 输出边界 | 统一声明研究判断、投资决策和交易执行之间的边界 | `global_research_output_boundary` |
| 加载与校验 | 管按需加载、任务加载规则、最小样例和校验脚本 | `canonical_rule`、`task_loading_rules` |

正式机器约束都在 YAML 里，Markdown 只做解释。对应关系：

| 内容 | YAML 文件 |
|---|---|
| 公共定义 | `schemas/common.yaml` |
| 语义结构域 | `schemas/语义结构域/` 下的 objects / relations / actions |
| 证据域 | `schemas/证据域/` 下的 objects / relations / actions / policies |
| 判断推理域 | `schemas/判断推理域/` 下的 objects / relations / actions / policies |
| 治理域 | `schemas/治理域/` 下的 objects / relations / actions / policies |
| 工程交付与Bundle契约 | `schemas/工程交付与Bundle契约/` 下的 engineering / validation 机器契约 |

核心规范用 `scripts/validate_core.py` 校验；具体本体包实例用 `scripts/validate_bundle.py` 校验。`fixtures/minimal_bundle` 与 `fixtures/minimal_industry_bundle` 分别是判断链与行业包结构的第一验收样例。

## 10. 域间连接怎么理解

跨部分的写入、检索、推理、复盘，都应走固定的域间关系契约。概述层先记住几条高频关系：

| 连接方向 | 意义 |
|---|---|
| 语义结构域 → 判断推理域 | 状态、事件、判断、预期、资产影响都要挂到研究对象上。 |
| 证据域 → 语义结构域 / 判断推理域 | 用来源、主张和事实说明对象、关系、事件、状态、信号和判断凭什么成立。 |
| 判断推理域 → 治理域 | 推理运行记录用了哪些规则、消费了哪些信号、走了哪些步骤。 |
| 治理域 → 全部对象 | 来源追溯、动作审计、审核复盘可以覆盖所有对象。 |
| 工程交付与Bundle契约 → Bundle / 运行端 | 提供按需加载、发布校验和跨包解析入口。 |
| Action → ActionFollowup → 下游 Action | Action 完成后的后续信号驱动下游动作，但不得绕过审核直写正式资产。 |

> 代号索引已移至文末附录，需要时查阅。

## 11. 输入输出与边界

| 输入 | 进入哪 | 产出 | 谁接着用 |
|---|---|---|---|
| 自然语言研究问题 | 语义结构域 | 研究对象、概念范围、候选锚点 | 证据检索、推理入口 |
| 随手判断或聊天记录 | `team workspace` / 证据域 | 候选主张、候选假设、候选判断 | 追踪、复盘、候选沉淀 |
| 原始材料 | 证据域 | 来源、摄入记录、主张 | 事实归一、推理、补丁 |
| 结构化数据读数 | 证据域 / 判断推理域 | 事实、变量观测 | 状态假设、信号 |
| 推理运行结果 | 治理域 | 运行记录、规则应用、步骤 | 复盘、规则评测、补丁 |
| 后验结果 | 治理域 | 复盘记录、补丁、可复用发现 | 本体优化、复用沉淀 |

框架负责表达研究判断、证据链、预期差、资产影响和投资命题；交易指令、仓位、目标价、收益率预测和投资决策流程不由本框架直接生成。自动生成内容也只能先作为候选，正式入库必须经过门禁、审核和审计。

## 12. 最后一句话

这套框架不是静态投研知识库，而是一个**投研判断过程资产化系统**。

它允许判断先以低成本进入，再通过证据、推理、预期差、资产影响和复盘逐步升级，最后把被验证过的判断模式沉淀成本体包，供下一次研究按需加载和复用。
