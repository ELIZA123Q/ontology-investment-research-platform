# 04-治理域规范

治理域回答三件事：资产能不能进、当前任务能不能用、错了以后怎么改。工程交付不在本文展开；`05_工程交付与Bundle契约.md` 负责目录、manifest、registry、scenario pack、校验脚本和发布加载规则。

治理域负责准入、审核、补丁、动作提案、消费门禁、未决事项、复盘、审计和复用晋升。

**任何 AI Agent 不应直接改正式资产**；需要写回时，应先生成动作提案或补丁请求，再由策略、审核或 owner 执行。

外置 Runtime / 编译场景 Skill 默认读取本文的最小治理闭环、消费门禁和写回边界；只有在生成、校验或发布 bundle 时，才读取工程交付契约。

本文主体参考 `schemas/治理域/` 的文件结构组织:先看 `objects_governance*.yaml` 对应的对象,再看 `relations_governance.yaml`、`actions_governance.yaml`、`rules.yaml` 和 `policies_governance.yaml`,最后看队列、复盘、函数治理、复用资产和边界。ActionFollowup 契约见 `actions_governance.yaml#side_effects`。

## 1. 它产出什么

| 产出 | 说明 |
|---|---|
| 准入规则 | 对象、关系、证据、判断、规则和补丁进正式资产前有一致门禁。 |
| 审核记录 | 记录准入、补证、冲突裁决、状态升级、复盘和合规裁决。 |
| 补丁机制 | 管理结构变更、修正、合并、拆分、延后、回滚和迁移。 |
| 动作提案 | 承接人或 AI Agent 拟提交的业务事务,先提案、再审核、再执行。 |
| 消费门禁 | 决定当前 Skill 是否能使用某资产、以什么置信度使用、是否降级或阻断。 |
| 未决事项 | 管理未映射概念、悬空关系、缺证、冲突主张、过期信号和待审核任务。 |
| 运行轨迹 | 记录推理怎么跑的,支撑回放、评测、复盘和问题归因。 |
| 复用晋升 | 验证过的对象、规则、模板、案例和复盘发现进入复用池。 |

## 2. 最小治理闭环

治理域的最小闭环不是让所有对象一次性进入正式本体包,而是保证每一次写入、升级、复盘和发布前置判断都有可追溯路径。

宏观判断流见 `00_框架概述`;本文只聚焦治理专有链路,也就是候选资产如何过门禁、如何写入、错了如何形成补丁。

最小链路为:

**候选对象、候选关系、候选证据、候选判断或候选规则 → 准入检查 → 审核 / 补证 / 拒绝 / 隔离 → 正式写入或进入 staging → 生成 ActionAudit → 到期复盘或运行复盘 → 形成 ReviewRecord → 必要时生成 PatchRequest → 补丁处理结果进入 PatchLedgerItem → 复用资产或版本发布。**

其中,`ActionProposal` 是写回前的提案,`ActionAudit` 是写回后的审计,`ReviewRecord` 是审核或复盘结论,`PatchRequest` 是结构性变更请求,`PatchLedgerItem` 是补丁处理账本。任何 AI Agent 不应直接改正式资产;需要写回时,应先生成动作提案或补丁请求,再由策略、审核或 owner 执行。

---

## 3. 基本原则

- 写入有审计:任何创建、修改、废弃、审核、复盘都留痕。
- 变更有补丁:对正式资产的结构性改动走补丁管理。
- 复盘有对象:判断、资产影响、投资命题、运行结果都通过复盘记录形成后验。
- 复盘先修方法:团队判断记录复盘默认修正研究方法，不默认修改本体；达到聚合门槛或由行业 owner 标记为结构性缺口后，也只能进入候选生产和补丁流程。
- 提案有入口:人和 AI Agent 的状态变更先形成动作提案,再按策略审核或执行。
- 函数有契约:AI 能力必须声明输入、输出、权限、逻辑块、评测和可写回边界。
- 运行有轨迹:推理运行记录用了哪些规则、走了哪些步骤、消费了哪些信号、基于哪个 bundle 版本。
- 候选不污染正式资产:bundle workbench 与 team workspace 的内容默认不是正式推理资产。
- 消费先过门禁:状态、权限、时点、版本、场景、证据新鲜度、判断状态和规则状态都要检查。
- 复用要有复盘支撑:从单次判断提炼的规则、模板或情景路径,必须有复盘记录或审核记录支撑。

## 4. Objects：对象一览

完整字段以 `schemas/治理域/objects_governance.yaml` 为准;所有对象都继承公共字段(id、治理层级、记录状态、有效期等)。

| 对象代号 | 中文名 | 用途 |
|---|---|---|
| PatchRequest | 本体补丁请求 | 表达候选的结构变更、补证、修订、废弃、合并、拆分或迁移需求。 |
| PatchLedgerItem | 补丁账本项 | 记录补丁的合并、拒绝、延后、失败或回滚结果。 |
| ActionProposal | 动作提案 | 表达人或 AI Agent 拟提交的可审核业务事务,引用既有 Action 和输入载荷。 |
| LogicFunction | AI 逻辑函数 | 可发布、可评测、可监控的函数化 AI 能力。 |
| LogicBlock | 逻辑函数块 | LogicFunction 内部的离散执行步骤,用于读取、检索、转换、校验、提案或渲染。 |
| AutomateFlow | 自动化流 | 声明 Monitor、计划或外部事件触发后调用哪个 Function 并生成什么 ActionProposal。 |
| ObjectViewSpec | 对象视图规格 | 围绕某类业务对象组织信息、指标、证据、历史和可执行动作。 |
| EvalCase | 评测用例 | 单个输入、期望结果和评分规则。 |
| EvalSuite | 评测集 | 多个评测用例的版本化集合。 |
| EvalRun | 评测运行 | 一次评测集运行记录。 |
| EvalResult | 评测结果 | 单个用例在某次运行中的得分、通过状态和摘要。 |
| MetricSnapshot | 指标快照 | 记录函数、Action、评测或推理运行的成功率、耗时、通过率等指标。 |
| InferenceRun | 推理运行记录 | 记录一次推理的问题、版本、证据、时点基准、运行状态和反馈。 |
| RuleApplication | 规则应用记录 | 记录一条规则在某次运行里的触发、消费信号、检查和结论。 |
| ReasoningStep | 推理步骤 | 记录一次图谱跳转、对象匹配、证据消费或中间决策。 |
| ActionFollowup | 动作后续信号 | 记录 Action 执行后的系统事实、相关对象、载荷摘要和下游处理方式。 |
| ActionAudit | 动作记录 | 记录对象创建、字段更新、状态变更、关系写入、审核或复盘动作。 |
| ReviewRecord | 审核/复盘记录 | ReviewRecord（判断复盘记录）统一承载准入审核、证据审核、冲突裁决、状态确认、判断复盘、补丁审核和合规裁决。 |

### 4.1 容易混淆的治理对象

以下几组概念经常被混用,读写时先看它们分别回答什么问题:

| 对象 | 解决什么 | 例子 |
|---|---|---|
| `ActionProposal` | 一次具体动作是否可以执行,强调"能不能执行"。 | 创建一个对象、激活一个信号、升级一个判断 |
| `PatchRequest` | 正式资产结构是否需要变更,强调"本体或 bundle 是否需要改"。 | 合并两个公司对象、修正规则、补一个状态变量 |
| `PatchLedgerItem` | 补丁最终怎么处理。 | 接受、拒绝、延后、合并、回滚 |

`ActionProposal` 面向一次可执行动作,`PatchRequest` 面向结构性资产变更。两者可以关联,但不能互相替代。动作提案执行后必须有 `ActionAudit`;补丁处理结果必须进入 `PatchLedgerItem`。

### 4.2 ActionAudit 与 ActionFollowup

`ActionAudit` 和 `ActionFollowup` 解决的问题不同:

| 对象 | 回答的问题 | 能不能触发下游 |
|---|---|---|
| `ActionAudit` | 哪个 Action 被谁在什么时候以什么输入执行了,结果是什么。 | 作为审计依据,不直接表达编排意图。 |
| `ActionFollowup` | Action 执行后发生了什么运行事实,是否需要下游 Action、审核、补丁或复盘。 | 可以触发 `AutomateFlow`、`ActionProposal`、`ReviewRecord` 或 `PatchRequest` 候选。 |

`ActionFollowup` 是动作后续信号,不是判断推理域 `Event`。外部政策、订单、价格、技术或公司事件仍用 `Event`;动作完成、动作失败、证据主张已创建、判断草稿已生成、人工审核被请求等系统事实才用 `ActionFollowup`。数据变新、变旧或 requirement 越界也发出 ActionFollowup,例如 `DataStaleDetected` 和 `DataRequirementBreached`。机器契约见 `schemas/治理域/actions_governance.yaml` 的 `trigger_followup` side effect 和 `schemas/工程交付与Bundle契约/policies_validation.yaml.action_followup_side_effect_gate`。

### 4.3 ReviewRecord 的语义分层

`ReviewRecord` 是统一记录对象,但不能把审核、复盘和合规裁决混成一种语义。消费端应优先读取 `reviewType`:

| reviewType | 用途 |
|---|---|
| `admission_review` | 准入审核 |
| `evidence_review` | 证据审核 |
| `conflict_review` | 冲突裁决 |
| `status_review` | 状态升级/降级确认 |
| `retrospect` | 判断或资产影响复盘 |
| `patch_review` | 补丁审核 |
| `compliance_review` | 权限、信息墙、标记裁决 |

## 7. Action 执行契约（Rules + Events）

治理域是全域 ActionFollowup 的**编排枢纽**：各域 Action 可声明 `trigger_followup`，但路由、落库和后续动作受本域规则约束。`ActionAudit` 记录「做了什么」；`ActionFollowup` 记录「做完后触发了什么、可路由到哪里」。公共约定见 `00_框架概述` §8.2–8.3。

### 7.1 编排主链

```text
CreateActionProposal → ActionProposalCreated → SubmitActionProposalForReview
  → HumanReviewRequested → ApproveReview → ReviewRecordCompleted
    → CreatePatchRequest / AppendPatchLedgerItem

Monitor 命中 → AutomateFlow → LogicFunction → CreateActionProposal（复盘/补证）
```

所有跨域 ActionFollowup 的 `allowed_next_actions` 须经 `governance.trigger.followup_to_next_action` 校验；不得直写 `shared/` 正式资产（`governance.permission.no_direct_write_from_followup`）。

### 7.2 按动作族看门禁与事件

| 动作族 | 代表动作 | 必经规则 | 发出事件 | 典型下游 |
|---|---|---|---|---|
| 动作提案 | `CreateActionProposal`、`ExecuteApprovedActionProposal` | `proposal_registered_action`、`ai_direct_write_to_shared` | `ActionProposalCreated` | 提交审核 |
| 审核 | `SubmitActionProposalForReview` | `action_followup_to_followup_action` | `HumanReviewRequested` | 批准/拒绝/补证 |
| 复盘结案 | `RecordReviewOutcome` | `review_to_patch_request_gate` | `ReviewRecordCompleted` | 补丁候选或 `bias_log` |
| 运行记录 | `CreateInferenceRun`、`RecordActionFollowup` | 新鲜度/权限规则 | `BundleGapDetected`、`DataStaleDetected` 等 | 补证、监控 |

### 7.3 规则卡片

#### `governance.action_precondition.proposal_registered_action`
- **回答问题**：提案引用的动作是否已注册？
- **检查时机**：创建或执行 `ActionProposal`
- **执行者**：`schema_enforced`
- **通过**：`proposal_admitted` → **失败**：`block_next_action`

#### `governance.trigger.followup_to_next_action`
- **回答问题**：ActionFollowup 能否触发这条后续动作？
- **检查时机**：`RecordActionFollowup` 之后、任何 follow-up 之前
- **执行者**：`schema_enforced`
- **通过**：`trigger_next_action` → **失败**：`block_next_action`
- **说明**：全域 Events 表的「允许下游」列都受本条约束

#### `governance.permission.no_direct_write_from_followup`
- **回答问题**：能否借 ActionFollowup 直写正式资产？
- **检查时机**：执行写回前
- **执行者**：`schema_enforced`
- **通过**：仅作触发线索 → **失败**：`enqueue_review`

#### `governance.promotion.review_to_patch_request_gate`
- **回答问题**：复盘缺口要不要晋升补丁？
- **检查时机**：`RecordReviewOutcome`
- **执行者**：`policy_gate` + `human_review_required`
- **通过**：`candidate_patch_request`（结构性/重复缺口）→ **失败**：`bias_log_item`（单次方法修正）

#### `governance.blocking.ai_direct_write_to_shared`
- **回答问题**：AI 能否绕过提案写 `shared/`？
- **检查时机**：任何 AI 发起写回
- **执行者**：`schema_enforced`
- **通过**：有已批准提案或补丁账本 → **失败**：`block_next_action`

### 7.4 ActionFollowup：权威定义与跨域事件

| 事件 | 触发源 | 推荐载荷（除公共字段外） | 下游 |
|---|---|---|---|
| `ActionProposalCreated` | Action | — | `SubmitActionProposalForReview` |
| `HumanReviewRequested` | Action | — | 审核队列 |
| `ReviewRecordCompleted` | Action | — | 补丁账本 |
| `BundleGapDetected` | Action | 结构缺口摘要 | `CreatePatchRequest` |
| `DataStaleDetected` | Action 或 Rule（判断推理域新鲜度规则） | `scenarioId`、`runtimeDataRequirementKey`、`staleReason` | 补证、`EvaluateMonitor` |
| `DataRequirementBreached` | 同上 | `requiredForFormalJudgment`、`onMissingBehavior` | 审核、补证提案 |
| `ActionFailed` | `RecordActionFollowup` | `failureReason` | 阻断后续 |

`DataStaleDetected` / `DataRequirementBreached` 在判断推理域 `actions_reasoning.yaml` 有推理侧发出定义；**治理域登记为路由与补证编排的权威消费点**。与 `ontology_feedback` 分工：前者是数据过期/缺失，后者是结构缺口。

## 9. Policies：准入、消费与质量门禁

机器策略见 `schemas/治理域/policies_governance.yaml`。资产进正式库前要过对应检查:

| 检查 | 通过条件 | 处理方式 |
|---|---|---|
| 对象准入 | ID 稳定、类型合法、名称清楚、状态合法、来源可追溯、归属明确。 | 进准入审核或补证。 |
| 关系准入 | 端点存在、方向合法、类型匹配、来源可追溯。 | 进悬空关系或补丁。 |
| 判断准入 | 判断有锚点、基础假设、证据、竞争解释和状态审计。 | 进状态升级审核或补证。 |
| 证据准入 | 主张/事实的来源、定位、状态、可靠性和冲突完整。 | 进证据/冲突审核或隔离。 |
| 补丁准入 | 补丁来源、目标、影响范围、状态清楚且有审计。 | 进补丁审核。 |
| 动作提案 | 提案引用已定义 Action,风险、审核要求、写回模式和输入载荷完整。 | 高风险进审核;非法直写阻断。 |
| 函数化能力 | 函数输入输出、逻辑块、权限、写回边界和审核策略完整。 | 阻断发布或要求补评测。 |
| 推理运行 | 运行记录了 bundle 版本、规则应用、步骤、证据和失败原因。 | 标记阻断/失败,进反馈闭环。 |
| 复盘入库 | 复盘记录了结果、时间尺度、预期差、有效证据、遗漏反证和修正建议。 | 进复盘审核或补丁。 |
| 合规标记 | 派生对象继承最严格标记。 | 进信息墙审核或阻断。 |
| 时点回放 | 回放/回测/复盘声明时点,只用当时已知信息。 | 标记无效回放或阻断。 |

资产被消费端任务能力消费前,应执行消费门禁。与上面的准入检查不同,消费门禁不决定资产是否进入正式库,而决定当前任务是否可以使用该资产、以什么置信度使用、是否需要降级或阻断。

| 检查 | 通过条件 | 未通过处理 |
|---|---|---|
| 状态可用 | 资产处于 active、approved、published 或允许被当前任务读取的状态。 | 降级为参考线索,或阻断正式输出。 |
| 权限可用 | 当前用户、任务和输出场景满足来源标记与信息墙要求。 | 隐藏、脱敏、阻断或进入权限审核。 |
| 时点可用 | 回放、复盘或历史验证只使用当时可见信息。 | 标记无效回放或重新按 as-of 加载。 |
| 版本可用 | bundle、schema、规则和引用版本兼容。 | 进入版本兼容处理或阻断。 |
| 场景匹配 | 资产适用于当前行业、主题、对象或场景。 | 降低权重或不加载。 |
| 证据新鲜度 | 证据的业务时间、有效期和采集时间满足任务要求。 | 降置信度、要求补证或阻断升级。 |
| 判断状态 | 判断状态满足当前输出层级要求。 | candidate 只能参考,不能生成正式资产影响。 |
| 规则状态 | 规则、模板或情景路径已审核或允许试运行。 | 待审核规则只能用于候选分析。 |

复盘什么时候触发,遵循 `retrospect_trigger_policy`:

| 触发对象 | 触发条件 | 输出 |
|---|---|---|
| 判断输出 | 预期验证日到期,或对应时间窗结束。 | ReviewRecord |
| 资产影响 | 影响窗口结束,或价格/基本面结果已可观测。 | ReviewRecord,含预期差和定价复核 |
| 投资命题 | 到定期复盘周期,或核心判断已结算。 | ReviewRecord,含规则修正建议 |
| 推理运行 | 运行部分/阻断/失败且缺口超过治理时限。 | ReviewRecord、PatchRequest 候选 |

## 11. 判断复盘与本体优化的边界

判断记录与复盘流的低摩擦入口在 `team_workspaces/<workspace_id>/judgments/`。`JudgmentRecord` 是工作流记录，不是本体对象，也不作为正式推理资产。普通推理禁止默认读取 team workspace；只有用户明确要求验证或继续跟踪某条记录时，才能读取指定记录作为待验证 thesis，且不能把它当作已审核事实、正式规则或正式判断。

本体优化是低频治理动作。`ReviewRecord.feedbackScope=personal_method_revision` 时，复盘沉淀到团队工作区的 bias log，`followupPatchRequestIds` 保持为空。只有当 `feedbackScope=ontology_gap` 且声明 `aggregationKey`，并达到默认门槛或由行业 owner 明确认定 `structuralGap=true` 时，才允许在 bundle workbench 生成候选资产或 `PatchRequest`；不得自动写入正式 bundle。

| 复盘类型 | 粒度 | 主要问题 | 默认去向 |
|---|---|---|---|
| 团队判断记录复盘 | per-record | 我这次判断、节奏、催化剂、预期差和定价判断对不对。 | `team_workspaces/<workspace_id>/bias/log.yaml`、`ReviewRecord.methodRevisionSuggestion` |
| 本体历史回放校验 | per-ontology / per-rule | 这套传导、规则或情景路径在历史上是否成立。 | `EvalResult`、候选 PatchRequest |

二者在聚合门禁通过时相交：多个独立判断或历史案例暴露同一个结构性缺口后，进入候选生产与本体优化任务池。

## 12. 函数化能力与生产化治理

LogicFunction 是本规范对齐 Function 的发布单元,LogicBlock 是它的步骤单元;字段以 `schemas/治理域/objects_governance.yaml` 为准。函数可以读取对象、证据、规则和场景引用,但需要写回时只能生成 ActionProposal 或执行已批准提案。完整 Logic 分层和 `ScenarioModel` / `InferenceRule` 的职责边界以 `references/06_能力暴露与运行消费规范.md` 为准。

AutomateFlow 是 Monitor、计划或外部事件到 Function 的版本化连接。团队判断记录复盘的标准链路是 `Monitor(triggerAction=enqueue_retrospect)` 命中后,由 AutomateFlow 调用 LogicFunction 生成复盘 ActionProposal 或 ReviewRecord 候选;图谱上必须能通过 `automateTriggeredBy` 和 `automateInvokesFunction` 找到触发源和目标函数。

ObjectViewSpec 是对象中心应用入口。它围绕 Company、Segment、Product、Asset、StateVariable、ScenarioPath 等对象展示核心状态、关联对象、证据、信号、历史运行和可执行 Action,避免每个应用各自维护一套对象含义和动作逻辑。

EvalCase、EvalSuite、EvalRun、EvalResult 和 MetricSnapshot 共同支撑生产化评测与监控:函数发布前要有评测集,运行后要有通过率、失败率、耗时、阻断率和审核通过率等指标。

函数化能力、自动化流和评测指标属于生产化治理能力,不是最小判断流闭环的必需对象。MVP 阶段可以只保留对象定义和发布约束,实际使用时优先围绕 `ActionProposal`、`ReviewRecord`、`InferenceRun` 和 `PatchRequest` 跑通闭环。

## 13. 复用资产分类与字段映射

复用资产是四部分共同沉淀的结果,bundle 是它们的组合发布单元:

| 复用资产类型 | 来自 | 对应内容 | 怎么复用 |
|---|---|---|---|
| 语义锚点资产 | 语义结构域 | 概念体系、概念、边界、行业、环节、公司、产品、材料、资产 | 作为研究入口和对象映射基础 |
| 证据资产 | 证据域 | 来源、摄入、主张、事实候选、引用定位、可靠性 | 支持事实复核和材料再利用 |
| 判断资产 | 判断推理域 | 假设、信号、判断、预期、资产影响、投资命题 | 支持复盘和预期差比较 |
| 派生指标资产 | 判断推理域 | 派生指标、算法引用、刷新策略 | 支持估值、同比、分位、暴露计算 |
| 规则模板资产 | 判断推理域 | 推理规则、状态传导、传导模板、情景路径 | 支持同类问题的推理复用 |
| 模拟资产 | 判断推理域 | 情景模拟、假设性输入、模拟影响 | 支持 what-if 和情景对比 |
| 运行轨迹资产 | 治理域 | 推理运行、规则应用、推理步骤 | 支持规则评测和链路复现 |
| 复盘治理资产 | 治理域 | 复盘记录、补丁请求、补丁账本、动作记录 | 支持后验校验和治理审计 |

复用资产要声明一份元数据 `reuse_metadata`:资产类型、来源域、来源对象、适用范围、校验状态、支撑的复盘记录、版本和维护角色。

## 15. 全局合规边界

治理域不生成投资交易动作,不输出买卖建议、目标价、收益率预测或仓位建议。它只记录研究判断、资产影响候选、复盘结论和动作提案的边界。

证据、对象、关系、判断、规则和补丁的正式写回都必须经过对应准入与审核。受限来源参与生成主张、事实候选、观测、信号、判断或资产影响时,派生对象必须保留来源链路和权限标记;摘要、改写或归并不得消除原始限制。

回放、回测、复盘必须声明 as-of 时点,并按当时可见信息评价判断。缺少权限、时点、版本或预期基准时,运行端应降级、阻断或进入人工审核,不能用不完整上下文生成高置信结论。

## 16. 治理域不负责什么

治理域不负责具体目录结构，不负责 runtime package 生成，不负责平台路由，不负责 CLI 执行，不负责用户对话入口。这些分别由 `PROJECT_ARCHITECTURE.md`、`05_工程交付与Bundle契约.md`、`PLATFORM.md` 和 `PIPELINE.md` 承担。
