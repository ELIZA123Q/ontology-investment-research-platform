# 01-语义结构域规范

本文是语义结构域的人类说明，负责解释稳定研究对象、术语口径、概念边界和长期语义关系。机器约束以 `schemas/语义结构域/` 下 YAML 为准。

语义结构域负责一件事：把"我们到底在研究什么"说清楚。它定义研究范围、术语口径、概念边界,以及行业、环节、公司、产品、材料、资产这些研究对象和它们之间的关系。

正文用通俗语言叙述,英文名是系统内部对象/关系/动作的代号,集中放在对照表里,平时阅读可以跳过。

本文主体参考 `schemas/语义结构域/` 的文件结构组织:先看 `objects_ontology.yaml` 对应的对象,再看 `relations_ontology.yaml`、`actions_ontology.yaml`、`rules.yaml`,最后看输入输出、质量门禁和边界。`events.yaml` 已 deprecated，ActionFollowup 契约见 `actions_ontology.yaml` 的 `side_effects`。

---

## 1. 它产出什么

| 产出 | 说明 |
|---|---|
| 术语口径 | 把研究范围和"算不算在内"的边界定下来。 |
| 研究对象 | 行业、产业链环节、公司、产品、材料、资产标的等现实世界锚点。 |
| 业务关系 | 产业、环节、公司、产品、材料、资产之间的显式连接。 |
| 推理锚点 | 判断推理域的事件、状态、判断、资产影响都挂到这些对象上。 |
| 治理入口 | 概念冲突、边界争议、对象废弃和关系修订进入治理流程。 |

本域只保存相对稳定的语义锚点，不保存运行时事实和判断结论。价格、产能、库存、交期、盈利预测、政策强度、市场预期、投资判断等动态内容，不进入语义结构域，而应进入证据域、判断推理域、治理域或工程交付与 Bundle 契约。语义结构域的价值在于让这些动态内容有稳定的挂载对象。

## 与其他域的边界

| 内容 | 放哪里 |
|---|---|
| 行业、环节、公司、产品、材料、资产 | 语义结构域 |
| 材料来源、原文主张、事实候选 | 证据域 |
| 价格、库存、交期、需求、供给等变量 | 判断推理域 |
| 判断、预期差、资产影响 | 判断推理域 |
| 创建、合并、废弃、审核、补丁 | 治理域 |
| Bundle 目录、scenario pack、runtime contracts | 工程交付与 Bundle 契约 |

## 2. 基本原则

核心约束:

- 先定边界再建对象:研究范围和"纳入/排除"规则先用概念和边界裁定表达清楚。
- 概念不自动变对象:名词、主题和术语先进入 Concept 或边界裁定,只有需要被稳定引用时才映射为正式对象。
- 对象承载现实:每个业务对象都应该是能被证据、事件、变量、判断引用的真实对象。
- 关系要显式:归属、参与、生产、上下游、替代、竞争、暴露等连接,以明确端点和方向为准。
- 来源可追溯:关键概念、边界、对象、关系都要有来源或治理说明。

设计指南:

- 稳定关系留在本域:归属、参与、生产、使用、映射、暴露等相对长期成立的连接可以入库;增强、削弱、变化、传导、预期差、催化、阻断等推理性内容优先交给判断推理域。
- 关系细节可扩展:核心只定义端点、方向和公共字段,行业特有的强度、技术依赖等留给业务包扩展;运行时产能、库存、交期、价格等观测不写入本域关系。
- 生命周期可治理:创建、更新、废弃、合并、拆分、边界裁定和候选晋升都留痕,接受审核或补丁管理。

## 3. Objects：对象一览

完整字段以 `schemas/语义结构域/objects_ontology.yaml` 为准;所有对象都继承公共字段(id、治理层级、记录状态、有效期等)。

| 对象代号 | 中文名 | 用途 | 常见连接提示 |
|---|---|---|---|
| ConceptScheme | 概念体系 | 管一个行业/主题的术语口径集合。 | 用 `conceptInScheme` 承接下属概念,并保留来源。 |
| Concept | 概念 | 定义某个术语、技术、环节在本体里的口径。 | 归属概念体系;需要稳定引用时用 `conceptMapsToObject` 映射对象。 |
| ConceptBoundary | 概念边界裁定 | 记录"纳入/排除/相邻/交叉/延后"的边界判断。 | 用 `boundaryForConcept` 指向被裁定概念。 |
| Industry | 产业 | 宏观产业分类锚点。 | 可用 `subIndustryOf` 形成产业层级。 |
| Segment | 产业链环节 | 产业链中可独立分析的位置。 | 通常用 `segmentBelongsToIndustry` 归属产业。 |
| Company | 公司 | 核心研究主体。 | 常用 `companyBelongsToIndustry`、`companyParticipatesInSegment`。 |
| Product | 产品 | 公司的产品或产品线。 | 常用 `productProducedBy`、`productBelongsToSegment`。 |
| Material | 材料 | 关键原材料、零部件、投入品。 | 常用 `materialBelongsToIndustry`、`materialUsedInSegment`。 |
| Asset | 资产标的 | 判断最终作用的股票、债券、期货等。 | 常用 `companyLinkedToAsset` 或 `assetLinkedToIndustry`。 |
| ObjectSet | 对象集合 | 可复用、可命名的对象集合,如公司池、资产篮子、主题暴露集合。 | 枚举型用 `setContainsMember`;规则型声明筛选规则。 |

`ObjectSet` 不替代正式对象,只是为批量推理、监控订阅、场景加载提供一个入口。枚举型集合要显式列出成员(`setContainsMember`),规则型集合要声明筛选规则。

概念不等于正式对象。`Concept` 用于管理术语、别名、口径和边界;只有当某个概念需要被证据、事件、状态变量、判断或资产影响稳定引用时,才映射为正式对象。无法判断是否应映射时,进入未解析项或边界审核,不直接创建正式对象。

举例来说,"先进封装"可以先是 `Concept`,当它在某个行业包中需要承载公司参与、产品归属、证据挂载和判断锚定时,才映射为 `Segment`。"磷化铟"如果后续会承载供给、价格、出口管制、国产替代等判断,应映射为 `Material`。"AI 算力景气"更像主题或口径,通常保留为 `Concept` 或 `ObjectSet`,不自动创建为 `Industry` / `Segment`。

## 4. Relations：关系一览

完整定义以 `schemas/语义结构域/relations_ontology.yaml` 为准。关系都是有方向的,从起点指向终点。

关系分为稳定语义关系和推理性关系。稳定语义关系描述相对长期成立的归属、参与、生产、使用、映射、暴露等连接;涉及增强、削弱、变化、传导、预期差、催化、阻断的关系,原则上进入判断推理域。若业务包需要保留结构性倾向关系,必须声明适用条件、证据来源、有效期和置信度,且不得把它当作一次具体判断。

概念之间的关系管术语体系内部的包含、排除、重叠和映射;业务对象之间的关系管真实世界里的归属、生产、使用、暴露和连接。

概念之间:

| 关系代号 | 起点 → 终点 | 含义 |
|---|---|---|
| conceptInScheme | 概念 → 概念体系 | 概念属于某个体系。 |
| conceptBroaderThan | 概念 → 概念 | 前者是后者的上位概念。 |
| conceptNarrowerThan | 概念 → 概念 | 前者是后者的下位概念;正式维护以 `conceptBroaderThan` 为主,本关系通常作为反向查询视图或派生关系。 |
| conceptIncludes | 概念 → 概念 | 当前口径下前者包含后者。 |
| conceptOverlapsWith | 概念 → 概念 | 两个概念范围有交叉。 |
| conceptExcludes | 概念 → 概念 | 当前口径下前者排除后者。 |
| boundaryForConcept | 边界裁定 → 概念 | 边界裁定适用于某概念。 |
| conceptMapsToObject | 概念 → 稳定语义对象 | 概念映射到正式对象或对象集合;不直接映射到状态变量、信号、事件或判断。 |

业务对象之间:

| 关系代号 | 起点 → 终点 | 含义 |
|---|---|---|
| subIndustryOf | 产业 → 产业 | 子产业归属上级产业。 |
| segmentBelongsToIndustry | 环节 → 产业 | 环节归属产业。 |
| companyBelongsToIndustry | 公司 → 产业 | 公司归属产业。 |
| companyParticipatesInSegment | 公司 → 环节 | 公司参与某环节。 |
| productProducedBy | 产品 → 公司 | 产品由公司生产或经营。 |
| productBelongsToSegment | 产品 → 环节 | 产品归属某环节。 |
| materialBelongsToIndustry | 材料 → 产业 | 材料归属产业。 |
| materialUsedInSegment | 材料 → 环节 | 材料用于某环节。 |
| companyLinkedToAsset | 公司 → 资产 | 公司对应资产标的。 |
| assetLinkedToIndustry | 资产 → 产业 | 资产对应产业。 |
| segmentConnectsToSegment | 环节 → 环节 | 环节间的上下游、加工、替代、互补或竞争。 |
| companyRelatesToCompany | 公司 → 公司 | 供应、代工、合作、竞争、投资控制或授权。 |
| productRelatesToProduct | 产品 → 产品 | 依赖、替代、互补、代际、部件、集成或竞争。 |
| materialUsedInProduct | 材料 → 产品 | 材料具体用于某产品。 |
| productHasMaterialDependency | 产品 → 材料 | 产品或技术路线对某材料存在结构性依赖;增强、削弱、迁移等变化交给判断推理域表达。 |
| materialRelatesToMaterial | 材料 → 材料 | 替代、前驱、伴生、工艺互补或产能竞争。 |
| assetExposedToTarget | 资产 → Industry / Segment / Company / Product / Material / Concept / ObjectSet | 资产暴露到稳定语义对象;若暴露对象是状态变量、信号、催化剂或事件,应进入判断推理域。 |
| setContainsMember | 对象集合 → 成员对象 | 集合的显式成员,并说明纳入依据。 |

## 5. Actions：可以做哪些动作

完整定义以 `schemas/语义结构域/actions_ontology.yaml` 为准;每个动作都会生成一条动作记录。

这里的动作是对象动态行为的合法入口,对应对象建模里的"方法"部分,但不把方法直接塞进对象字段。对象的静态属性由 `schemas/语义结构域/objects_ontology.yaml` 定义;可执行行为由 `schemas/语义结构域/actions_ontology.yaml` 定义;可复用门禁与后续信号由第 6 节「Action 执行契约」说明（YAML:`rules.yaml`、`actions_ontology.yaml#side_effects`）。重点说明三个:
- `CreateOntologyRelation` 只负责创建显式关系,写入公共属性和审计;行业特有的关系子类型、强度等属性由业务包定义。
- `UpdateOntologyObject` 只能改非状态字段;状态变化要走专门的流转或治理动作。
- `DeprecateOntologyObject` 用"废弃/被替代/归档"状态保留历史。
- `MergeOntologyObject` 和 `SplitOntologyObject` 用来处理重复对象或过粗对象,不能用人工改 ID 的方式绕过治理。
- `MapConceptToObject` 和 `UnmapConceptFromObject` 专门管理概念到正式对象的映射,防止名词被自动升级成对象。

图谱生成和推理以显式关系为准。缺端点、缺证据或涉及其他 owner 资产时,进入待解析项、审核队列或补丁。

| 动作代号 | 作用 |
|---|---|
| CreateConceptScheme | 新建概念体系。 |
| CreateConcept | 新建概念并归入体系。 |
| DecideConceptBoundary | 做一次边界裁定。 |
| CreateIndustry | 新建产业。 |
| CreateSegment | 新建环节并归属产业。 |
| CreateCompany | 新建公司并连产业、环节。 |
| CreateProduct | 新建产品并连公司、环节。 |
| CreateMaterial | 新建材料并连产业、环节。 |
| CreateAsset | 新建资产标的。 |
| CreateObjectSet | 新建对象集合。 |
| ResolveObjectSet | 按规则解析集合成员并刷新快照。 |
| UpdateObjectSetMembers | 手动维护集合成员。 |
| CreateOntologyRelation | 新建一条显式关系。 |
| UpdateOntologyObject | 更新对象的非状态字段。 |
| DeprecateOntologyObject | 废弃对象(保留历史)。 |
| MergeOntologyObject | 合并重复对象,保留主对象并迁移别名、关系和引用。 |
| SplitOntologyObject | 拆分过粗对象,生成多个候选对象和迁移计划。 |
| MapConceptToObject | 把概念正式映射到稳定语义对象。 |
| UnmapConceptFromObject | 取消错误或过期的概念映射。 |
| ApproveCandidateObject | 候选对象通过校验后转为正式对象。 |
| RejectCandidateRelation | 拒绝候选关系并记录原因。 |

## 6. Action 执行契约（Rules + Events）

本域规则只回答「能不能建对象、能不能改状态、关系端点是否合法」，不表达投研判断。执行路径对齐 ActionType 契约：**Action → 校验规则 → 对象变更 → ActionFollowup side effect → 下游动作**。

公共 ActionFollowup 载荷与 Event/ActionFollowup 区分见 `00_框架概述` §8.2–8.3。YAML 字段细节见 `schemas/语义结构域/rules.yaml` 与 `actions_ontology.yaml` 的 `trigger_followup` side effect。

### 6.1 按动作族看门禁与事件

| 动作族 | 代表动作 | 必经规则 | 通过后 | 发出事件 | 典型下游 |
|---|---|---|---|---|---|
| 概念边界 | `DecideConceptBoundary`、`MapConceptToObject` | `concept_object_mapping_gate` | 映射允许或进审核 | `ConceptBoundaryDecided` | 无 / 边界审核 |
| 对象准入 | `CreateCompany` 等、`ApproveCandidateObject` | `candidate_object_admission_gate` | 正式对象或准入审核 | `ObjectCandidateApproved` | `CreateActionProposal`、`CreatePatchRequest` |
| 关系创建 | `CreateOntologyRelation` | `relation_endpoint_owner_gate` | 关系候选或补丁 | `OntologyRelationCreated` | 无 |
| 结构变更 | `MergeOntologyObject`、`SplitOntologyObject`、`DeprecateOntologyObject` | `object_state_change_via_action` | 状态迁移 + 审计 | `ObjectStructureChanged` | `CreatePatchRequest`（跨域） |

反例：绕过 Action 直接 PATCH 对象 `recordStatus` → 被 `object_state_change_via_action` 阻断。

### 6.2 规则卡片

#### `semantic.validation.concept_object_mapping_gate`
- **回答问题**：这个概念现在要不要映射成正式对象？
- **检查时机**：`MapConceptToObject`、`UnmapConceptFromObject`、`DecideConceptBoundary` 执行前
- **执行者**：`policy_gate` + `human_review_required`（边界未决时）
- **通过**：`mapping_allowed` → **失败**：`boundary_review_required`
- **正/反例**：概念有明确边界且将被证据/判断稳定引用 ✓；术语仍处争议期 ✗

#### `semantic.promotion.candidate_object_admission_gate`
- **回答问题**：候选对象能不能进正式库？
- **检查时机**：各类 Create 对象动作、`ApproveCandidateObject`
- **执行者**：`schema_enforced` + `skill_must_check`
- **通过**：`formal_object` → **失败**：`admission_review_item`
- **正/反例**：稳定 ID、类型、来源、必需关系齐全 ✓；缺 owner 或来源 ✗

#### `semantic.blocking.relation_endpoint_owner_gate`
- **回答问题**：这条关系的端点和 owner 是否合法？
- **检查时机**：`CreateOntologyRelation`、`RejectCandidateRelation`
- **执行者**：`schema_enforced`
- **通过**：`relation_allowed` → **失败**：`candidate_patch_request` 或阻断
- **正/反例**：端点存在且属当前 bundle ✓；跨 owner 无补丁路径 ✗

#### `semantic.action_precondition.object_state_change_via_action`
- **回答问题**：状态变更是否经由已注册 Action？
- **检查时机**：废弃、合并、拆分、候选晋升
- **执行者**：`schema_enforced`
- **通过**：`state_transition_allowed` → **失败**：`block_next_action`
- **正/反例**：`DeprecateOntologyObject` + `ActionAudit` ✓；后台直改状态 ✗

### 6.3 ActionFollowup 差异字段

本域事件均属 `event_family: semantic.object_lifecycle`。除公共载荷外无额外 `recommended` 字段；`ObjectCandidateApproved` 与 `ObjectStructureChanged` 的 `terminal_handling` 分别为 `trigger_next_action` 和 `create_patch_request_candidate`，后者常跨域进入治理域 `CreatePatchRequest`。

## 8. 输入与输出

| 输入 | 处理成 | 给谁用 |
|---|---|---|
| 研究问题、行业主题、公司名、产品名 | 概念、行业、环节、公司、产品 | 证据域、判断推理域 |
| 材料里的术语和边界线索 | 概念、边界裁定 | 证据归一、治理审核 |
| 业务结构线索 | 关系实例 | 图谱检索、多跳推理 |
| 上市公司和资产映射 | 公司、资产 | 资产影响、投资命题 |
| 治理补丁 | 对象、关系、边界的更新/废弃/合并/拆分 | 本体包发布 |

## 9. Policies：质量底线

| 检查 | 通过条件 | 处理方式 |
|---|---|---|
| 概念映射 | 范围内的概念要么映射到对象,要么进未解析项。 | 提交边界审核或登记为未映射概念。 |
| 对象关系 | 环节、公司、产品、材料具备必需的归属关系。 | 阻断入库,生成补丁或审核项。 |
| 关系端点 | 关系的起点终点能找到、类型合法。 | 进入悬空关系处理。 |
| 来源追溯 | 关键概念、边界、事实性对象和关系有来源或治理说明。 | 进入缺证据队列。 |
| 状态合法 | 对象状态字段符合规定取值和状态机。 | 留痕并提交治理审核。 |

候选对象和正式对象必须区分。自动抽取产生的对象、关系、边界裁定默认是候选状态;只有通过来源校验、端点校验、类型校验和必要的人工确认后,才可进入正式状态。候选内容可以被消费型任务能力参考,但不得作为高置信锚点直接生成结论。

关系方向以主关系为准,尽量避免人工维护双向冗余。若声明了 `inverse_of`,系统可以生成反向查询视图;需要显式保存反向关系时,必须自动校验两边端点、方向和证据一致。

## 10. 上游与下游关系

| 方向 | 本域提供 | 下游怎么用 |
|---|---|---|
| 证据域 | 各类研究对象和概念 | 证据通过提及、支持关系挂到对象上。 |
| 判断推理域 | 语义锚点和业务关系 | 状态、事件、判断、资产影响挂到对象上。 |
| 治理域 | 对象、关系、动作结果 | 用审计和复盘关系记录变更与审核。 |
| 本体包 | 稳定对象、关系、概念边界 | 作为可复用的语义锚点发布。 |

## 11. 边界与交接

| 边界项 | 本域做的 | 交给谁 |
|---|---|---|
| 投资判断 | 提供研究对象和锚点 | 判断和资产影响由判断推理域承接 |
| 动态事实和观测 | 提供稳定挂载对象 | 价格、产能、库存、交期、政策变化、市场预期进入证据域或判断推理域 |
| 原始证据正文 | 提供对象挂载目标 | 来源、主张、事实由证据域承接 |
| 推理运行 | 提供挂载对象 | 运行轨迹由治理域承接 |
| 入库裁决 | 提供候选对象、关系、边界 | 审核、补丁由治理域承接 |
| 行业实例扩展 | 定义结构和锚点 | 具体行业内容进入行业本体包 |
