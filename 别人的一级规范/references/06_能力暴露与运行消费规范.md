# 06-能力暴露与运行消费规范

本文面向运行端、Agent Runtime 和外置消费 Skill 开发者，解释如何稳定消费正式 Bundle。仓内 OntoFactory 不再编排消费推理；请使用 `skills/<scenario_id>/` 编译包 + 外置 Runtime。推理框架参考见 `archive/external_runtime_reference/14-投研推理/`。

## 1. 本文件依赖谁、输出给谁

消费规范连接前序域和运行时工作区。运行端读取时应先确认当前任务需要哪一层,避免把完整工程契约作为默认上下文。

| 来源 | 本文件怎么用 |
|---|---|
| `01-语义结构域` | 识别对象、边界、关系、ObjectSet 和正式语义锚点。 |
| `02-判断推理域` | 使用状态变量、状态假设、信号、判断、市场预期、预期差、资产影响候选、规则和情景路径。 |
| `03-证据域` | 使用来源、主张、事实候选、业务时间、新鲜度、冲突状态和权限标记。 |
| `04-治理域规范` | 使用准入门禁、消费门禁、ReviewRecord、ActionProposal、PatchRequest、审计和复盘规则。 |
| `05-工程交付与Bundle契约` | 优先使用 `runtime_contracts/runtime_index.yaml` 和 `scenario_runtime_index.yaml`;兼容期可读 `bundle_summary.yaml`、`capability_index.yaml`、`loading_rules.yaml`、registry 和目录路径。 |

消费运行的主要输出包括 `RuntimeEvidenceSnapshot`、`InferenceRun`、`JudgmentOutput(candidate)`、观察级或降级结论、补证任务和结构缺口反馈。只有用户明确要求持续跟踪或复盘时，才额外创建或更新 `JudgmentRecord`。

消费型任务能力读取各域时,也按 schema 桶定位上下文:

| schema 桶 | 消费时主要读取什么 |
|---|---|
| objects | 当前任务需要的对象、状态、证据、治理记录和视图。 |
| relations | 对象挂载、证据支撑、推理链路、审核和复盘关系。 |
| actions | 允许发起的候选动作、动作提案和写回边界；ActionFollowup 契约见各域 `actions_*.yaml#side_effects`。 |
| rules | 必跑的推理规则、证据规则、治理规则和降级规则。 |
| events | 判断推理域 `Event`（外部研究事实）；系统侧后续信号见 actions 行的 `trigger_followup`。 |
| policies | 准入、消费、权限、时点、版本、加载和输出边界。 |

## 2. 文档定位与消费边界

本文说明正式行业 Bundle 如何被运行端稳定消费。它重点回答一个问题:研究员提出问题、事件或团队判断记录时,运行端如何用最小必要上下文读取 Bundle,形成可追溯、可降级、可复盘的判断结果。

前五个文档定义资产是什么、如何治理、如何交付;本文件定义消费型任务能力如何按需加载、如何运行、如何输出、如何写回候选结果。它不是 Bundle 生产手册,也不是准入审核层的替代品,而是让 Bundle 被安全、低成本、可追溯消费的运行说明书。

Bundle 提供对象、关系、状态变量、证据索引、场景模型、规则、能力索引和加载契约；消费运行通过当次 `RuntimeEvidenceSnapshot` 注入实时证据，并把运行结果写入 team workspace。

需要特别区分三件事:

- Bundle 是能力包,提供可消费的研究结构。
- JudgmentRecord 是 team workspace 的工作流记录，不是本体对象，也不参与默认 runtime 加载。
- 复盘先沉淀为案例和偏误;重复、结构性、可归因的缺口再反哺本体。

消费型任务能力不直接修改正式 Bundle,不直接把候选对象写入 `shared/`,不直接把团队判断记录升级为正式规则,不直接把单次复盘失败转成正式 `PatchRequest`,也不直接生成交易执行建议。

当消费过程中发现缺口时,应根据缺口类型输出 `ontology_feedback`、`candidate_patch_request`、补证任务、`ReviewRecord` 或 `ActionProposal`。正式对象、关系、规则、模板和 bundle 版本变更,必须分别由 `04-治理域规范` 和 `05-工程交付与Bundle契约` 承接。

## 3. 标准运行链路

```text
用户输入问题 / 事件 / 明确跟踪请求
→ 00 形成 ResearchMissionContract、最小覆盖映射和路由决策
→ 平台匹配入口能力，如 AnalyzeEventImpact / CaptureJudgment / RunCounterCheck
→ 读取 00_bundle_manifest.yaml
→ 读取 runtime_contracts/runtime_index.yaml
→ 加载 scenario_runtime_index.yaml 中的 required_assets
→ 注入当次 RuntimeEvidenceSnapshot
→ 执行对象、关系、证据、反证、预期、权限、时点、版本门禁
→ 调用 LogicFunction、Rule Registry 或规则模板
→ 输出 markdown 报告、reasoning_result.json、ontology_feedback.json
→ 普通问题只保存当次运行结果
→ 明确要求记录、持续跟踪或复盘时才写 JudgmentRecord
→ 结构缺口进入 ontology_feedback 或 candidate_patch_request
→ 复盘后经治理流程决定是否形成 PatchRequest 或正式资产候选
```

路由全集与执行状态见 [`PLATFORM.md`](../PLATFORM.md)。这条链路是本文主线。

## 4. 三层逻辑视图

三层是加载视图。消费端只读取正式 `shared/`、`scenario_packs/`、`runtime_contracts/` 与当次 `RuntimeEvidenceSnapshot`，禁止读取 bundle workbench 候选。

| 逻辑层 | 作用 | 现有承载位置 |
|---|---|---|
| 语义层 | 让 AI 建立研究世界观,识别对象、边界、关系和核心状态变量。 | `shared/concept_layer/`、`shared/semantic_objects/`、`shared/semantic_relations/`、`shared/reasoning_assets/state_variables.yaml` |
| 能力层 | 说明遇到某类投研问题时应调用哪条处理路径、执行哪些门禁、允许输出什么。 | `shared/_index/capability_index.yaml`、`shared/reasoning_assets/scenario_models.yaml`、`scenario_packs/*/loading_rules.yaml`、`LogicFunction`、研究动作提案 |
| 明细层 | 提供字段、已审核证据和发布来源索引；生产审核、评测和历史材料不进入正式加载面。 | `schemas/`、`shared/evidence_index/`、`shared/governance/asset_provenance.yaml`；生产记录在 `bundle_workbenches/<bundle_id>/` |

语义层可以被摘要常驻加载;能力层用于选择场景模型和执行路径;明细层只在门禁、证据追溯、字段解释、评测或冲突处理时读取。

## 5. Logic 分层与平台术语对齐

本规范采用主流 Ontology 平台的命名和职责边界: `ObjectType` / `LinkType` 表达对象和关系,`ActionType` 是唯一受治理写回事务,`Function` 承接服务端逻辑和 function-backed action,`ObjectView` 承接对象中心应用视图,自动化流程对齐 Automate。

本仓库的等价映射如下:

| 平台术语 | 本规范承载 | 边界 |
|---|---|---|
| `ObjectType` / `LinkType` | `objects_*.yaml` / `relations_*.yaml` | 定义对象、关系、字段和端点。 |
| `ActionType` | `actions_*.yaml` + `ActionProposal` + `ActionAudit` | 改变对象、关系或状态的受治理入口;包含参数、校验、side effects 和审计。 |
| `Function` | `LogicFunction` + `LogicBlock` | 执行型逻辑原语;读取对象、证据和规则,输出结构化结果或 ActionProposal。 |
| `ObjectView` | `ObjectViewSpec` | 对象中心应用视图,正式对象仍由 bundle 承载。 |
| Automate | `AutomateFlow` | 声明触发条件、调用哪个 Function、产生什么 ActionProposal。 |

因此 Logic 只分四层:

| 层 | 资产 | 职责 | 交接边界 |
|---|---|---|---|
| What | Rule Registry 中的规则 / `InferenceRule` 兼容对象 / `ConductionTemplate` / `ScenarioPath` | 声明条件、输入输出边界、检查项和可引用 Function。Rule Registry 是 **Action 校验规则的复用库**：`rule_binding=action` 绑 `rule_refs`；`inference_asset` 绑 `inference_consumer_rule_refs`；`automate_flow` 绑 AutomateFlow。 | 执行步骤交给 How。 |
| How | `LogicFunction` / `LogicBlock` | 执行读图、检索、计算、LLM 总结、渲染或 ActionProposal 草案生成。 | 正式写回交给 Do。 |
| Which | `ScenarioModel` / `capability_index` / `loading_rules` | 选择场景、加载 refs、跑确定性门禁、调用 Function。 | 解释和提案由 How 生成。 |
| Do | `ActionType` / `ActionProposal` / `ActionAudit` | 参数化、受治理、可审计地写回。 | 推理和模型编排交给 What / How / Which。 |

命名上统一收敛为:rules 表达声明式门槛、推理条件、评分、晋升、阻断和动作前置条件,并以 **复用库** 形式挂回 Action（`rule_refs` / `inference_consumer_rule_refs`）;ActionFollowup 契约挂在 `actions_*.yaml` 的 `side_effects(type=trigger_followup)` 上,表达 Action 执行后的后续信号和下游触发;判断推理域 `Event` 仍是外部研究事实对象;functions 表达可执行计算、抽取、匹配、生成和编排能力;policies 表达运行策略和治理裁决;contracts 表达稳定接口和不变量。后续目录命名沿用这些类别，保持职责清晰。

执行编排统一收束到 `LogicFunction`。active `InferenceRule` 使用 `functionRef`，active `ScenarioModel` 和 scenario pack `loading_rules` 通过 `invoke_function` 调用 `LogicFunction`。

**Function 四层边界（P2）：** Action 简单门禁走 `rule_refs`；复杂校验走 `validation_checks(mode=function)`；执行型 Action 仅白名单可声明顶层 `function_ref`（`ComputeDerivedMetric`、`RunSimulation`、`CompareSimulations`、`EvaluateMonitor`、`ResolveObjectSet`）。`rule_binding=action` 的规则不得写 `function_ref`；`inference_asset` 规则若写 `function_ref`，必须通过 `inference_binding.function_refs` 或 `canonical_inference_rule_ids` 链接 canonical `InferenceRule`，避免与 `rules.yaml.condition` 重复实现。

`InferenceRule` 继续存在,但它不是所有规则的总容器。新规则优先进入对应域 `rules.yaml`;只有投研传导类、需要版本状态和复盘沉淀的 inference rule,才资产化为 `InferenceRule`。证据质量、权限、动作前置条件和后续信号触发规则分别归属证据域或治理域。

后续信号统一记为 `ActionFollowup`,机器契约见各域 `actions_*.yaml` 的 `trigger_followup` side effect。消费型任务能力必须区分:判断推理域 `Event` 是外部研究事件,如政策、订单、价格、技术或公司事件;`ActionFollowup` 是 Action 执行后的 side effect,如 EvidenceClaimCreated、StateHypothesisProposed、JudgmentOutputDrafted、HumanReviewRequested。`ActionFollowup` 可以触发下游 Action 或审核,但不能替代 `ActionAudit`,也不能直接修改正式 bundle。

标准 scenario pack 包含 `runtime_data_requirements.yaml`。它是场景级运行时查证和数据事件清单:通过 `evidence_slot_refs` 指向 `evidence_refs.yaml` 中的 evidence slot,通过 `freshness_policy_ref` 指向 `policies_governance.retrieval_policy.freshness_policy`,并声明缺少当期证据时如何降级。它还必须声明 `freshness_event_policy`:哪些观测写入、新鲜度变化、过期或 requirement 越界会发 ActionFollowup,以及可触发哪些下游 Action。证据实例仍使用既有字段,例如 `SourceDocument.sourceForm`、`SourceDocument.sourceReliability`、`SourceDocument.capturedAt`、`EvidenceClaim.claimStatus`、`EvidenceClaim.validTo`、`EvidenceFact.factStatus` 和 `StateVariableObservation.observationTime`。

`data_bindings.yaml` 是可选的语义接线层：`target_ref` 指向场景变量或 evidence slot，`data_product_ref` 指向平台数据产品目录，`value_contract` 规定运行值与来源字段。它与 `runtime_data_requirements.yaml` 通过 `data_binding_refs` 相连。绑定状态描述接线成熟度，不描述数据真值；只有运行期材料或带完整来源的人工输入才能变成观测候选。任何 `api_key`、token、password 或 secret 都不得进入 bundle。

`ontology_feedback` 和数据变化事件分工不同。`ontology_feedback` 用于结构缺口,例如对象缺失、状态变量缺失、关系或规则缺失;普通数据刷新、数据过期、当期数据缺失或数据新鲜度变化,应通过 `StateVariableObservationRecorded`、`DataFreshnessChanged`、`DataStaleDetected` 或 `DataRequirementBreached` 这类 ActionFollowup 驱动监控、补证、降级或重跑推理。

`templates/cross_bundle_runtime_scenario_template/` 和 `fixtures/judgment_tracking_scenario/` 属于跨 bundle 运行时场景形态,用于团队判断记录跟踪流等应用层工作流。它们使用自己的运行时契约,与标准 scenario pack 的 bundle 校验路径分开。

## 6. 能力层契约

能力层表达一个完整、自洽的投研判断步骤,例如事件影响解析、反证检查、预期差评估或资产影响候选生成。

`shared/_index/capability_index.yaml` 是能力导航入口。每条能力至少说明:

- `capability_id`: 稳定能力 ID,如 `AnalyzeEventImpact`。
- `input_contract`: 可接收的问题、事件、证据或对象引用。
- `output_contract`: 允许输出的结构,并引用 `schemas/common.yaml.global_research_output_boundary`。
- `bound_scenario_models`: 绑定的 `ScenarioModel`。
- `bound_logic_functions`: 可选绑定的 `LogicFunction`；一旦 active 场景声明 `invoke_function`，运行器必须实际解析并执行其 `blockRefs`，同时输出执行轨迹。
- `required_refs`: 需要读取的 scenario ref 文件或 shared 资产类型。
- `deterministic_gates`: 必跑的确定性门禁。
- `failure_behavior`: 缺证、缺关系、缺反证或缺市场预期时的降级方式。

推荐的首批能力 ID:

| 能力 ID | 作用 | 典型输出 |
|---|---|---|
| `CaptureJudgment` | 在用户明确要求记录时，把自然语言判断写成 team workspace `JudgmentRecord`。 | `JudgmentRecord`、promotion assessment、复盘计划 |
| `AnalyzeEventImpact` | 从事件或问题映射到正式场景框架，结合当次证据输出可降级判断；默认不持久化长期记录。 | `RuntimeEvidenceSnapshot`、`InferenceRun`、`JudgmentOutput(candidate)`、结构缺口反馈 |
| `RunCounterCheck` | 检查 weakening / blocking 反证和竞争解释。 | 反证清单、置信度调整、缺口反馈 |
| `EvaluateMarketExpectationGap` | 对比判断与 `MarketExpectation`,识别预期差是否可成立。 | 预期差状态、缺口或降级原因 |
| `GenerateAssetImpactCandidate` | 在证据、反证、预期差和边界门禁通过后生成资产影响候选。 | `AssetImpact` 候选或观察结论 |
| `ReplayHistoricalCase` | 用历史案例或 as-of 回放验证规则和情景路径。 | `EvalResult`、`ReviewRecord`、`PatchRequest` 候选 |

能力层命名优先使用候选、影响、缺口或复盘任务，避免把研究过程误读成最终估值结论。

`ActionProposal` 表示研究动作提案。投资交易动作边界以 `schemas/common.yaml.global_research_output_boundary` 为准。

允许的研究动作包括:

- 补证任务。
- 复盘任务。
- 本体补丁候选。
- 人工审核任务。
- 继续观察或监控任务。

投资交易动作边界在 `schemas/common.yaml.global_research_output_boundary` 中统一声明。

### 6.1 两个入口共享框架，但持久化策略不同

`CaptureJudgment` 和 `AnalyzeEventImpact` 都可以使用正式场景框架，但前者是明确的记录动作，后者是默认无长期副作用的分析动作。

`CaptureJudgment` 保存原话、作者、锚点、场景、假设、候选变量、所需数据、支持信号、证伪条件、下次复盘时间和 promotion assessment。它不得把记录自动转成正式证据或规则。

`AnalyzeEventImpact` 加载正式框架和当次证据快照，形成传导链、支持与反证、结论等级和跟踪指标。普通问题即使生成 `JudgmentOutput(candidate)`，也不创建 `JudgmentRecord`；只有用户明确要求“记录、持续跟踪或复盘”时，才调用持久化入口。

具体工作区字段和路径以 `schemas/工程交付与Bundle契约/contracts_workspace.yaml` 为权威。

## 7. 规则责任与失败处理

所有 Rule Registry 规则、`InferenceRule` 兼容对象和 `ScenarioModel` 都应声明或引用 `enforcement_contract`。它回答一条规则由谁保证、失败后如何处理、是否需要人工复核。

推荐责任等级:

| 等级 | 含义 |
|---|---|
| `schema_enforced` | 字段、枚举、状态或引用由 schema 和校验脚本保证。 |
| `policy_gate` | 由 policy、quality gate、loading_rules 或 ScenarioModel 确定性步骤保证。 |
| `skill_must_check` | 运行端 / 任务能力开发者显式检查,缺失时降级或记录缺口。 |
| `human_review_required` | 进入 ReviewRecord、review_queue 或 ActionProposal 审核。 |
| `reference_only` | 仅作解释或导航。 |

规则还要声明 `failure_behavior`,常见取值包括 `block_with_gap`、`downgrade_to_observation`、`enqueue_review`、`create_patch_request_candidate`、`lower_confidence` 和 `ask_user_for_clarification`。

`ask_user_for_clarification` 应谨慎使用。只有当缺失信息会导致入口能力无法选择、研究对象无法定位或输出边界无法判断时,才向用户追问;其他缺口优先通过降级、补证任务、`ontology_feedback` 或 `ActionProposal` 承接。

| 情况 | 优先处理 |
|---|---|
| 缺少必要对象 | 先基于候选对象降级输出,并记录对象缺口或未解析项。 |
| 缺少证据 | 输出观察级结论,同时生成补证任务。 |
| 缺少市场预期 | 不生成高置信资产影响,降级为预期待核查。 |
| 用户问题确实无法定位 | 向用户追问。 |
| 涉及权限或输出边界 | 阻断、脱敏或转人工审核。 |

原则是:机器稳定校验字段、枚举、状态和引用;LLM 负责路由、总结、解释和提案候选。

本体优化是低频治理动作。普通事件分析不自动沉淀长期记录；明确进入跟踪的判断先在 team workspace 复盘，多次独立记录或历史案例指向同类结构问题时，再在 bundle workbench 生成候选资产或补丁候选。

推荐的回流门槛是:

```text
ReviewRecord → bias_log / case_memory
RepeatedGap → candidate_patch_request
ApprovedGap → PatchRequest
```

也就是说,一次看错、证据不足或判断失败,通常先记录为 `ReviewRecord`、`bias_log` 或 `case_memory`;重复出现且能归因到对象缺失、状态变量缺失、规则缺失、证据链缺口时,才进入 `candidate_patch_request`;经过审核确认后,才成为正式 `PatchRequest`。

## 8. 冲突登记视图

冲突使用现有结构承载，不新增根目录冲突文件:

| 冲突类型 | 写入位置 |
|---|---|
| 叙述性矛盾、反证、材料分歧 | `research_memory/wiki/contradictions.md` |
| EvidenceClaim / EvidenceFact 之间的结构化冲突 | `evidence_conflict_record`、证据关系中的冲突关系 |
| 悬空引用、不可解析关系、未裁决冲突 | `bundle_workbenches/<bundle_id>/reviews/review_queue.yaml` 或 `research_memory/wiki/` |
| 需要修改正式资产或跨包 owner 的问题 | `PatchRequest` |
| 需要人工裁决或复盘的问题 | `review_queue`、`ReviewRecord` |

冲突影响结论时,消费型任务能力降低置信度、阻断正式资产影响候选,或生成补证/补丁/复盘任务。

## 9. 消费失败如何回流生产闭环

本文不展开材料蒸馏、冷启动或 bundle 生产流程。消费规范只说明:消费型任务能力在使用 bundle 时发现缺口,应如何把缺口反馈给生产闭环。

| 消费失败类型 | 消费侧处理 | 回流对象 |
|---|---|---|
| 对象缺失或无法定位 | 使用候选对象或概念级锚点降级输出,标记不能形成正式结论。 | `ontology_feedback.unresolved_object`、未解析项、必要时 `candidate_patch_request` |
| 状态变量缺失 | 只输出观察级判断或补充状态变量建议,不硬造观测。 | `ontology_feedback.missing_state_variable`、补丁候选 |
| 关系或传导链缺失 | 保留部分链路和缺口位置,不补写正式关系。 | `ontology_feedback.missing_relation`、`ActionProposal` 或补丁候选 |
| 规则、模板或情景路径不足 | 降级为人工分析说明,记录需要新增或修正规则。 | `ReviewRecord`、`candidate_patch_request` |
| 证据不新鲜、缺证或冲突未裁决 | 降置信度、阻断升级或生成补证任务。 | 补证任务、证据冲突裁决、`ReviewRecord` |
| 运行时数据刷新或过期 | 发 ActionFollowup,触发监控、补证、重跑推理或降级。 | `DataFreshnessChanged`、`DataStaleDetected`、`ActionProposal` |
| 市场预期缺失或不可比 | 不生成高置信资产影响,降级为预期待核查。 | 预期补证任务、观察级结论 |
| 权限、时点或版本不满足 | 阻断、脱敏、重新按 as-of 加载或进入审核。 | 合规审核、版本兼容处理、`ActionAudit` |
| 多次复盘暴露同类缺口 | 先聚合案例和偏误,确认结构性问题后再进入补丁。 | `bias_log`、case_memory、`PatchRequest` |

回流不等于直接写库。生产型任务能力或治理流程负责把这些反馈转成候选资产、补丁请求、能力索引调整或工程发布任务。消费型任务能力只负责定位缺口、说明降级原因、保留来源链路和提交候选反馈。

## 10. 验收标准

一个 bundle 可以被稳定消费,至少应通过以下检查:

- 能从 `bundle_summary.yaml` 定位研究范围、能力入口和已知缺口。
- 能从 `capability_index.yaml` 选择合适的能力和场景模型。
- 能从 `loading_rules.yaml` 加载最小必要 refs,不全量读取 bundle。
- 能执行证据、关系端点、反证、市场预期、预期差和写回权限等门禁。
- 能输出 `InferenceRun` 或明确降级为观察,并把缺口写入 `ontology_feedback`。
- 能用 `EvalCase/EvalSuite/EvalRun/EvalResult` 记录典型事件链路是否跑通。
- 普通事件分析不创建 JudgmentRecord；明确跟踪或复盘时，能生成符合 `judgment_record_contract` 的记录和验证计划。
- 能区分 `ReviewRecord`、`bias_log`、`ontology_feedback`、`candidate_patch_request` 和 `PatchRequest`,避免单次判断失败直接污染正式本体包。

验收失败是生产闭环的输入。失败项转成补证任务、候选资产生产任务、PatchRequest 或复盘任务。
