# 诊断报告：「我的研究」进度虚高（无 05 产出却显示 5/5）

日期：2026-07-30
涉及界面：前端「我的研究」列表（`07_runtime/app/runs/page.tsx` + `07_runtime/app/components/run-list.tsx`）
涉及数据：`90_compat/instances/00_本机运行/workbench.sqlite`

---

## 1. 现象（用户反馈）

「我的研究」界面中，部分项目的**进度已经显示 5/5、状态 complete**，但点开该项目后**并没有真正的 05 阶段产出（stage_05 最终交付报告）**。进度与真实产出不一致，误导判断。

## 2. 真实数据证据

当前库中受影响的项目（进度虚高）为 **1 个**：

| run id | 显示进度 | 显示状态 | 实际最高已批准阶段 | 是否有已批准的 stage_05 |
|---|---|---|---|---|
| `f19c7d94-d6ea-4796-acbb-61d63c41257c` | 5 | complete | **1**（仅 stage_01 v1 批准） | **否**（stage_05 v1/v2 均为 `superseded`，从未 approved） |

该 run 的 stage_XX 产出真实状态：

| 阶段 | 版本/状态 | 是否曾 approved |
|---|---|---|
| stage_01 | v1 approved / v2 needs_review | ✅ 仅 v1 |
| stage_02 | v1–v3 failed / v4 superseded | ❌ |
| stage_03 | v1–v4、v6–v7、v8–v10 多为 superseded，v6/v7 failed | ❌ |
| stage_04 | v1 failed / v2–v4 superseded | ❌ |
| stage_05 | v1、v2 均为 **superseded** | ❌ **从未批准** |

结论：该 run 实际只完成了 stage_01，其余阶段全部失败或被取代，却在前端显示 `5/5 · 已完成`。

> 注：此前曾在库中观察到一批「归档测试/归档命名」的草稿 run（current_stage=0 但库内有已批准产出），属测试残留数据，本次复测时已被清理（当前库共 7 个 run，仅上述 1 个虚高）。但下面给出的修复逻辑对两类漂移（虚高/虚低）都能一次性校正。

## 3. 根因

进度字段 `research_runs.current_stage` 只在**批准产出**时被写入，且是**单向推进**；但当该产出后续被**取代（supersede）降级**时，进度**不回退**。

- 单向推进发生在 `07_runtime/adapters/db/artifacts.ts` 的 `approveArtifact()`（约 109–144 行）：
  - `current_stage: stage || run.current_stage`
  - `status: stage === 5 ? "complete" : "in_progress"`
  - 即：只要某个 `stage_05` 被批准过，`current_stage` 立刻被钉成 5、状态 complete。
- 降级不回退：`supersedeOtherArtifactAttempts()` 与 `supersedeDownstream()`（`artifacts.ts` 94–108 行）会把旧版本/下游产出置为 `superseded`，但**没有重新计算 run 的进度**。
- 调用取代逻辑的位置：`engine/workflow/approve.ts:102-103`、`engine/workflow_shared.ts:379`、`engine/workflow/change_set_apply.ts:132`。

典型漂移路径：`stage_05` 被批准（进度=5/complete）→ 用户重新生成 `stage_05`（v2）→ 旧 v1 被 `supersedeOtherArtifactAttempts` 降级为 `superseded`，v2 也未再批准 → 此时库内已无任何 approved 的 `stage_05`，但 `current_stage` 仍停在 5、状态仍 complete。

## 4. 修复方案（分阶段）

### 阶段一：新增「进度重算」单一真相源（防复发）
在 `07_runtime/adapters/db/runs.ts` 新增 `recomputeRunProgress(runId)`：
- 读取该 run 所有 `status='approved'` 且 `kind LIKE 'stage_%'` 的产出；
- 取已批准阶段的**最大编号**作为 `current_stage`；
- `status`：最高阶段 ≥5 → `complete`，>0 → `in_progress`，=0 → 保持原状态（不误改归档/草稿语义）。

挂点（任何会改变「已批准产出集合」的地方都触发重算）：
1. `approveArtifact()`：用 `recomputeRunProgress` 取代当前的直接赋值（artifacts.ts 131–135）。
2. `supersedeOtherArtifactAttempts()` 与 `supersedeDownstream()` 末尾：调用 `recomputeRunProgress`。
3. `change_set_apply.ts:132` 之后、`workflow_shared.ts:379` 之后：调用 `recomputeRunProgress`。

### 阶段二：存量修复（修正当前虚高）
新增脚本 `07_runtime/scripts/recompute-run-progress.ts`：遍历 `listRuns()`，对每个 run 调 `recomputeRunProgress`，打印修正前后。手动跑一次，把 `f19c7d94` 等漂移项校正为真实进度（该 run 将变为 `1/5 · in_progress`）。

### 阶段三：验证
- 新增单元测试：批准 stage_05 → `current_stage=5`；随后取代该产出 → `current_stage` 回退到实际最高已批准阶段。
- 运行现有 `research_experience_metrics.test.ts` 等确保无回归。

## 5. 风险与备注
- **complete 口径**：当前沿用「stage_05 被批准即 complete」（`approve.ts` 现状）。`research_experience_metrics.ts:91` 另有更严口径（要求全部 5 阶段均 approved）。本次**不改 complete 语义**，仅让 `current_stage` 与实际已批准阶段一致；若你希望「complete」也改为要求全阶段批准，请单独告知。
- 不删除任何数据，重算仅调整 `current_stage`/`status` 两个字段，属于最小风险修正。
- 测试残留的「归档测试/归档命名」run 若再次出现，阶段二脚本会一并按真实产出校正（不会误删）。
