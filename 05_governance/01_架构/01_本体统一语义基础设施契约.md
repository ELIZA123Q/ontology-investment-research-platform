# 01 本体统一语义基础设施契约

状态：active  
适用范围：`90_compat/ontology/`、`90_compat/methods/`、`90_compat/workflow/`、`07_runtime/`、`90_compat/instances/`、`90_compat/methods/05_表达/`

## 1. 核心原则

投研本体是整个投研工作台的统一语义基础设施。它定义投研领域中稳定存在的对象、关系、状态、事件与约束，形成全系统唯一一致的业务语义标准。

本体不保存单次研究事实，不编排 01—05，不登记方法执行状态，不承担具体研究逻辑，也不直接推出投资判断。工作流、方法、数据连接器、模型和表达层可以各自执行不同职责，但必须围绕同一批本体对象和关系交换信息。

因此，“本体约束”不只表示 Stage04 运行若干规则。它至少同时满足：

1. **定义唯一**：稳定业务类型、关系、属性值域只在正式本体定义一次。
2. **引用统一**：方法、阶段产物、数据映射和判断结果使用稳定语义 ID，不另造同义对象。
3. **交换有类型**：模块间 I/O 能还原为本体对象、关系或明确标注的运行对象。
4. **约束前置**：对象类型、关系端点、必填属性、范围和时间约束在写入时校验，不只在末端审计。
5. **演进可追溯**：每次运行记录本体版本与内容指纹；语义变更可以定位受影响产物。

## 2. 权威分层

| 内容 | 唯一权威 | 其他层怎样使用 |
|------|----------|----------------|
| 稳定对象、关系、状态、事件、业务枚举、稳定约束 | `01_semantic/01_ontology/models/*.yaml` | 通过语义目录读取，不手写副本 |
| 正式模型文件集合与指纹顺序 | `01_semantic/01_ontology/model_registry.yaml` | 所有目录、生成器、影响分析和发布校验读取同一注册表 |
| 领域业务参数实例 | `90_compat/ontology/02_领域/<domain>/business_instances.yaml` | 以正式类型实例化，保留来源和版本 |
| 跨阶段标识、状态机、运行与发布合同 | `05_governance/02_合同/` | 明确标注为运行合同，不伪装成本体 |
| 研究结构、取证和裁决方法 | `90_compat/methods/` | 声明适用的本体对象、关系和输入输出 |
| 阶段编排与职责 | `90_compat/workflow/` | 规定何时创建、补全、确认哪些语义对象 |
| 单次事实、规则评价、判断和留痕 | `90_compat/instances/` / Runtime 数据库 | 以本体实例图和阶段投影保存 |
| 面向读者的表达 | `90_compat/methods/05_表达/` / Stage05 | 只投影已确认判断，不创建新业务语义 |

“唯一权威”不等于所有内容都放进本体。流程状态、API、任务调度、权限、重试、方法选择等仍属于各自合同；它们不得再定义一套平行业务语言。

## 3. 统一语义链

```text
正式本体定义
  → Runtime Semantic Catalog
  → 阶段 Schema / 方法路由 / 数据映射 / UI 选项
  → Business Instance Graph
  → EvidenceFact / Signal / Hypothesis / Judgment
  → ReportClaim / Expression
```

逆向追溯必须成立：

```text
Expression
  → Judgment
  → RuleEvaluation + MethodApplication
  → Hypothesis + Signal
  → EvidenceFact
  → EvidenceClaim
  → SourceDocument
```

方法负责“怎样研究”，本体负责确保这条链上的对象含义、关系和边界一致。

## 4. Runtime 读取规则

### 4.1 唯一读取入口

Runtime 读取正式本体统一经过：

- `07_runtime/engine/ontology_catalog.ts`：服务端完整语义目录，提供对象、关系、规则、枚举、模型版本和内容指纹。
- `07_runtime/engine/ontology_vocabulary.generated.ts`：供浏览器和 Zod 使用的只读枚举投影；漂移测试必须证明它与正式本体完全一致。
- `07_runtime/engine/semantic_reads.ts`：读取已确认阶段快照的防腐层；正式图存在时必须校验阶段产物指纹，禁止图与 JSON 静默漂移。
- `01_semantic/01_ontology/model_registry.yaml`：正式模型文件集合与内容指纹顺序的机器权威；任何新模型必须先登记，禁止各校验器维护自己的文件清单。

除语义目录、生成/漂移校验脚本和冻结校验器外，业务模块不得自行扫描 `models/*.yaml`，也不得手写正式本体已有的枚举副本。

### 4.2 明确的防腐层

Runtime 特有的 `Task`、`Run`、`StageArtifact`、`MethodApplication` 等对象仍由公共合同定义。它们与正式业务对象接触时必须通过显式关系或引用字段，例如：

- `MethodApplication.target_ontology_object_refs`
- `JudgmentUnit.scope_ref`
- `EvidenceFact.ontology_node_ids`
- `Judgment.rule_evaluation_refs`

不得以一个宽泛字符串字段替代可解析的语义引用。

## 5. 阶段语义责任

| 阶段 | 必须围绕本体形成的结果 |
|------|------------------------|
| 01 受理 | 识别研究对象、时间范围和判断动作；未识别项显式标记为候选或缺口 |
| 02 结构 | 创建冻结范围、判断单元、状态变量绑定、证据要求和竞争解释；全部引用可解析 |
| 03 证据 | 将外部数据映射为 SourceDocument → EvidenceClaim → EvidenceFact，并绑定范围、时间与判断单元 |
| 04 判断 | 从事实形成 Signal、Hypothesis、RuleEvaluation、Judgment 和 ReasoningTrace；禁止证据直达判断 |
| 05 表达 | 将已确认 Judgment 投影为表达；不得新增事实、关系或判断 |

## 6. 数据映射合同

连接器返回的是外部数据，不是本体实例。进入研究链前必须完成：

1. 外部标识到稳定对象 ID 的映射；
2. 外部字段到本体属性或明确运行字段的映射；
3. 单位、时间、范围和口径归一；
4. 来源、原文、字段血缘和获取时间留痕；
5. 无法映射的字段进入候选/缺口队列，不静默降为自由文本。

本体不规定调用哪个连接器，也不替连接器取数；它规定取回的数据在系统里“是什么”以及“可以怎样关联”。

版本化映射的机器权威为
`05_governance/02_合同/ontology_data_mapping_profiles.yaml`，Runtime 通过
`07_runtime/engine/data_mapping_profiles.ts` 校验目标对象和属性是否仍存在于正式本体。
连接器调用留痕必须携带 mapping profile ID、版本、目标类型和字段血缘；标记为
`candidate_only` 或 `requires_context` 的映射不得伪装为已物化本体实例。
注册表的 `required_connectors` 必须与 Stage03 Runtime 实际接线通道一一对应；
未登记通道不得以 `unregistered` 状态进入新的生产研究。结构化行情、财务、宏观、
指数和基金结果最多先形成 `Observation` 候选；事件数据最多先形成 `Event` 候选；
研报、新闻与网页阅读结果最多先形成 `SourceDocument` 候选，均不得直达最终判断。

## 6.1 本体变更影响合同

本体变更必须经过 `ontology_consumer_registry.yaml` 声明的消费面影响分析。
`07_runtime/engine/ontology_impact.ts` 按语义元素签名识别对象、关系、规则和场景的
新增、删除与修改，输出受影响代码/资产路径和必跑回归；同时根据阶段
`semantic_context.ontology_fingerprint` 识别仍绑定旧本体基线的运行。影响分析只决定
“哪里需要审阅或重算”，不得静默改写历史研究结论。

## 6.2 正式发布语义基线

生产正式包必须同时冻结两项机器资产：

- `semantic_context.yaml`：汇总 Stage01—05 的本体版本、内容指纹、声明对象、
  引用对象、解析集合、任务局部对象和覆盖率；
- `business_instance_graph.yaml`：冻结与 Stage02—04 已批准产物投影指纹一致的
  正式实例图。

`run_manifest.yaml` 必须绑定两项资产的内容哈希。发布校验重新计算当前正式本体
内容指纹，并确定性核对集合划分、覆盖率、解析状态、图权威合同和阶段投影指纹。
生产包任何阶段存在未解析语义引用、旧本体指纹或实例图兼容回退时均不可发布。
历史 `fixture` 可以不补写语义基线，仅作为显式只读回归存在。

`npm --prefix runtime run ontology:audit` 负责持续检查模型注册表、Runtime 正式模型读取入口、
18 个 Stage03 接线与映射 Profile 的集合一致性，以及发布、评价、雷达和治理查询是否仍经过
受控语义读取层。

## 6.3 通用关系写入

关系编辑器不得接受自由文本关系名。系统根据所选源对象类型，从正式本体目录筛选
定义域兼容的关系，再从当前正式实例图筛选值域兼容的目标对象。新关系通过
`LinkOntologyObjects` Runtime Action 建立提案，必须经过人工批准和图版本检查，
最终由完整图合同再次校验关系属性、端点类型、语义闭包及禁止证据直达判断约束。
该 Action 属于运行治理，不进入正式本体。

## 7. 强制验收指标

| 指标 | 目标 |
|------|------|
| 正式本体枚举的 Runtime 手写副本 | 0 |
| 新写入实例的对象类型与关系端点校验覆盖 | 100% |
| Stage02—05 主链引用可解析率 | 100% |
| 完成态运行的本体版本与内容指纹记录率 | 100% |
| EvidenceFact 绕过 Signal/Hypothesis 直达 Judgment | 0 |
| 无法映射却以普通自由文本进入正式链的字段 | 0 |

## 8. 迁移顺序

1. **语义目录收口**：统一本体加载、枚举投影、版本和指纹。
2. **阶段 I/O 收口**：逐项移除 Zod、UI、归一化器中的平行枚举和对象类型。
3. **实例图前置**：Stage02 起即以图为权威，阶段 JSON 逐步降为可编辑投影。
4. **数据映射本体化**：连接器字段进入可版本化 mapping profile。
5. **查询与交互本体化**：搜索、导航、缺口发现和影响分析从语义图生成。
6. **演进治理**：本体变更自动生成影响清单、迁移要求和回归范围。

任何一步都不得把方法逻辑或工作流状态塞进正式本体来换取表面统一。
