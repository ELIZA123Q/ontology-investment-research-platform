# 02_本体缺口扫描矩阵与处理细则

本附录保存缺口扫描矩阵字段、下游压力测试、必须记录条件、分级状态、承接处理与缺口说明生成细则。主规范保留“先扫缺口再定稿”与分级枚举；正式 schema 以 [`../模板/02_任务本体视图模板.yaml`](../模板/02_任务本体视图模板.yaml) 与 [`../模板/02_本体缺口说明模板.md`](../模板/02_本体缺口说明模板.md) 为准。

---

### 7.2 缺口扫描矩阵

每次 02 必须在 YAML 或配套扫描文件中形成缺口扫描矩阵。建议字段如下：

| 字段 | 含义 |
|---|---|
| `required_item` | 本次研究最少需要的对象、变量、关系、路径、规则、反证条件或证据 profile |
| `required_by` | 来自 01 的哪个问题、判断目标、路径节点或输出要求 |
| `current_mapping` | 当前正式本体如何承接 |
| `coverage_status` | `direct_cover` / `upper_cover` / `weak_cover` / `missing` |
| `evidence_collectable` | 03 是否能据此收集或标注证据 |
| `reasoning_usable` | 04 是否能据此执行路径判断、反证处理或结论强度判断 |
| `gap_severity` | `none` / `minor` / `major` / `blocking` |
| `needed_action` | 无需补充 / 03 候选补丁 / 02 返工 / 退回 01 / 本体优化 |
| `usage_limit` | 若进入 03 或 04，必须遵守的限制 |

`coverage_status` 不能只写“已覆盖/未覆盖”。尤其要识别 `upper_cover` 和 `weak_cover`，因为大多数本体问题不是完全没有字段，而是有上位壳、无推理承载力。

### 7.3 下游压力测试

每个必要本体项都必须通过下游压力测试。02 不问“文本上有没有写到”，而问：

1. **03 证据压力测试**：03 能否据此设计实例、观测、证据和反证需求？
2. **04 推理压力测试**：04 能否据此判断路径成立、路径削弱、路径阻断或竞争解释？
3. **05 表达压力测试**：05 需要表达的研究结论，能否由 04 在该结构上推出？

只要某项本体承接不能指导 03 收证据，或不能支撑 04 推理，就不能判定为充分覆盖。即使它能被某个上位概念勉强挂接，也只能判定为 `upper_cover` 或 `weak_cover`。

### 7.4 必须记录的条件

出现以下任一情况，02 必须触发本体缺口说明，不得只在正文中轻描淡写：

1. 01 的核心研究对象只能映射到泛化对象，无法映射到具体对象或明确上位类；
2. 任一主路径缺少必要状态变量；
3. 任一主路径缺少可执行的实例、观测、证据或反证需求；
4. 任一主路径缺少削弱、阻断或竞争解释条件；
5. 任一关键结论类型找不到对应推理规则或输出口径；
6. 03 必须临时新增对象、变量、关系、路径或证据 profile 才能继续；
7. 04 只能依赖“可能、影响、风险、变化、相关、扰动、因素”等泛化表达完成判断；
8. 关键对象、状态变量、路径、规则或证据 profile 中，`upper_cover`、`weak_cover`、`missing` 合计超过 30%；
9. 出现任一 `blocking` 缺口；
10. 出现会改变核心待验证命题、对象范围或输出口径的 `major` 缺口。

必须记录的条件优先于模型自评。只要触发，不能把阶段状态写成无缺口通过。

### 7.5 缺口分级与阶段状态

缺口严重度按后续影响分级：

| 严重度 | 判定标准 | 阶段处理 |
|---|---|---|
| `none` | 正式本体直接覆盖，03 可收证据，04 可推理 | 可进入 03 |
| `minor` | 有少量上位覆盖或候选项，但不影响主路径和关键判断 | 可进入 03，但必须传递限制 |
| `major` | 影响部分主路径、关键变量、反证或输出口径 | 原则上返工 02；若继续进入 03，只能作为候选验证任务 |
| `blocking` | 导致 03 无法收证据、04 无法推理，或 01 边界本身无法承接 | 不得进入正式 03，需退回 01、返工 02 或进入本体优化 |

阶段状态建议这样使用：

```yaml
ontology_gap_scan:
  status: no_gap | minor_gap | major_gap | blocking_gap
  can_enter_03: true | false
  limitation_for_03: []
  limitation_for_04: []
```

### 7.6 正式本体不能完全承接时怎么办

没有找到现成定义时，先判断缺的是结构还是现实信息：

| 情形 | 处理方式 |
|------|----------|
| 缺少稳定的对象、关系、变量、事件、规则或证据 profile 定义 | 记录本体缺口；必要时形成任务候选 |
| 名称、角色或范围无法唯一理解 | 先澄清；影响研究意图时退回 01 |
| 已有类型，但缺少现实公司、产品、关系或事件 | 作为实例需求交给 03 |
| 已有关键变量，但缺少现实方向、数值或时间 | 作为观测需求交给 03 |
| 已有证据要求，但尚未取得来源和材料 | 作为证据需求交给 03 |
| 只有上位概念能承接，无法形成证据需求或推理规则 | 判定为 `upper_cover` 或 `weak_cover`，写入缺口扫描 |
| 必须依赖 03 临时新增结构才能继续 | 触发本体缺口说明，并限制 04 不得基于临时结构输出强判断 |

任务候选只用于本次研究临时承接不可缺少、但尚未正式入库的稳定结构。它必须与正式本体分开保存，并说明使用边界和风险。

03 可以基于材料提出候选对象、候选变量、候选路径或候选规则输入，但不得直接把这些内容变成正式本体。04 可以读取候选项作为观察或待验证解释，但不得把未确认候选项作为强结论依据。

### 7.7 缺口说明的生成规则

02 每次都必须完成本体缺口扫描。是否单独生成《02_本体缺口说明》，按以下规则处理：

| 扫描结果 | 是否单独生成缺口说明 | 处理 |
|---|---|---|
| `no_gap` | 不强制 | 在 YAML 中记录扫描通过 |
| `minor_gap` | 可选，但必须在 YAML 中记录 | 可以进入 03，并传递限制 |
| `major_gap` | 必须生成 | 原则上返工 02；如继续，只能进入候选验证 |
| `blocking_gap` | 必须生成 | 不得进入正式 03 |

缺口说明只记录缺失的判断能力、本次影响、下游限制和待确认问题，不直接决定正式本体如何修改。正式入库仍需要本体维护流程确认。
