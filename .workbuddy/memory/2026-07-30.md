## 开发服务器卡死诊断与处理
- 现象：http://127.0.0.1:3000 打不开，curl 返回 HTTP 000（不可达），但 `lsof -i :3000` 显示 node 进程仍在 LISTEN。
- 诊断：进程处于「端口监听但完全不响应 HTTP」的病态卡死态（典型为 8GB 内存压力下 Node 进程死锁/内存耗尽）。普通 SIGTERM 可能杀不掉。
- 处理：用 `kill -9` 强制清除 3000 端口 LISTEN 进程（`for pid in $(lsof -tiTCP:3000 -sTCP:LISTEN); do kill -9 $pid; done`），再后台 `npm run dev:singleton` 重启，约 6 秒后 HTTP 200 恢复。
- 注：`dev-singleton.sh` 启动时会自动 kill 端口旧进程，但卡死进程不响应 SIGTERM 时会失败，故需手动 kill -9。
- 根因/预防：机器 8GB 内存 + 多应用（Claude/飞书/Cursor/Chrome）并发，Next.js dev(webpack, 1.4万文件) 易触发内存压力卡死。建议运行期间少开重型应用；频繁卡死则考虑关闭部分应用或重启机器释放内存。

## dev 服务器再次打不开（09:51）——本次为 OOM 进程退出，非卡死
- 现象：curl HTTP 000，且 `lsof -iTCP:3000 -sTCP:LISTEN` 无任何进程（与上午 09:22 的「LISTEN 但 HTTP 000 卡死」不同，本次是进程被彻底杀掉）。
- 内存：`vm_stat` 显示 Pages free ≈ 66MB、Pages wired down ≈ 2.3GB。Node 在启动阶段（next dev + webpack 拉起）即被 macOS OOM(jetsam) 杀掉，后台任务进程直接退出，端口始终起不来。
- 处理尝试：直接 `npm run dev:singleton` 后台重启 + 90 秒轮询，端口一直未监听 → 确认非重启可解，是整机物理内存不足。
- 结论：`top`/`ps` 在沙箱内受限读不到进程列表；需用户在「活动监视器」按内存排序关闭 Chrome/飞书/Cursor/Claude 等大户，把压力降到绿色、free≥1.5GB 后再启动。8GB 机器同时跑工作台+多重型应用本就吃紧，长期建议释放内存或分流重型应用。

## 10:57 再试重启仍失败——根因锁定为 macOS 压缩内存
- 用户选「重启机器」方案，但执行 `npm run dev:singleton` 后仍 60 秒无 LISTEN，启动即 OOM。
- `vm_stat`：Pages free≈61MB、Pages wired down≈1.6GB、Pages occupied by compressor≈3.56GB。wired 较上午(2.15GB)略降（疑似系统重启过），但 compressed 升至 3.56GB，free 仍触底。
- 结论：关应用 / 重启 dev server 都释放不掉 macOS 的压缩内存页，只有**系统级重启（苹果菜单→重启）**能清空 compressed+wired，让 free 回到数 GB，dev server 才能稳定拉起。已明确区分「重启机器」与「重启 dev server」，请用户系统重启后再让启动。
