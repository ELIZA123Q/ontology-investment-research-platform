# 研究员工作台持续优化 Goals

日期：2026-07-22  
状态：active  
总目标：让研究员从一个判断问题出发，以尽可能少的工程操作获得可核验、可反证、可继续跟踪的研究结论；本体与审计能力在后台发挥作用，不要求研究员理解内部对象和文件合同。

## 当前基线

- 项目定位、本体 3.0、01—05 阶段合同、方法资产、正式包与工作台导出边界清楚。
- 全项目规范、本体、V3 样例和 TypeScript 类型检查通过。
- Runtime 当前为 36 个测试文件、176 项测试全部通过；TypeScript 类型检查和生产构建通过。
- 首页、研究项目库、新建研究、结构、证据、判断、交付、历史和知识库均已实际走查。
- 当前强项是语义约束、证据上限、J0 正确停止、来源冻结和审计追溯；主要短板是研究员主线、运行状态一致性、长任务可恢复性与交付表达。

## Goal 1：先把系统事实显示正确

优先级：P0  
状态：completed（2026-07-22）  
目标：任何页面显示的状态、数量、版本和交付就绪结论，都与当前权威产物一致。

验收标准：

1. Runtime 全量测试、类型检查和构建通过。
2. 证据页只统计当前 Stage03 artifact/attempt，不混入历史版本、判断审阅或独立审阅工作项。
3. 运行状态、产物状态和工作台导出校验状态不再裸露英文枚举。
4. 来源变化的失效闭包有明确语义测试：来源 → 陈述 → 事实 → 评价/证据组合；不错误使稳定对象或判断单元失效。
5. UI 中“已完成”“可以交付”“正式发布”“工作台导出校验通过”四种含义保持分离。

## Goal 2：建立研究员默认主线

优先级：P0  
状态：in_progress  
目标：研究员不进入高级编辑、不阅读 YAML/JSON，也能从问题走到结论、边界和下一步。

验收标准：

1. 每个研究只有一个突出主动作：继续当前阶段、处理待审、补证或查看交付；同屏不出现多个同优先级入口。
2. 概览首屏在常见桌面高度内显示：当前结论、结论强度、最关键依据/缺口、下一步动作。
3. `JU/ER/EV/MA/RC` 等内部 ID 默认收进“审计详情”，主视图使用研究语言。
4. 结构页默认按“核心问题—关键判断—必要证据—反证/竞争解释”分层，不一次铺开完整关系图。
5. 研究项目库支持搜索、状态筛选、最近更新排序、归档；删除不是主要管理动作。
6. 用 3 个真实任务做可用性走查：首次使用者无需口头指导即可完成范围确认、结构审阅和证据处置。

## Goal 3：把证据台变成日常研究驾驶舱

优先级：P0  
状态：completed（2026-07-22）  
目标：研究员围绕“判断缺什么”工作，而不是围绕来源列表或系统对象工作。

验收标准：

1. 每个判断单元显示最低证据组合、当前覆盖、最薄弱环节、反证覆盖和可达到的最大 J。
2. 缺口按“阻断主判断 / 限制强度 / 仅补充”分级，默认先处理边际价值最高的 3 项。
3. 来源卡明确区分线索、已抓取正文、已核验引文、已形成 EvidenceFact 四个状态。
4. AI 可提出补证建议并执行公开来源取得，但任何事实进入判断前保留对象级人工确认。
5. 重复来源、同源转载和同一 source_group 不被误计为独立证据。
6. 证据更新能生成局部重算计划，并向研究员解释“哪些判断需要重看、为什么”。

验收证据：`source_coverage.test.ts` 覆盖未核验来源排除、同一 `source_group` 去重、反证缺口和来源四态前置条件；`evidence_review_assist.test.ts` 覆盖缺口优先级；`market_radar.test.ts` 与 `change_set.test.ts` 覆盖可达后代失效、局部 patch 边界和稳定对象不误失效。全量 34 个测试文件、172 项测试、类型检查和生产构建通过。

## Goal 4：让 AI 能持续、可恢复地执行

优先级：P0  
状态：in_progress  
目标：长时间取证与分阶段生成不依赖单个 HTTP 请求或单个 Next.js 进程存活，失败后可从检查点恢复。

验收标准：

1. 用持久化 job 表记录任务、阶段、状态、租约、心跳、重试次数、预算、输入 artifact/hash 和输出 artifact。
2. 独立 worker 领取任务；进程重启后，过期租约可安全回收，旧 worker 不能覆盖新结果。
3. 每个阶段支持 `queued/running/waiting_for_review/waiting_for_input/retrying/blocked/completed/cancelled`，并提供研究员可读原因。
4. 自动执行只跨越确定性步骤；范围确认、证据事实批准、判断批准和发布保持人工门。
5. 每个 run 有最大轮数、最大来源数、最大 token/金额、硬超时和停止规则；达到上限时生成缺口说明，不无限循环。
6. 支持“继续到下一个人工门”的一键运行，而不是要求研究员逐阶段点击生成。
7. 有故障注入测试覆盖：模型超时、网络失败、进程重启、重复投递、取消与租约竞争。

建议状态机：

```text
研究问题
  → 自动形成范围草稿
  → [人工确认范围]
  → 自动生成结构 + 结构自检
  → [人工确认结构]
  → 多轮取证/覆盖评估/停止规则
  → [人工确认事实与缺口]
  → 自动裁决 + 确定性规则 + 独立审阅
  → [人工确认判断]
  → 自动生成研究稿与审计索引
  → [人工确认交付]
```

## Goal 5：让本体成为“隐形能力”

优先级：P1  
状态：pending  
目标：本体用于消歧、补全、约束、关联和增量更新；研究员默认看到业务对象和可解释建议。

验收标准：

1. 知识库默认按研究任务展示相关子图，不加载完整对象/关系/规则网络。
2. 本体命中要解释“系统因此补了什么、限制了什么、关联了什么”，而不只显示类型节点。
3. `task_local` 候选有频次、跨任务复用、专家确认和晋升/驳回记录，形成可治理的本体缺口队列。
4. 相同对象、指标、时间口径可跨 run 对齐；不同口径必须显式提示不可直接比较。
5. 图谱查询服务于研究问题，例如“这条证据影响哪些判断”“这个变量在哪些研究中出现”，而不是只展示 ER 图。

## Goal 6：证明流程增益值得成本

优先级：P1  
状态：pending  
目标：不仅证明合同能跑，还证明研究员更快、更稳地得到可用判断。

验收标准：

1. 除 R/U/delta/S/C 外，记录研究员体验指标：首次可用结论时间、人工操作次数、返工次数、补证命中率和一次完成率。
2. 至少 8—12 个真实半导体任务覆盖成功判断、冲突停止、证据不足、增量改判和来源失效。
3. 补一个第二领域的小型压力测试，验证通用核心与领域扩展边界，不急于扩成全行业产品。
4. 与同证据直接生成基线比较时，同时报告研究质量增益和时间/调用成本。
5. 每个版本只推进能够改善研究员任务成功率或系统可信度的功能，避免以对象数、关系数或页面数作为成功指标。

## 执行顺序

1. Goal 1：恢复可信基线。
2. Goal 2 + Goal 3：打通研究员主线与证据驾驶舱。
3. Goal 4：引入持久任务队列和“运行到人工门”。
4. Goal 5：收敛本体展示，建设缺口治理闭环。
5. Goal 6：用真实任务验证增益，决定扩领域与产品化节奏。

## 每轮持续执行协议

每轮只领取一个可在当前代码状态下闭环的最小里程碑：先记录基线与目标指标，再实现，再运行相关测试和全量校验，最后更新本文件状态。遇到需要研究判断或会改变权威合同的分歧时停止自动推进，提交决策项；普通实现细节、可逆 UI 优化和测试补齐不阻断持续执行。
