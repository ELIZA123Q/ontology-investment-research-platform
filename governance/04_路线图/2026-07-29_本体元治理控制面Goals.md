# 2026-07-29 本体元治理控制面 Goals

状态：completed

## 一、目标决策

本项目不新增与语义结构域、判断推理域、证据域并列的第四个业务本体域。
本轮建立独立的本体元治理控制面，用机器合同管理资产权威、候选受理、变更影响、
实施验证、迁移和正式发布。治理记录只引用业务面，不进入投研业务实例图，
也不得作为商业判断的 `RuleEvaluation` 依据。

## 二、成功标准

1. 受治理核心资产具有唯一 `authority_ref`、责任角色、版本、状态、消费面和校验 Profile。
2. `task_local` 候选的“专家确认/登记晋升”与“正式发布”分离。
3. 正式变更必须依次经过影响分析、批准、实施、验证和发布，不允许越级。
4. `released` 必须满足目标 ID 可解析、必跑检查全部通过、发布指纹已绑定；破坏性变更另须迁移记录。
5. 治理对象和治理规则不得进入正式本体模型注册表或商业判断规则引用。
6. 历史研究结论不得被本体变更静默改写，只能进入影响、迁移、重算或历史只读状态。

## 四、明确不做

1. 不在 `ontology/01_通用/model_registry.yaml` 注册治理模型。
2. 不把审批、权限、Stage 状态、发布状态编码成投研业务对象。
3. 不允许治理检查支撑或提高商业判断等级。
4. 不由候选队列自动修改正式本体 YAML。
5. 不因本体升级覆盖历史运行产物。

## 五、发布门

```text
task_local 候选
  → 专家确认
  → 变更提案 proposed
  → 影响冻结 impact_assessed
  → 批准 approved
  → 实施 implemented
  → 验证 validated
  → 正式发布 released
```

`promoted` 作为历史兼容候选状态，只表示已创建变更提案，不表示已经进入正式本体基线。

## 六、实际实现

- 数据库 v14 新增 `ontology_change_requests` 和 `ontology_change_request_events`；
  历史 `promoted` 记录只回投影为 `proposed`，不会伪装成 `released`。
- Runtime 状态机直接读取 `governance_control_contract.yaml`，避免另建一套迁移顺序；
  非法越级、缺影响快照、缺实现引用、检查未通过、目标未解析、指纹不一致和破坏性变更缺迁移均会阻断。
- 候选治理 API 在登记 `promoted` 时创建正式变更提案；独立变更 API 负责后续状态推进，
  变更当前状态和每次决定分别保存，历史追加不可覆盖。
- 本体治理页将历史 `promoted` 展示为“变更已受理”，另行展示正式变更状态；
  只有 `change_request.status=released` 才计入“已正式发布”。
- 项目总校验已接入元治理控制面正向检查和六项负向回归。
