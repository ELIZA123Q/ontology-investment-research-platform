# 00_项目定位与边界

> 本文件是全项目上位约束。任何下游规范、知识库、本体与运行时文档与本文件冲突时，以本文件为准。

## 0. 上位总纲（三段式）

**一、项目是什么**

本项目是一个**本体约束的投研判断工作台**：以本体提供语义与约束、以证据与确定性计算提供事实基础、以 LLM 完成受约束判断。它把研究问题转化为判断结构，围绕每个判断单元准备证据，由 AI 运行时应用方法规则完成裁决，并将过程和结果保存为可追溯的判断实例。

三层公式：

> 可靠判断 = 确定性计算（取证与统计） + 语义与约束（本体） + 受约束的开放推理（LLM）

主链是：

> 研究问题 → 判断结构 → 证据集合 → 运行时裁决 → 判断实例 → 用户表达

阶段分工：`02` 搭结构，`03` 备事实与计算，`04` 做判断；本体贯穿三者，但不替代任一阶段。

**二、本体做什么、不做什么**

本体是**投研任务运行时的语义与约束基础设施**，不是「专业词典」，也不是自动推理引擎。它至少承担四个作用：

| 作用 | 含义 | 落点 |
|------|------|------|
| 统一概念 | Event、StateChange、StateVariable、EvidenceClaim、Judgment、AssetImpact 等口径一致 | `ontology/01_通用` |
| 限定关系 | 事件影响哪些状态变量、状态如何关联产业链对象、证据支持哪个判断 | 本体关系 + 任务视图 |
| 约束输入输出 | 阶段判断须有时间区间；影响判断须明确对象、方向与传导路径 | 阶段 schema + 正式规则 |
| 帮助 Runtime 选上下文 | 按任务切本体切片与方法子集，而不是把全部本体与知识库塞给模型 | `runtime/` 语义路由与上下文装配 |

这里的“基础设施”还意味着：研究流程、方法资产、数据映射、知识资产和运行结果必须引用同一批稳定语义 ID，并通过本体对象与关系完成跨模块交接；不得在 Runtime Schema、UI 或阶段模板中平行维护另一套同义业务类型和值域。执行要求见 [`01_本体统一语义基础设施契约.md`](./01_本体统一语义基础设施契约.md)。

它**不**负责替代 AI 执行研究，也**不**预先规定每次任务必须采用的完整推理路径，更**不**穷举现实世界因果规则。真正的推理发生在 04 与 `runtime/` 面对本次证据裁决时，而不是本体 YAML 自动推出结论。

**三、项目怎样证明价值**

项目通过分层对打评测（普通单次 Prompt → 分阶段无本体 → 分阶段+本体 → 全栈方法与证据约束）评估：术语与口径漂移、数字与来源错误、判断结构完整度、竞争解释覆盖、结论与证据匹配、运行稳定性与返工定位。只有这些能力得到验证，才进一步扩展行业范围和产品形态。细节见 `evaluation/`。

**应停止使用的表述**（避免外部按「本体自动推理」误解本项目）：

1. 「本体自动完成投研推理」。
2. 「把研究员的思维全部编码成本体」。
3. 「只要本体足够完整，AI 就能得到正确结论」。
4. 「01—05 就是本体推理链」。
5. 「所有规则、流程和知识库都属于本体」。
6. 「本体驱动投研推理系统」（易被读成本体在推理；应使用「本体约束的投研判断工作台」）。

## 1. 项目定位

本项目是一套**本体约束的投研判断工作台**：帮你把问题收成可核对、可反证、可复盘的判断。

你提出事件、变量、材料线索或投资假设；系统按统一口径整理对象与关系，按可复用方法拆解、取证和裁决；本次选了什么方法、用了什么证据、得出什么结论，都会留痕。

不以从零批量生成选题为主。还没形成明确判断时，可以先把观察收成可验证问题；只有落到具体对象、关键变量、证据要求和反面证据检查，才进入 01—05。

重点回答：

> 一个投研判断为什么成立，证据是否充分，是否存在反面证据，结论应说到什么强度，以及后续如何复盘。

---

## 2. 项目要解决的问题

1. **把问题变成可执行任务** — 收敛为对象、范围、关键变量、证据要求和反面证据条件明确的判断任务。
2. **统一语义和分析口径** — 用本体统一核心概念，用分析框架组织常见判断机制。
3. **让证据准备和推理过程可检查** — 材料归一为可追溯实例，再逐段验证支持、削弱、失效条件与竞争解释。
4. **让每次判断可留痕、可复盘** — 区分「本体没有定义」「本次实例缺失」和「现有证据不足」。
5. **保留可复用的方法信息** — 区分稳定分析方法与本次事实、结论。

---

## 3. 本项目不做什么

1. 不替研究员从零批量生成选题，也不凭空创造投资判断。
2. 不做通用行情或资讯查询；材料是证据来源，不是最终交付。
3. 不输出直接买卖建议或确定性价格预测。
4. 不追求全行业、全公司、全历史的知识库覆盖；以最小充分范围为原则。
5. 不把单次结果直接等同于稳定方法、本体或 Skill。
6. 不复用旧事实和旧结论代替重新判断；可复用结构与规则，但每次必须刷新实例和证据。
7. 不处理内幕或未授权信息。

不能直接进入流程的问题：纯事实查询、直接交易问题、确定性预测、过大过泛无法落到对象与反证的问题。系统应拒绝、降级或改写（例如将「能不能买」改写为「公开证据是否支持进一步研究价值」）。

## 4. 适用问题范围

当前服务于**投研判断推理型问题**，以及能被收敛为此类问题的事件观察、材料线索或初步想法。

| 主任务类型 | 示例 |
|------------|------|
| 状态与趋势判断 | 未来 6—12 个月，存储芯片供需是否会改善？ |
| 事件或变化影响判断 | InP 出口管制是否会影响相关材料、产品或公司？ |
| 传导路径判断 | InP 供应受限是否会传导到光芯片、光模块及相关公司？ |
| 假设验证与更新判断 | “AI 光模块高景气将持续支撑中际旭创业绩”是否仍成立？ |

证据更新与历史复盘都需落到上述某一主类型。本体缺口发现是附带诊断，不是独立任务类型。

## 6. 两类结果

| 结果类型 | 回答的问题 | 主要内容 |
|----------|------------|----------|
| 任务判断结果 | 本次问题得到什么判断？ | 本次对象、实例、证据、路径状态、结论、限制和留痕 |
| 分析方法信息 | 这类问题通常应该怎样分析？ | 问题拆解、分析顺序、关键变量、证据要求、反面证据方向和适用边界 |

历史事实和历史结论不能直接代替下一次判断。沉淀与版本化机制不在本总纲规定。

## 7. 核心资产分层（五层）

项目按五层职责组织，层间可引用，职责不重复：

| 层 | 目录 | 回答的问题 | 不应保存 |
|----|------|------------|----------|
| 语义本体 | `ontology/` | 有哪些稳定对象、关系、状态与约束型规则？ | 单次观测、来源说法、任务结论；取证与裁决方法正文 |
| 方法资产 | `methods/`（02/03/04） | 这类问题可以怎样判断、需要什么证据、证据够了能裁到哪？ | 本次证据状态与最终观点 |
| AI 运行时 | `runtime/` | 本次任务怎样编排、选方法、绑证据、应用规则？ | 平行的公共合同或本体 |
| 运行实例 | `instances/` | 本次实际做了什么、用了哪些证据、得出什么判断？ | 被当成长期有效的方法或事实 |
| 表达交付 | `delivery/` + 05 | 不同用户怎样读结果？ | 新事实、新判断 |

上位约束（`governance/`）与阶段合同（`workflow/`）不属于上述五层业务资产，是它们的治理框架与执行边界。成熟稳定流程可沉淀为 Skill，属方法资产附属，不与五层并列。

**推理在哪里发生**：真正的裁决发生在 04 与 `runtime/` 面对本次证据时，不是本体或方法 YAML 自动推出结论。

**规则怎样被使用**：区分设计态与运行态——设计态规则（本体的语义/约束、`methods/` 的方法定义）声明「何时可以这样判断、何时不能」；运行态是本次实际选用与应用后写入 `instances/` 的规则评价（`RuleEvaluation`）。设计态不预置本次结论。

三库边界：**02 声明可以怎样组织判断，03 声明什么证据可以用，04 声明证据可以怎样裁决。** `methods/` 只登记能力、适用条件和候选关系；合法路由值域由公共合同约束；本次具体选择由 `runtime/engine/` 完成并写入 `instances/`。正式本体、任务视图与本次记录的分工见 [`ontology/01_通用/00_投研本体框架概述.md`](../../ontology/01_通用/00_投研本体框架概述.md) 与 02 规范；关键判断编号在 02 创建并由下游原样继承。

## 8. 方法论有效性原则

1. **问题可判断** — 落到对象、范围、关键变量与可支持/推翻的信息。
2. **逻辑可解释** — 说明变量如何变化、影响如何传导。
3. **证据可对应** — 每项关键判断有证据要求；不足时保留未知。
4. **变量不断链** — 02 选中的变量在 03/04 得到交代，不静默消失。
5. **结论有边界** — 说明范围、强度、限制、失效条件与跟踪信号。
6. **方法与事实分离** — 可复用结构 vs 本次时点事实与结论。
7. **产出可交付** — 未达高质量只能作草稿、返工或缺口说明。
8. **规范不膨胀** — 核心规范固定为 00、00A、01—05；新对象进本体，新结构进模板，成熟流程进 Skill。

## 9. 文档职责与表达原则

### 9.1 四类文档各自保存什么

| 文档类型 | 应保存 | 不应保存 |
|---|---|---|
| 阶段规范 | 输入、顺序、交付物、质量与退回、上下游交接 | 某类问题的完整方法、来源大全、当期事实 |
| 方法资产（`methods/`） | 可复用的拆解、变量、路径、证据组合、判断方法 | 阶段流程复述、单次状态与结论 |
| 正式本体 | 稳定定义、类型、关系、约束与机器标识 | 写作教程、来源清单、临时观点；取证与裁决方法正文 |
| 单次产物 | 本次范围、数据、证据、判断、限制与审计 | 被默认当作长期有效的方法或事实 |

同一规则只保留一个权威出处，其他文件只链接。机器枚举与值域以 YAML / CSV schema / registry 为准；Markdown 解释业务含义，不平行维护另一套机器合同。

### 9.2 三个知识库怎样分工

- **methods/02_判断结构**：一类问题通常判断什么、怎样拆解。
- **methods/03_取证**：需要哪些证据组合、来源与停止规则。
- **methods/04_裁决**：合格证据怎样形成、削弱、阻断或修改判断。

各库以 `README.md` 为唯一入口。

### 9.3 研究员正文与系统记录

正文让不读 YAML 的读者理解问题、依据、边界与跟踪；优先用业务语言（关键判断、待验证观点、必要证据组合、证据能支持的结论强度、改判信号）。

系统对象名、状态码、内部 ID、路径编号与机器字段留在 YAML / CSV / 审计中。正文不得用「门禁」「放行」「证据篮子」「取证配方」「使用上限」「强绑定」「硬桥接」「阶段包」「本体同源」「机器事实」「派生矩阵」等工程化表达替代研究语言。

写法：先判断再依据与限制；事实、来源观点、推论与未决分开；一句一层因果；表格用于比较不重复正文；流程状态不能代替研究结论。
