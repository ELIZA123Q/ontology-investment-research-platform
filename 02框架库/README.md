# 02 框架库使用说明

## 1. 定位

本目录为 02 提供可复用的分析参考。框架回答“一类问题通常有哪些机制、变量、证据、竞争解释和阻断条件”，用于帮助研究者更快搭建并检查本次研究逻辑，但不代替独立判断。

02 应先根据 01 的研究需求识别真正需要辨别的核心矛盾，再参考本目录检查遗漏、补充视角，最后形成属于当前任务的研究框架并映射正式本体。库中框架不是现实事实、正式本体、研究结论或必须照填的报告模板。

```text
01 研究需求
→ 识别核心矛盾并独立搭建基本问题树
→ 查找基础框架和行业框架补充机制、证据与反证
→ 按本次对象、范围和时间裁剪组合
→ 匹配正式本体并形成任务本体视图
→ 03 准备现实实例、观测和证据
```

基础框架的固定结构、证据等级、本体映射和验收要求见[基础框架编写与验收标准](基础框架库/00_基础框架编写与验收标准.md)。半导体行业的主框架、场景卡、调用规则与治理见[半导体行业框架库](行业框架库/半导体行业/README.md)和[总纲与治理规则](行业框架库/半导体行业/00_半导体行业框架库总纲与治理规则.md)。

| 涨价能否持续 | BF-PC-01 | BF-SD-01、BF-EE-01 | 报价等同成交和公司实现价 |

| 冲击如何跨产业链传导 | BF-VT-01 | BF-SD-01、BF-RS-01 | 概念邻近当稳定供应关系 |
| 公司靠什么挣钱 | BF-BM-01 | BF-IC-01、BF-FQ-01 | 收入增长不检查单位经济和现金 |

## 6. 使用方法

### 6.1 先独立形成核心矛盾

根据当前问题建立基本问题树，说明前置条件、并列问题、竞争解释和停止节点。不要从标题或关键词直接套框架。

### 6.2 再用框架检查遗漏

重点检查：对象和口径是否一致；状态变量是否可观察；是否跳过商业化、履约或财务环节；是否缺少业务时间、竞争解释、阻断条件和下一验证点。

### 6.3 按任务边界裁剪组合

只保留能影响本次判断的模块。框架库不能扩大 01 已确定的对象、时间、地域和产业链范围，也不能为追求完整而编造变量或信号。

### 6.4 最后匹配本体

先查一级通用本体，再查领域本体。正式定义、领域扩展和任务候选必须分开记录。框架中列出的候选变量不会自动成为正式 `StateVariable`。

## 7. 最小使用记录

研究逻辑只需记录：

- 本次研究的核心矛盾和独立形成的问题树；
- 参考了哪些基础或行业框架；
- 框架补充、纠正或排除了什么；
- 最终结构为何与参考框架不同；
- 哪些路径因证据、本体或边界不足被降级或停止。

## 9. 质量边界

框架使用后的最终研究逻辑必须满足：对象可识别、变量可观察、传导可解释、证据可追溯、反证可执行、时间可复盘、本体层级不混淆。任何框架都不得替代研究员确认、证据准备、正式本体校验和后续复盘。

## 10. 自动校验

在项目根目录运行：

```bash
python3 02框架库/validate_frameworks.py
```

脚本只读检查正式框架 ID、场景卡 ID、front matter、框架十一段/场景卡九段结构、`builds_on` 与推荐主框架引用、内部链接、行业权威来源、本体标识符，以及半导体“两横六纵 + 10 张场景卡”覆盖，不修改任何文件。
