## 1. 输入解析字段

### 1.1 字段结构

`input_resolution` 说明系统如何在不伪造用户确认的前提下，确定 01 已经可以进入 02。

```yaml
input_resolution:
  mode: direct_extract | inherited_context | user_clarified
  status: resolved
  source_refs:
    - "<当前输入、任务 ID、需求版本或历史运行引用>"
  system_understanding:
    core_object: "<主判断对象>"
    judgment_action: "<主要判断动作>"
    time_window: "<判断时点和观察窗口>"
    scope_boundary: "<地域、产业链、对象和不研究事项>"
    delivery_landing: "<用途、报告原型和拆分粒度>"
  rollback_assumptions:
    - assumption: "<系统采用的非结构性假设>"
      basis: "<为什么可以暂时这样处理>"
      rollback_trigger: "<什么情况出现时重新解析或退回 01>"
  clarifications:
    - question_id: "<真实问答编号>"
      topic: "<澄清主题>"
      question: "<真实提出的问题>"
      answer: "<用户真实回答>"
      answered_at: "<ISO 8601，含时区>"
  unresolved_structural_ambiguities: []
```

正式通过版必须满足：

- `status=resolved`；
- `source_refs` 非空；
- `system_understanding` 五项完整；
- `unresolved_structural_ambiguities=[]`；
- `user_clarified` 模式至少有一条真实 `clarifications`；
- 未发生问答时 `clarifications=[]`，不得为了凑字段补写问答。

### 1.2 直接提取示例

适用于用户已经一次性说明对象、时间、范围、用途和交付的情况。

```yaml
input_resolution:
  mode: direct_extract
  status: resolved
  source_refs:
    - current_user_input
  system_understanding:
    core_object: "全球存储芯片中的 HBM、非 HBM DRAM 与 NAND"
    judgment_action: "判断当前周期阶段及未来 6—24 个月的切换条件"
    time_window: "以每次运行的数据截止时点为当前锚点，前瞻 6—24 个月"
    scope_boundary: "全球供需与价格周期；不做单公司估值和交易建议"
    delivery_landing: "行业周期判断，用于行业跟踪和假设更新"
  rollback_assumptions: []
  clarifications: []
  unresolved_structural_ambiguities: []
```

此模式应展示系统理解后直接进入 02，不要求用户再次回答“对象是什么、时间是什么、交付是什么”。

### 1.3 继承上下文示例

适用于批量、回放、定期更新或已有任务增量运行。

```yaml
input_resolution:
  mode: inherited_context
  status: resolved
  source_refs:
    - "task_id: TASK-MEM-CYCLE"
    - "requirement_version: 3"
    - "current_run_delta: 更新截至本期的数据与判断"
  system_understanding:
    core_object: "继承需求版本 3 的存储产品范围"
    judgment_action: "更新周期状态与原假设"
    time_window: "按本次数据截止时点滚动解析"
    scope_boundary: "继承版本 3；本轮没有新增地域或对象"
    delivery_landing: "行业周期判断的定期更新"
  rollback_assumptions:
    - assumption: "未明示变更的任务边界继续沿用版本 3"
      basis: "本轮只要求更新数据和判断"
      rollback_trigger: "本轮材料显示对象、主通道或用途已经改变"
  clarifications: []
  unresolved_structural_ambiguities: []
```

### 1.4 真实澄清示例

适用于“某政策对半导体有什么影响”这类会因主通道不同而形成不同结构的问题。

```yaml
input_resolution:
  mode: user_clarified
  status: resolved
  source_refs:
    - current_user_input
    - current_dialogue
  system_understanding:
    core_object: "中国半导体设备厂商"
    judgment_action: "判断美国管制变化对国产设备替代节奏的影响"
    time_window: "当前有效规则与未来 12—24 个月"
    scope_boundary: "优先验证设备验证和订单通道；不展开二级市场情绪"
    delivery_landing: "主题深度研究，用于更新国产替代假设"
  rollback_assumptions: []
  clarifications:
    - question_id: CL-01
      topic: primary_channel
      question: "本次优先判断市场情绪，还是设备验证与订单的实质传导？"
      answer: "优先看设备验证和订单，不讨论短期股价。"
      answered_at: "2026-07-13T10:00:00+08:00"
  unresolved_structural_ambiguities: []
```

## 2. 运行场景

| 场景 | 默认解析方式 | 必须检查 | 不应做 |
|---|---|---|---|
| 一次性完整输入 | `direct_extract` | 核心字段是否完整、是否互相冲突 | 重复询问用户已经说清的事项 |
| 批量任务 | `inherited_context` 或每条 `direct_extract` | 每条任务是否有独立边界；批次参数是否真的适用于全部对象 | 用统一批处理话术冒充每条任务的用户回答 |
| 历史回放 | `inherited_context` | 当时信息截止边界、原判断对象和原任务版本 | 把后见事实混入当时输入 |
| 定期更新 | `inherited_context` | 既有需求是否仍有效；滚动时间和动态对象是否需要刷新 | 每次机械重复三问 |
| 增量运行 | `inherited_context` | 本轮变更是否触及主对象、主通道、关键范围或交付 | 静默覆盖既有需求或把增量任务扩成全量重做 |
| 新问题且有歧义 | `user_clarified` | 哪一个问题最能消除结构性歧义 | 一次抛出固定问题清单 |

### 2.1 批量任务

批量任务可以共享清楚声明的批次级范围、时间和交付要求，但每个子任务仍需独立记录对象和规范化问题。若批次中不同对象需要不同判断结构，应拆成不同任务组。

### 2.2 历史回放

至少记录：原任务或原判断引用、历史截止时点、当时可用信息边界、回放目的，以及是否只复现原判断还是同时做事后验证。事后事实只能进入复盘结果，不能反向改写原始 01。

### 2.3 定期更新

定期更新继承稳定的需求说明，由本次运行刷新实际数据截止时点、动态对象和证据范围。若核心对象、主通道或交付用途没有变化，无需重新受理；若发生变化，创建新需求版本并重新执行结构性歧义检查。

### 2.4 增量运行

增量运行记录“继承项、变更项、变更来源、是否改变结构”。只有结构性变更才触发追问或新版本；新增材料、数据或证据通常由 03 处理，不应被误判为 01 未确认。

## 3. 核心任务字段

### 3.1 核心研究主线

`main_judgment_axis` 至少包括：

```yaml
main_judgment_axis:
  object: "<主判断对象>"
  comparison_scope: "<比较对象；无比较时写「无比较」>"
  judgment_action: "<状态、趋势、阶段、影响、路径或假设更新>"
  primary_channel: "<本次唯一主通道>"
  key_question: "<最需要回答的可验证、可反证问题>"
  expected_05_landing: "<05 最终应形成的判断表达>"
  non_core_axes:
    - "<辅助观察、不研究或另立任务的方向>"
```

`schema_version: "1.4.0"` 起 `comparison_scope` 为必填。机制、分化等可作为意图提示写入正文「结论粒度」，不另设强制 `judgment_landing` 枚举。

### 3.2 时间口径与交付深度

`schema_version: "1.4.0"` 起必须填写：

```yaml
time_scope:
  lookback: "<回看期；不适用则写「不适用：…」>"
  as_of: "<当前判断时点锚点及刷新口径>"
  forward: "<前瞻期；不适用则写「不适用：…」>"
delivery_depth:
  conclusion_granularity: "<结论说到什么粒度即可>"
  minimum_delivery: "<最低交付要求：至少交出什么即可停>"
```

不适用项不得留空；须写「不适用」及简短原因。`delivery_depth` 只约束做到什么程度，不得写成 02 路径节点或 04 结论。

### 3.3 范围过宽检查

`overscope_check.status` 取值：

- `pass`：已收敛，可进入 02；
- `needs_clarification`：需要用户选择主线；
- `split_required`：必须拆成多个 01 任务；
- `out_of_scope`：无法改写为本流程可承接的判断任务。

正式通过版（`stage_status=complete` 且 `task_disposition=accepted`）只能使用 `pass`。若检查结果为 `needs_clarification` / `split_required` / `out_of_scope`，应写入对应的 `task_disposition`，不得伪装成 `accepted`。

### 3.4 研究价值检查

至少记录：

- `disagreement_or_unknown`：本次要区分的分歧或关键未知；
- `changing_variable`：正在变化或进入验证窗口的变量；
- `asset_or_decision_impact_path`：如何连接行业、公司、资产或研究动作；
- `decision_use`：结果将改变什么；
- `why_now`：为什么在本窗口研究；
- `incremental_question`：相对已有认识新增回答什么。

正式通过版要求 `status=pass` 且 `value_level` 为 `high` 或 `medium`。

### 3.5 任务处置

`task_disposition` 与全局 `stage_status` 分开填写：

| `task_disposition` | 典型 `stage_status` | 含义 |
|---|---|---|
| `accepted` | `complete` | 《投研需求说明》成立，可进入 02 |
| `needs_clarification` | `blocked` | 存在结构性歧义，先追问 |
| `out_of_scope` | `complete` | 不在本流程范围，输出不予受理说明 |
| `split_required` | `blocked`（或正式拆题说明时用 `complete`） | 须拆成多个 01 |

`overscope_check.status` 中的同名枚举是检查过程结果；只有收敛后的最终处置写入 `task_disposition`。

### 3.6 观察维度、初步线索与前提三分

观察维度使用业务语言，例如需求、订单、库存、产能、价格、成本、毛利率、交期、资本开支、市场预期、竞争格局、国产替代和技术替代。只保留能区分不同解释的维度，不做指标堆砌。

初步线索至少覆盖：支持方向、削弱方向、反面情形和其他可能解释。它们只是研究需求，不是 02 的正式路径、03 的证据规则或 04 的结论。

正文「前提与假设」按三类记录：

| 类型 | 含义 |
|---|---|
| 已知事实 | 用户给定或继承前提；01 不核验，不得写成 03 已证实 |
| 用户假设 | 用户明确采用、尚未被本任务验证的立场或边界 |
| 待验证假设 | 本次需要支持、削弱或反证的命题 |

系统非结构性默认继续放在 `rollback_assumptions`，不得记入用户假设。

## 4. 改写与收敛示例

### 4.1 状态与趋势问题

原始输入：

```text
存储芯片目前处于什么周期，本轮周期什么时候结束？
```

不合格改写：

```text
研究存储芯片行业周期变化。
```

可用改写：

```text
截至每次运行的数据截止时点，全球存储芯片中 HBM、非 HBM DRAM 与 NAND 分别处于什么供需与价格周期阶段；未来 6—24 个月内，哪些需求、库存、有效供给、价格和产能信号将支持周期延续，或表明周期转入见顶、正常化或下行？
```

### 4.2 未经验证的事实前提

原始输入：

```text
近半年 HBM 已经上涨，原因是什么？
```

可用改写：

```text
近半年是否存在具有代表性的 HBM 价格上涨；若存在，其主要驱动来自 AI 需求、供给约束、客户提前采购、产品结构变化，还是其他因素？
```

### 4.3 过宽事件问题

原始输入：

```text
某地缘谈判对半导体产业有什么影响？
```

不能直接整理成“全球半导体全链综合影响”。应先判断是否能从输入中提取唯一主线；不能时只问主线选择。收敛后可形成：

```text
谈判缓和是否已经构成半导体材料与制造实物流压力缓解的信号，还是影响主要停留在市场情绪定价层面？
```

不研究事项可写：长期制裁制度变化、单公司业绩测算、全板块统一股价判断。

## 5. 动态范围

| 原始表达 | 01 的处理 | 不应处理 |
|---|---|---|
| 当前 | 以每次运行的数据截止时点为锚点 | 固化为文档生成日 |
| 近半年 | 按运行日前最近六个月或最近两个季度滚动解析 | 固化为某一次绝对区间 |
| 代表性公司 | 写明选择口径和刷新规则 | 写死一次性名单且不说明口径 |
| 最新公告 | 写明后续运行需重新识别最新有效公告 | 只引用当前看到的一份公告 |
| 历史时点 | 写明当时信息截止边界 | 使用回放时才知道的后见事实 |

## 6. 交付原型

| `delivery_archetype.primary` | 适用问题 |
|---|---|
| `event_commentary` | 事件、政策、公告或产业消息的影响 |
| `industry_dynamic_commentary` | 行业数据、业绩会或多家公司信息反映的变化 |
| `industry_cycle_report` | 周期状态、拐点和切换条件 |
| `company_earnings_commentary` | 财报、指引、订单或经营更新 |
| `theme_deep_dive` | 技术、赛道、制度或产业趋势的深度研究 |

若用户没有指定报告类型，可以按核心问题推荐一个原型并标记为可回滚假设。只有当原型选择会改变范围、对象拆分或正文落点时才追问。

## 7. 常见输入处理

| 输入 | 处理方式 |
|---|---|
| 明确判断问题 | 直接提取并检查质量门槛 |
| 行业状态问题 | 收敛为状态与趋势判断 |
| 事件或政策线索 | 收敛为影响判断；涉及多段机制时考虑路径判断 |
| 新公告、新数据、新材料 | 通常作为已有假设的增量更新；边界不变时继承原任务 |
| “这个逻辑还成立吗” | 收敛为假设验证与更新判断 |
| “当时判断对不对” | 明确历史信息边界和原主任务类型 |
| 纯资料总结 | 只有用于更新或验证判断时才进入本流程 |
| 纯行情查询或文本润色 | 转交其他流程 |
| 直接买卖建议 | 尝试改写为具体投资假设；仍不具体则澄清或不予受理 |
| 问题过大 | 收窄、拆题或追问核心主线；无法收敛则不予受理 |

## 8. 版本兼容

01 需求说明当前正式版本为 `schema_version: "1.4.0"`：在 1.3.0 条件触发 `input_resolution` 与 `task_disposition` 基础上，新增必填 `main_judgment_axis.comparison_scope`、`time_scope`、`delivery_depth`，并以规范第 2.3 节完整性总判据作为进入 02 的语义标准。正文「前提与假设」须区分已知事实、用户假设与待验证假设。

历史版本继续可校验：

- `1.3.0` / `1.2.0`：使用 `input_resolution`；不强制新三组字段；
- `1.1.0`：使用 `user_confirmation` 三项问答结构。

正式通过版均须 `task_disposition=accepted`。新运行不得继续以 1.1.0 的三问结构作为强制准入门，也不得跳过 1.4.0 的比较范围、时间三件套与交付深度。

不予受理说明使用 `schema_version: "1.1.0"`：`stage_status=complete`，`task_disposition` 为 `out_of_scope` 或 `split_required`。
