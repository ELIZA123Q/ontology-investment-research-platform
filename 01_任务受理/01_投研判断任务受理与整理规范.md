# 01_投研判断任务受理与整理规范

## 1. 文档定位

本文档规范 01 阶段如何把研究员提出的问题、事件观察、材料线索、数据变化或已有任务增量，整理成可以进入 02 的投研判断任务。

01 的目标是形成一份边界清楚、可验证、可反证、可重复执行的《投研需求说明》。01 只解决“要研究什么”，不提前解决“本体如何表达、证据是否充分、结论是什么”。

`stage_status=complete`（阶段完成）只表示 01 阶段工作已结束；只有同时 `task_disposition=accepted`（予以受理）才表示《投研需求说明》可进入 02。二者都不代表本体一定能够承接、证据已经充分或判断已经成立。正式发布还必须满足本规范第 7 章和 [`../00_全局/00A_高质量产出判别标准.md`](../00_全局/00A_高质量产出判别标准.md)。

详细字段、运行场景和改写示例见 [`01_附录1_任务受理字段与场景参考.md`](01_附录1_任务受理字段与场景参考.md)；正式文件结构以 [`模板/01_投研需求说明模板.md`](模板/01_投研需求说明模板.md) 为准。

---

## 2. 阶段边界与可否进入下一步

### 2.1 01 负责什么

01 负责：

1. 保留原始输入并识别本次研究意图；
2. 把输入收敛为一个核心判断问题和一条核心研究主线；
3. 按第 2.3 节完整性总判据，明确对象与比较范围、时间三件套、用途、排除范围、前提三分、结论粒度和 05 交付落点；
4. 区分已知事实、用户假设、待验证假设、继承上下文、系统整理和可回滚假设；
5. 判断是否存在会改变任务结构的歧义；
6. 检查研究价值、范围是否过宽以及是否可以交给 02；
7. 记录返工原因和下一步需要补充的关键信息。

01 不读取、不引用也不校验本体文件，不查询事实数据，不设计正式判断路径、证据规则或推理结论。02 发现本体不能承接已经明确的需求时，应记录本体候选或缺口，不得要求用户为了适配本体而改变真实意图。

### 2.2 可受理任务

每项任务只设置一个主类型：

| 主类型 | 需要回答的问题 |
|---|---|
| 状态与趋势判断 | 当前处于什么状态，未来可能如何变化 |
| 事件或变化影响判断 | 某事件、政策、公告或数据变化是否影响目标对象 |
| 传导路径判断 | 某项变化是否通过特定通道传导 |
| 假设验证与更新判断 | 已有判断或投资假设是否仍成立、需要如何更新 |

事件观察、材料线索、证据更新、定期跟踪、增量运行和历史复盘都可以作为输入形态，但必须落到上述主类型之一。

纯事实查询、资料罗列、文本处理、无条件价格预测、直接交易建议、未授权信息请求，以及无法改写为可验证、可反证判断的问题，不进入 01—04 流程。

### 2.3 完整性总判据（对 02 可执行）

一份投研需求是否完整，**不取决于字段是否全部填写**，而取决于它是否足以让 02 在以下约束下形成可执行的判断结构：

1. **不擅自改变研究问题**；
2. **不擅自扩大边界**；
3. **不擅自补充核心假设**。

具体来说，进入 02 的 01 至少应让 02 能够确定下表内容。缺任一项且不同补法会改变任务结构时，不得记为完整受理。

| 02 需要确定的内容 | 01 应提供的信息 | 执行口径 |
|---|---|---|
| 本次到底判断什么 | 核心判断问题 | 必须 |
| 判断谁、比较谁 | 对象范围与比较对象 | 必须写清比较对象；无比较时显式写「无比较」 |
| 判断哪个时间段 | 回看期、当前时点、前瞻期 | 按任务适用填写；不适用项写「不适用」并说明原因，不得留空含糊 |
| 结论用于什么决策 | 使用场景与决策目的 | 必须 |
| 应输出哪种判断 | 状态、趋势、阶段、影响、路径、假设更新等 | 以 `judgment_landing` / 主任务类型为准；机制、分化等可作为意图提示，不另设强制落点枚举 |
| 哪些内容不研究 | 明确排除范围 | 必须 |
| 哪些只是前提 | 已知事实、用户假设、待验证假设 | 必须三分；「已知事实」仅指用户给定或继承前提，不得冒充 03 已核验事实 |
| 判断做到什么程度即可 | 结论粒度与最低交付要求 | 必须；只约束做到什么程度即可停，不写成 02 路径或 04 结论 |

### 2.4 可否进入 02

进入 02 前必须同时满足：

1. **意图真实**：不得偷换用户问题，不得把系统推断写成用户确认；
2. **主线单一**：明确一个主对象、一个判断动作、一个主要通道和一个核心待验证问题；
3. **按 2.3 完整**：上表信息足以让 02 搭结构，且不会迫使 02 自行改问题、扩边界或补核心假设；
4. **可验证、可反证**：问题不预设答案，并保留支持、削弱、反证和竞争解释方向；
5. **有研究价值**：存在可辨别的分歧或未知、正在变化的变量、影响路径和决策时效；
6. **无结构性歧义**：不存在会改变主对象、主类型、主通道、关键范围或交付落点的未决问题；
7. **可重复执行**：相对时间和动态对象保留刷新口径，不固化为某一次运行结果。

## 3. 条件触发的输入解析与交互

### 3.1 基本决策规则

01 不把固定问答次数作为可否进入下一步的条件。按以下顺序处理：

```text
读取当前输入、有效历史上下文和已有需求说明
↓
提取核心字段并检查冲突
├─ 信息足够且无结构性歧义
│  → 展示系统理解、信息来源和可回滚假设
│  → 生成 stage_status=complete、task_disposition=accepted 的 01，进入 02
└─ 存在会改变任务结构的歧义
   → stage_status=blocked、task_disposition=needs_clarification
   → 只追问当前最关键的问题
   → 获得真实回答后重新检查
```

“展示”指在对话或正式 01 本阶段输出的“输入解析与系统理解”中清楚呈现，不要求用户再次复述或点击确认。用户若未提出异议，不得反向记为“用户已确认”；系统理解仍应标记为系统提取或继承上下文。

### 3.2 三种合法解析模式

| 模式 | 适用情况 | 是否必须发问 |
|---|---|---:|
| `direct_extract` | 当前输入已经说明对象、时间、范围、用途和交付 | 否 |
| `inherited_context` | 批量、回放、定期更新或增量运行可以继承有效需求说明 | 否 |
| `user_clarified` | 初始输入存在结构性歧义，已通过真实问答消除 | 是，只问关键问题 |

继承上下文时必须记录来源任务、版本或运行标识，并检查当前输入是否与既有需求冲突。既有需求失效、版本不明或本次增量改变任务结构时，不得静默继承。

### 3.3 不得伪造用户确认

系统可以自动提取、归纳、规范化和提出可回滚假设，但不得：

1. 用系统推断、默认值、模板示例或批处理参数冒充用户回答；
2. 把“未发现歧义”写成“用户已确认”；
3. 事后补写并不存在的提问、回答或确认时间；
4. 将历史任务中的回答移植到已改变结构的新任务；
5. 为满足字段或校验器而制造交互记录。

只有真实发生的问答才写入 `clarifications`。未追问时该字段为空，由 `input_resolution.mode`、来源记录和系统理解说明为什么可以直接进入 02。

### 3.4 什么是结构性歧义

以下歧义通常会改变 02 的任务结构，必须追问：

1. 核心对象或对象层级有多个实质不同解释；
2. 无法判断要做状态、趋势、影响、路径还是假设更新；
3. “影响”可能指供给、需求、成本、业绩、估值或预期，且不同选择会改变主通道；
4. 多个主线竞争，无法确定本次优先验证哪一个；
5. 时间、地域、产业链或对象范围的不同解释会改变核心路径；
6. 用途或交付落点会改变分析深度、对象拆分或正文结构；
7. 当前输入与继承的既有需求发生冲突；
8. 问题只能写成“综合影响”“全链分析”或“整体判断”。

追问时一次只问最关键的问题，并说明该答案会改变什么。能从当前输入或有效上下文可靠提取的信息不重复询问。

### 3.5 不阻塞 01 的缺口

以下内容可记录为可回滚假设或下游待解析项：

1. 不改变任务结构的名称规范化；
2. 02 才能完成的对象类型或本体角色归属；
3. 03 才能确定的实际数据截止时点、样本名单或来源；
4. 不影响主问题的补充对象；
5. 不影响研究范围的表达格式和版式偏好。

可回滚假设必须写明依据和触发回滚的条件。会改变主对象、判断类型、主通道、关键范围或用途的事项不得作为系统默认假设。

## 4. 核心字段

正式 01 本阶段输出至少表达以下内容。字段结构和枚举以本阶段模板为准，本规范不重复完整 YAML。字段服务于第 2.3 节完整性总判据，不得为填满模板而制造无判别力的占位内容。

| 字段组 | 核心要求 |
|---|---|
| 原始输入 | 保留本轮输入，并引用继承任务或历史上下文来源 |
| 输入解析 | 记录解析模式、系统理解、可回滚假设、真实澄清和未决歧义 |
| 规范化问题 | 不预设结论，可验证、可反证 |
| 最终落点 | 明确状态、趋势、阶段、影响、路径或假设更新 |
| 核心研究主线 | 一个主对象、比较范围（或「无比较」）、判断动作、主要通道、核心待验证问题和 05 落点 |
| 时间口径 | 分列回看期、当前时点、前瞻期；不适用项标明原因 |
| 研究范围 | 地域、产业链、对象、用途和不研究事项 |
| 范围过宽检查 | 说明为何已收敛，或为什么需要澄清、拆题或拒绝 |
| 研究价值 | 说明分歧或未知、变化变量、影响路径、决策用途和为什么是现在 |
| 观察与初步线索 | 记录有判别力的观察维度，以及支持、削弱、反证和竞争解释方向 |
| 交付深度 | 声明 05 报告类型、使用目的、结论粒度与最低交付要求 |
| 前提与假设 | 区分已知事实、用户假设、待验证假设；系统可回滚假设单独标明失效条件 |

核心研究主线只是 02 的输入线索，不得在 01 写成正式节点链、传导路径、证据槽位或推理结论。

### 4.1 范围与动态口径

“当前”“近半年”“未来 6 个月”“代表性公司”“最新公告”等动态表达必须保留业务含义和刷新口径，并落到回看期 / 当前时点 / 前瞻期三栏（或标明不适用）。文件日期只表示生成时间；03 在每次运行中记录实际采用的起止日期、对象名单和数据截止时点。

历史回放必须明确“截至当时可得信息”的截止边界，不得把后见事实混入原任务。增量运行应继承未改变的核心字段，只记录本轮变更和变更来源。

### 4.2 前提三分法

正文「前提与假设」必须按三类记录，避免 02 把前提当成待证命题，或把待证命题当成已确认事实：

| 类型 | 含义 | 02 用法 |
|---|---|---|
| 已知事实 | 用户明确给定或有效上下文继承的前提；01 不核验真伪 | 可作为结构前提；若后续被证伪，退回 01 或改写前提 |
| 用户假设 | 用户明确采用、但尚未被本任务验证的立场或边界选择 | 继承为任务约束；不得改写成系统默认 |
| 待验证假设 | 本次需要支持、削弱或反证的命题 | 进入 02 核心待验证结构 |

系统整理产生的非结构性默认，继续写入 `input_resolution.rollback_assumptions` 或「可回滚假设」，不得混入「用户假设」。

### 4.3 研究价值检查

`stage_status=complete` 且 `task_disposition=accepted` 必须满足 `research_value_gate.status=pass`，且 `value_level` 不得为 `low`。无法确认市场共识时，可以记录内部原判断、常见叙事或关键未知，但不得虚构市场观点。

主题宏大、材料丰富或事实正确都不能单独证明研究价值。低价值问题应收窄、延期或停止，不得仅为启动全链而包装成高价值任务。

## 5. 改写、拆题与追问

### 5.1 改写原则

1. 保留用户真实意图，不偷换问题；
2. 不预设利好、利空、改善或恶化；
3. 把未经验证的事实前提改写为待验证命题；
4. 明确对象、判断动作、时间窗口、主要范围和用途；
5. 优先使用“是否”“处于什么阶段”“在什么条件下”“哪些信息支持或削弱”等表达；
6. 区分用户原话、用户材料、继承上下文、系统整理和系统假设；
7. 不为了覆盖全面而并列多个主通道。

### 5.2 范围过宽时的处理

原始输入包含两个以上会改变结构的主通道时，采用以下一种处理：

1. **追问**：请用户选择核心主线；
2. **拆题**：形成多个独立 01 任务；
3. **收窄**：只在不改变用户明确意图时，把一个主轴作为本次任务，其余列为辅助观察或不研究事项；
4. **不予受理**：无法改写为有效判断任务时停止流转。

不得把宽泛事件、宏观主题、全产业链或“综合影响分析”原样交给 02。

## 6. 阶段状态、任务处置与质量状态

### 6.1 阶段状态与任务处置

`stage_status` 只使用全局枚举：`not_started`、`in_progress`、`complete`、`blocked`、`returned`。不得把业务处置结果写入该字段。

`task_disposition` 只记录 01 的任务处置结果：

| `task_disposition` | 典型 `stage_status` | 是否生成正式文件 | 处理方式 |
|---|---|---:|---|
| `accepted` | `complete` | 是 | 生成完整《投研需求说明》，进入 02 |
| `needs_clarification` | `blocked` | 否 | 只追问最关键问题；消除歧义后再生成正式文件 |
| `out_of_scope` | `complete` | 是 | 生成简短《不予受理说明》，不进入 02 |
| `split_required` | `blocked` | 否 | 拆成多个独立 01 后再受理；若输出拆题说明，可改记 `stage_status=complete` |

`needs_clarification` 只用于真实存在结构性歧义的情况，不得因为缺少固定数量的用户问答而触发。`out_of_scope` 与 `split_required` 都是处置结果，不是阶段执行状态；前者表示请求不在本流程范围，后者表示仍属投研判断但必须先拆题。

### 6.2 产出质量状态

| 状态 | 含义 | 处理 |
|---|---|---|
| `draft` | 尚未完成校验 | 不得正式交付 |
| `minimum_pass` | 可内部试做 | 不得作为高质量交付 |
| `high_quality_pass` | 规则校验通过，并达到本节高质量门槛 | 可正式交给 02 |
| `return_required` | 存在关键缺陷 | 返回 01 澄清或重写 |
| `stop_with_gap_report` | 当前无法形成有效任务 | 输出缺口或不予受理结果 |

阶段状态、任务处置、产出质量和后续结论强度必须分开记录。

## 7. 质量门槛与返工规则

本节是 01 阶段质量要求和返工条件的唯一权威。

### 7.1 进入 02 前的最低检查

进入 02 前先按第 2.3 节完整性总判据检查；再至少满足：

| 检查项 | 通过标准 |
|---|---|
| 输入解析 | 已标明解析模式和信息来源；系统理解已展示；真实问答未被伪造 |
| 结构性歧义 | 未决列表为空；如曾追问，只记录真实回答 |
| 核心问题 | 不预设结论，可验证、可反证 |
| 核心研究主线 | 主对象、比较范围（或「无比较」）、判断动作、主要通道和核心问题单一清楚 |
| 时间口径 | 回看期、当前时点、前瞻期已分列，或已标明不适用及原因 |
| 对象与范围 | 地域、产业链、对象、用途和不研究事项足以限定任务 |
| 前提三分 | 已知事实、用户假设、待验证假设已区分；已知事实未冒充已核验 |
| 结论粒度 | 结论粒度与最低交付要求已写清，且未写成正式路径或推理结论 |
| 范围过宽检查 | `overscope_check.status=pass`，不需要继续拆题 |
| 研究价值检查 | 状态为通过，价值等级不是低 |
| 线索完整 | 有支持、削弱、反证和竞争解释方向 |
| 可重复执行 | 动态时间和对象具有刷新规则 |
| 上下文一致 | YAML、正文和继承来源不存在冲突 |

### 7.2 高质量语义门槛

达到 `high_quality_pass` 时，重点确认：

1. 是否满足第 2.3 节：02 无需擅改问题、扩边界或补核心假设即可搭结构；
2. 规范化问题是否真正回答用户要判断什么；
3. 主线是否足够单点，能指导 02 搭建判断结构；
4. 比较对象、时间三件套、排除范围和交付深度是否与问题匹配；
5. 范围是否既不过宽，也没有漏掉必要边界；
6. 研究价值是否来自可辨别的认知差、变量变化和影响路径；
7. 观察维度、反证和竞争解释是否具有判别力；
8. 前提三分与可回滚假设是否透明，且没有替代用户作结构性选择；
9. 是否没有越界写入 02、03、04 的内容。

### 7.3 返工条件

出现以下任一情况，不得进入 02：

1. 不满足第 2.3 节完整性总判据；
2. 核心问题、对象、比较范围、判断动作、主通道或最终落点不清；
3. 时间三件套、范围、用途、结论粒度或最低交付要求不清，且不同选择会改变任务结构；
4. 前提未三分，或把系统推断写成用户假设 / 已知事实；
5. 当前输入与继承的既有需求冲突；
6. 主线无法成立，或问题仍是宽泛主题；
7. 范围过宽检查或研究价值检查未通过；
8. 反证或竞争解释方向缺失；
9. 系统推断被写成用户确认，或交互记录被伪造；
10. 结构化摘要与正文不一致；
11. 请求超出本项目范围且无法合理改写。

返工时必须说明：当前缺陷、它影响的任务要素、需要补充或重写的内容，以及重新进入 02 的判定条件。只追问能消除结构性歧义的最小问题集。

## 8. 输出与 02 交接

### 8.1 通过版

`stage_status=complete + task_disposition=accepted + quality_status=high_quality_pass` 时，按 [`模板/01_投研需求说明模板.md`](模板/01_投研需求说明模板.md) 生成：

```text
01-<核心主题>投研需求说明-<YYYYMMDD>-<当日序号>.md
```

通过版只写研究需求，不包含正式本体类型、路径、证据规则、推理结果或投资建议。模板中的说明、占位符和示例不得进入正式输出。

### 8.2 待澄清状态

`task_disposition=needs_clarification`（通常伴随 `stage_status=blocked`）不生成正式文件。对话中只说明：

1. 当前存在什么结构性歧义；
2. 它会改变什么；
3. 本轮需要回答的一个关键问题；
4. 回答后如何继续。

### 8.3 不予受理或须拆题

`task_disposition=out_of_scope`（`stage_status=complete`）时，按 [`模板/01_不予受理说明模板.md`](模板/01_不予受理说明模板.md) 生成：

```text
01-<核心主题>不予受理说明-<YYYYMMDD>-<当日序号>.md
```

`task_disposition=split_required` 时，优先拆成多个独立 01；若需要正式说明，可沿用不予受理模板并填写 `task_disposition=split_required`。

### 8.4 交给 02 的内容

02 读取：规范化问题、核心研究主线（含比较范围）、判断落点、时间口径（回看 / 当前 / 前瞻）、对象与排除范围、前提三分、观察维度、初步线索、研究用途、结论粒度与最低交付要求、可回滚假设、解析来源和范围过宽检查。

02 必须继承 01 的研究意图、比较范围、时间口径、前提约束和交付深度。不得擅自改写核心问题、扩大排除范围之外的边界，或把待验证假设改成已知事实。若发现新的结构性歧义，退回 01；若仅发现本体表达能力不足，在 02 记录本体候选或缺口，不视为 01 受理失败。

```text
研究输入
↓
01 条件解析
├─ task_disposition=needs_clarification（stage_status=blocked）：只追问结构性歧义
├─ task_disposition=split_required：拆题后再受理
├─ task_disposition=out_of_scope（stage_status=complete）：输出不予受理说明
└─ task_disposition=accepted（stage_status=complete）：展示系统理解和假设，进入 02
```
