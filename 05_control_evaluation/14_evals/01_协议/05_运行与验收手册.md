# 05 运行与验收手册

## 1. 运行环境

框架使用 Python 3、PyYAML 和标准库。仓库不保存任何模型密钥。真实模型由外部命令适配器读取自己的环境变量或密钥管理配置。

统一入口：

```text
05_control_evaluation/14_evals/03_执行/eval_cli.py
```

## 2. 五个命令

### 2.1 validate

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py validate
```

校验：

- 四个案例及分层；
- 冻结证据字段、定位、截止日和哈希；
- 3—7 条密封判断及最低证据组合；
- 密封 provenance 与客观检查；
- 四类扰动；
- 十一类缺陷；
- 生产者可见字段和密封隔离；
- 同证据主对比基线与弱基线配置；
- 指标、提示词和适配器协议。

正式模型配置预检：

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py validate \
  --profiles /path/to/model_profiles.yaml \
  --official
```

### 2.2 prepare

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py prepare \
  --run-dir /tmp/research-eval
```

生成 manifest、A—E 上下文、盲化候选、缺陷变体和请求计划。已有请求或响应日志的目录不能重新 prepare；需要续跑时直接执行 run，需要重新冻结时使用新目录。

### 2.3 run

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py run \
  --run-dir /tmp/research-eval \
  --profiles 05_control_evaluation/14_evals/03_执行/mock_profiles.yaml \
  --stage all \
  --intensity pilot_light
```

`--stage` 支持：

| 值 | 行为 |
|---|---|
| `calibration` | 只运行缺陷、正常版和扰动校准 |
| `formal` | 先恢复或运行校准，通过 C 门后执行正式阶段 |
| `all` | 校准和正式阶段全部执行 |

`--intensity pilot_light` 使用每个评测模型一次重复，并只跑 B/C/D 下游上下文，适合先验证真实模型适配和区分能力；通过后必须创建新的冻结运行目录，以 `--intensity formal_full` 跑三次重复和 A—E 全上下文。不得在同一运行目录混用两种强度。

真实模型首次预检必须设置新请求硬上限，例如：

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py run \
  --run-dir /tmp/research-eval \
  --profiles 05_control_evaluation/14_evals/03_执行/model_profiles.yaml \
  --stage calibration \
  --intensity pilot_light \
  --max-new-requests 2
```

达到上限后，程序会在发送下一请求之前停止并写入 `request_budget_exhausted`；续跑命中的既有 `request_id` 不占本次新增预算。该门只限制调用数，不降低单次结构化答案所需的 completion 空间，避免“上限过低但已计费、最终 JSON 为空”的浪费。

### 2.4 aggregate

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py aggregate \
  --run-dir /tmp/research-eval
```

只接受 `run_status.status=completed` 的运行。存在执行错误、校准阻断或缺失裁决时拒绝聚合。

### 2.5 report

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py report \
  --run-dir /tmp/research-eval
```

根据 `summary.yaml` 生成**研究员可读**的 Markdown 报告：先给案例级白话结论，再分节说明可靠性（R）、有用性（U）、相对同证据直出的增益（delta）、稳定性与评测器校准；不打综合分。

## 3. 模型档案

复制配置模板：

```text
05_control_evaluation/14_evals/03_执行/model_profiles.example.yaml
```

每个 profile 至少包含：

- `model_id`；
- `provider_family`；
- `command` 命令数组。

仓库已提供 `http_model_adapter.py`，兼容 OpenAI 风格的 Chat Completions 与 Responses API。每个 profile 只从环境变量读取配置，例如：

```bash
export EVAL_PRODUCER_API_KEY='...'
export EVAL_PRODUCER_BASE_URL='https://api.example.com/v1'
export EVAL_PRODUCER_MODEL='frozen-producer-model-version'
export EVAL_PRODUCER_API_STYLE='chat_completions'  # 或 responses
```

`JUDGE_A`、`JUDGE_B`、`DOWNSTREAM_A`、`DOWNSTREAM_B` 使用同样命名方式。密钥不会写入请求、响应、manifest 或报告。正式运行仍需在 `model_profiles.yaml` 中填写真实且冻结的 `model_id` 与 `provider_family`，并保证评测/下游角色独立。

角色绑定必须包含：

- `producer`：问题直答和证据摘要基线生产者；
- `judges`：两个独立评测模型档案（`single_vendor` 下可共用同一 `model_id`）；
- `downstream_models`：两个独立下游任务执行模型档案（`single_vendor` 下可共用同一 `model_id`）。

`run_mode: official`（`formal_full`）拒绝：

- 占位符和 mock 模型；
- 只有一个评测模型；
- 两个评测档案使用同一 `model_id`；
- 生产模型与评测模型重合；
- 下游模型与给它评分的评测模型重合。

`run_mode: single_vendor` 分成两种不可混淆的范围：

- 只有 1 个 `model_id` 时，范围固定为 `pipeline_only`：只能验证请求、恢复、聚合和报告链路，R/U/delta/S/C 不得作为研究增益证据；
- 至少 2 个互异 `model_id`，且生产者不兼任评测或下游角色时，范围为 `single_vendor_comparative`：可以形成供应商内的有边界试点结论，但不得外推为 `formal_full` 跨模型可靠率。

仓库当前 [`model_profiles.yaml`](../03_执行/model_profiles.yaml) 为生产 `deepseek-v4-flash` + 评测/下游 `deepseek-v4-pro` 的 `single_vendor_comparative` 档案；完整校准与 formal 发布仍须带显式 `--max-new-requests`，且不得把预算切片外推为正式可靠率。

## 4. JSONL 适配器协议

适配器通过标准输入/输出逐行收发 JSON 对象。

### 4.1 请求必需字段

```text
request_id
role
model_profile
messages
temperature
seed
max_output_tokens
response_schema
prompt_version
case_hash
```

请求还包含元数据，用于案例、角色、模型、种子、提示变体、上下文和候选顺序的聚合。

### 4.2 响应必需字段

```text
request_id
status
model_id
text
result
usage
latency_ms
error
```

`request_id` 必须与请求一致，`status` 只能为 `ok` 或 `error`。密钥不得进入请求、响应或运行日志。

## 5. 重试、幂等与断点续跑

- `request_id` 由案例、角色、模型、种子、提示变体、请求后缀、案例哈希和 payload 哈希共同确定；
- 已有响应的请求不会重复执行或追加日志；
- 无效 JSON、缺字段、请求 ID 错配、进程提前退出和超时都会触发重试；
- 最多重试两次；
- 第三次失败写入正式错误响应，不得静默丢弃；
- 响应日志顺序不影响聚合，聚合按请求元数据识别记录。

失败请求默认不会在同一 run 中被自动覆盖。修复适配器后需要创建新的冻结运行，或明确清理失败运行目录后重新 prepare。

## 6. 运行目录

典型运行目录：

```text
run_dir/
├── manifest.yaml
├── request_plan.yaml
├── contexts/                     # A—E 下游上下文
├── candidates/                   # 盲化系统候选
├── baselines/                    # 直接报告与证据摘要
├── defect_variants/              # 十一类缺陷版本
├── requests.jsonl
├── responses.jsonl
├── calibration_summary.yaml
├── run_status.yaml
├── summary.yaml
├── summary.json
└── report.md
```

`manifest.yaml` 保存案例哈希与系统产物哈希；`responses.jsonl` 是审计主记录；`summary.yaml/json` 是结构化聚合结果；`report.md` 是人类阅读版本。

## 7. 开发模式与正式模式

### 7.1 mock 开发模式

```bash
python3 05_control_evaluation/14_evals/03_执行/eval_cli.py run \
  --run-dir /tmp/research-eval \
  --profiles 05_control_evaluation/14_evals/03_执行/mock_profiles.yaml
```

mock 输出是确定性的，只用于验证：

- 全部角色可编排；
- 盲化和长度控制有效；
- 约 1,500 个请求可完整运行（含同证据直接生成基线）；
- 校准门能够阻断不合格评测器；
- R/U/delta/S/C 能生成 YAML、JSON 和 Markdown；
- 案例级输出裁决支持频率而非可靠概率；
- 断点恢复、去重和乱序响应有效。

mock 的 R、U、胜率或 C 不代表真实系统质量。若首轮只需验证区分能力，可参考 suite 中 `pilot_light_profile` 缩减重复与诊断组；正式发布仍用 `formal_full`。

### 7.2 正式模式

正式运行前必须冻结：

- 模型档案和模型版本；
- prompt version；
- 案例及证据哈希；
- 系统产物；
- 缺陷目录和扰动预期；
- 指标阈值（须标注 `pilot_threshold`）；
- 密封契约 provenance 与客观检查；
- 运行目录和运行模式。

运行后不得根据结果修改同一运行的密封契约或阈值。任何变更都必须创建新的 suite 或运行版本。

## 8. 自动测试

单独运行评测测试：

```bash
python3 05_control_evaluation/14_evals/03_执行/tests/test_eval_runtime.py
```

全仓验收：

```bash
python3 05_control_evaluation/03_校验/validate_project.py
```

当前测试覆盖：

- 案例缺字段；
- 证据无定位；
- 时间穿越；
- 摘录哈希不一致；
- 密封信息泄漏；
- 正式模型角色重合；
- 正文盲化标签残留；
- 十一类缺陷确实改变产物；
- 保守中位数、R 硬门槛、Wilson 区间、U/S/C 边界；
- 无效 JSON、超时、请求 ID 错配和两次重试；
- 校准失败阻断正式角色；
- 四案例端到端；
- 断点恢复、重复请求和乱序响应。

## 9. 常见失败与处理

| 失败 | 含义 | 处理 |
|---|---|---|
| `EVAL_FAIL` | 案例、配置、盲化或聚合契约不成立 | 按错误位置修复，不继续正式运行 |
| `EVAL_CALIBRATION_BLOCKED` | 整体或单个评测模型低于 C2 | 调整评测提示、模型或缺陷定位能力后创建新运行 |
| baseline 长度超出 ±15% | 比较可能受篇幅偏差影响 | 修改生成适配器，重新冻结运行 |
| 只有少于六次有效 R | 模型结构化输出或请求失败 | 检查响应日志，不用缺失值补齐 |
| 正文含内部标签 | 盲化无法保证 | 移除产物中的流程自评，重新 prepare |
| aggregate 拒绝 | run 未完整成功 | 先解决错误响应或校准阻断 |

## 10. 正式发布检查表

- [ ] `validate --official` 通过；
- [ ] 一个生产模型、两个评测模型、两个下游模型均已冻结版本；
- [ ] 评测模型优先来自不同模型家族；
- [ ] 案例、证据、密封契约、扰动和缺陷哈希未变；
- [ ] 两个评测模型分别达到 C2；
- [ ] 整体 C 至少为 C2；
- [ ] 运行状态为 `completed`，错误响应为 0；
- [ ] R/U/delta/S/C 分别报告，没有综合分；
- [ ] 案例级报告裁决支持频率，不写可靠概率；
- [ ] 案例集层可报告代理可靠率比例；四题不报区间、不外推；
- [ ] delta 主证据为相对同证据直接生成与同证据摘要；
- [ ] 问题直答仅作弱基线；
- [ ] U/C 阈值标注为 `pilot_threshold`；
- [ ] 密封契约声明独立性模式与客观检查；
- [ ] `report_value` 与 `restraint` 分层汇总；
- [ ] 报告包含最弱判断、最强反证、主要分歧、密封独立性和适用边界；
- [ ] 四题结果标注为校准试点，不宣称系统研究可靠率或未知任务泛化。

## 11. 扩展与专家复核

扩展新案例时按冻结证据准备度推进，不按旧任务数量推进。整体 C 达标后，可抽取 5%—10% 案例进行专家盲审，记录匿名审阅者、R/U 裁决、最严重错误、理由和时间。

专家结果用于校验 AI 代理评测，而不是事后修改当期 AI 评分。若专家与 AI 长期系统性分歧，应调整密封契约、角色提示或 C 校准集，并以新版本重新运行。
