# 2026-07-28 本体统一语义基础设施迁移账本

上位契约：[`../01_架构/01_本体统一语义基础设施契约.md`](../01_架构/01_本体统一语义基础设施契约.md)

## 一、问题重述

此前工程重点是“本体规则是否被执行”，但本体成为项目基础还要求“全系统是否只使用一套业务语义”。审计发现 Runtime、阶段 Schema、UI 和图物化器仍手写了部分本体已有的对象类型、关系端点与枚举，因此形成：

```text
正式本体语义
        ├─ 部分进入规则执行
        └─ Runtime 另写一套类型/值域/关系端点
```

这会导致本体变更不能自动传播、同一语义多处漂移、未知引用被弱类型字段掩盖。本轮把优化中心从“再增加几个末端规则”转为“定义入口收口 + 写入时强约束 + 运行指纹可追溯”。

## 二、现状审计

| 缺口 | 原行为 | 风险 | 目标 |
|------|--------|------|------|
| 多处扫描正式模型 | `adapters/ontology`、`graph_contract`、`ontology_rule_defs`、显示层各自读取 YAML | 解析与状态过滤漂移 | 统一语义目录 |
| Runtime 手写本体枚举 | 判断类型、J 等级、置信度、来源等级等在 Zod/UI/归一化器重复 | 本体修改不能自动传播 | 生成客户端安全投影 + 漂移校验 |
| 关系端点手写 | 范围成员与推理留痕可接受类型由代码数组维护 | 新增正式类型后 Runtime 不认识 | 从正式关系定义读取端点 |
| 未解析引用弱化 | 未知 `ontology_node_ids` 可能被物化为默认 `Industry` | 错误语义看似通过图校验 | 写图时拒绝未知非本地引用 |
| 方法对象引用只检查不删除 | `target_ontology_object_refs` 不验证是否属于任务语义对象集 | 方法与真实对象脱节 | Stage02 创建时校验解析性 |
| 只记录注入切片哈希 | 可追溯到 Prompt 文本，不能稳定说明完整本体基线 | 本体未注入部分变化难做影响分析 | 同时记录完整正式本体指纹 |

## 四、本轮实际改造

### 4.1 新增统一入口

- `06_runtime/engine/ontology_catalog.ts`
  - 按 `01_semantic_knowledge/01_ontology/model_registry.yaml` 唯一加载正式模型
  - 拒绝重复语义 ID

  - `npm run ontology:check`

### 4.2 已切换到本体权威的使用面

- Zod：判断类型、判断等级、置信度、来源等级、失败路由、证据角色、证据直接性、信号角色、规则结果、判断状态、冲突状态、市场预期、预期差、资产影响。
- UI：来源等级选择。
- 归一化：来源等级、证据直接性。
- 图合同与查询：正式对象、关系和规则通过统一目录读取。
- 图物化与 Action：范围成员、推理留痕节点从正式关系端点读取。
- 正式实例图：Stage02—04 在确认状态变更前，按 Stage02→03→04 从空图连续重放并通过本体图合同；不再增量叠加旧阶段节点。
- 投影血缘：阶段对象/关系携带 `stage_projection` 来源与阶段，Action 写入携带 `action` 来源；重建时只保留显式 Action 覆盖层。
- 图谱版本：每个阶段投影指纹绑定产物 ID、版本与内容；保存新图时同一运行仅保留一个 `approved` 实例图。
- 方法绑定：Stage02 的方法目标必须落在本次任务可解析语义对象集中。
- 阶段语义封套：新生成产物与确认动作确定性写入 `semantic_context`；正式发布汇总为 `semantic_context.yaml`，未解析引用直接阻断 production 发布。
- 正式发布语义基线：正式包同时冻结 `semantic_context.yaml` 与 `business_instance_graph.yaml`，清单绑定两者哈希、本体内容指纹和 Stage02—04 图投影指纹。
- 发布校验闭环：Runtime 与 Python 使用回归锁定的一致阶段哈希算法；新 production 包强制校验语义基线，历史 fixture 仅明示只读兼容。
- 受控语义读取：`semantic_reads` 在现代正式图存在时校验阶段产物 ID、版本、内容与图中指纹；旧运行才显式标记兼容回退。
- 外部数据映射：Stage03 实际接入的 18 个 MCP 通道已全部登记；结构化数值、事件、研报/新闻/网页分别受限为 `Observation`、`Event`、`SourceDocument` 候选，禁止直达判断。
- 映射覆盖门：注册表 `required_connectors` 与 active Profile 必须 18/18 一致；治理 API/UI 显示登记覆盖率。
- 通用关系编辑（历史方案）：已被 Ontology 4.0 业务命名 Action 取代；通用编辑仅保留给 ontology_admin 做结构治理，不在正常产品中暴露。
- 本体变更影响：语义元素 diff 通过消费面注册表生成 Schema、图、方法、工作流、映射、实例包和回归清单；运行语义封套用于识别旧基线运行。
- 治理界面/API：显示正式目录计数与指纹、映射 Profile 及旧本体运行数量，避免基础设施只存在于后台。
- 语义单一来源审计：`npm run ontology:audit` 检查模型注册表、Runtime 正式模型直接读取、
  18 个接线/必需/active 映射集合和高风险读取防腐层，防止后续重新长出平行定义。

## 五、未完成边界

本轮完成的是统一语义基础设施的 P0，不等于整个项目已完全本体化：

1. Stage02—04 的正式运行读已有单一实例图权威，但阶段 JSON 仍是主要编辑载体；尚未完成“从图生成文档投影”的单向化。
2. `graph_contract.validateSemanticClosure` 中仍有部分对象—关系闭包以代码表达，需逐步映射到正式约束或声明为 Runtime 合同。
3. `task_local:*` 可承接本体未覆盖的任务变量，但还缺正式的候选→审核→晋升生命周期。
4. 方法资产虽然引用本体对象，方法注册表还没有全量机器校验每项输入输出类型。
5. 既有历史包只能只读兼容，不应为追求表面一致而静默补写语义。
6. 本体影响分析已能列消费面和旧基线运行，但尚未自动创建迁移任务或选择局部重算范围。

## 六、下一步顺序

1. `SEM-GRAPH-001`：读面单向投影已落地（五域优化收口 D）；后续可继续把 UI/导出文档默认改为图投影，并压缩对原始阶段 JSON 的编辑入口。

优先级始终是“收口已有语义并让约束更早生效”，不是扩大第二行业或把研究方法塞进本体。
