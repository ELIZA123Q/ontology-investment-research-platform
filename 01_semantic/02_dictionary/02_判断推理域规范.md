# 投研本体 3.0：状态事件与判断约束规范

版本：3.0.0

机器权威：`models/state_event.yaml`、`models/judgment.yaml`、`models/scenario.yaml`

## 1. 职责分离

状态与事件模型描述对象在时间和范围下处于何种状态、发生了什么变化。判断模型描述研究问题如何拆成原子判断单元，以及证据和状态如何经信号、假设和稳定约束形成判断。研究方法的选择与使用记录属于公共合同，不成为正式本体规则。

## 2. 状态与事件对象

### 2.1 `StateVariable`

状态变量分为两个层次：

- 稳定定义：名称、类别、定义、变量种类、允许锚点、观测指引和领域证据画像。
- 任务绑定：具体语义对象、指标、研究范围和截止时间。

稳定定义允许 `metric_ref`、`scope_ref` 为空。具体任务必须通过 `stateVariableForObject` 绑定对象，观测和快照必须绑定实际范围和时间。该分离用于复用领域变量库，而不是放松任务实例约束。

### 2.2 `Observation`

观测记录一个状态变量的值，并区分观察时间、有效开始/结束时间、公布时间和研究截止时间。`observationOf` 指向唯一状态变量；`factGroundsObservation` 提供事实基础。

### 2.3 `StateSnapshot`

快照是在同一范围和截止时间下多个观测的不可变集合。`snapshotIncludesObservation` 只允许纳入截止时间之前已公布且范围一致的观测。快照不得原地覆盖。

### 2.4 `StateChange`

状态变化表达同一变量从前态到后态的已识别变化。它必须通过 `stateChangeOf` 指向唯一变量，通过 `stateChangeFromObservation` 与 `stateChangeToObservation` 连接可比的前后观测。变化不是事件的同义词。

### 2.5 `Event`

事件是已发生的事实性变化，记录发生时间、生效时间、公布时间和研究截止时间。`eventProducesStateChange` 只表示有证据支持的触发或原因候选，并用 `causal_status` 区分候选、支持和争议；它不自动证明唯一因果。

## 3. 时间一致性

正式状态链必须满足：

```text
observed_at <= cutoff_at
published_at <= cutoff_at
valid_from <= valid_to（若 valid_to 存在）
前态 observed_at < 后态 observed_at
事件 effective_at 不早于其可产生效力的业务时间
```

使用截止时间之后才公布的数据属于未来信息，必须拒绝并使下游快照、信号、规则评估和判断失效。

## 4. 判断对象

| 对象 | 作用 |
|---|---|
| `ResearchQuestion` | 有明确范围、回答标准和失败路由的研究问题 |
| `JudgmentUnit` | 在单一对象、范围、时间和口径下可独立裁决的最小单元 |
| `Signal` | 从证据事实或状态中解释出的中间结果 |
| `Hypothesis` | 具有方向、时间尺度和证伪条件的解释或预测 |
| `CompetingExplanation` | 对同一结果提供可区分替代机制的解释 |
| `BlockingFactor` | 限制方向、等级、范围或方法适用性的业务条件 |
| `RuleEvaluation` | 对正式稳定约束逐条件执行的不可变记录 |
| `Judgment` | 经证据、信号、假设与约束形成的范围化结论 |
| `ReasoningTrace` | 从输入节点到判断的不可变有序引用图 |

`MarketExpectation`、`ExpectationGap` 和 `AssetImpact` 是判断后的专门投影，不能绕过既有判断由来源或事实直接生成。

## 5. 正式推理关系

### 5.1 问题与判断单元

- `questionDecomposesIntoUnit / unitAnswersQuestion`
- `unitUsesScope / scopeUsedByUnit`
- `judgmentUnitRequiresEvidence / requirementForJudgmentUnit`

一个判断单元只能回答一个研究问题，但一个问题必须拆为一个或多个判断单元。

### 5.2 中间推理

- `factSupportsSignal / signalGroundedByFact`
- `signalDerivedFromState / stateProducesSignal`
- `signalEvaluatesHypothesis / hypothesisEvaluatedBySignal`
- `unitHasHypothesis / hypothesisForUnit`
- `competingExplanationForUnit / unitHasCompetingExplanation`
- `blockingFactorForUnit / unitHasBlockingFactor`

证据事实可以进入信号，状态也可以形成信号；信号再评估假设。竞争解释和阻断因素必须绑定具体判断单元，不能作为报告级装饰字段。

### 5.3 判断和留痕

- `judgmentBasedOnHypothesis / hypothesisSupportsJudgment`
- `judgmentResolvesUnit / unitResolvedByJudgment`
- `judgmentHasRuleEvaluation / ruleEvaluationForJudgment`
- `judgmentHasReasoningTrace / reasoningTraceForJudgment`
- `traceIncludesNode / nodeIncludedInTrace`

非草稿判断必须有规则评估和推理留痕。留痕按顺序引用实际使用的范围、状态、证据评估、证据组合、信号、假设、竞争解释、阻断因素和规则评估，不能只保存摘要文本。

## 6. 判断状态与不可判断

`Judgment.decision_status`：

- `draft`：尚未完成门槛检查。
- `supported`：支持链成立且冲突已处理。
- `contested`：存在未解决冲突或竞争解释无法区分。
- `blocked`：决定性反证或阻断因素禁止形成方向或等级。
- `indeterminate`：现有证据不足以裁决。
- `invalidated`：上游事实、范围或时间基础已失效。

`blocked` 和 `indeterminate` 必须填写 `not_judgeable_reason`。`conflict_status=unresolved` 时不得使用 `supported`；决定性冲突不得输出高等级判断。

## 7. 稳定规则

正式判断模型只保留：

- `judgment_evidence_threshold`：判断等级不得超过证据完整性、反证处理和范围一致性共同允许的上限。
- `judgment_status_consistency`：判断状态必须与冲突、阻断和不可判断原因一致。

阶段输出权限、表达措辞、方法路由和证据等级映射由公共合同或方法资产管理，不写入正式规则参数。

## 8. 禁止边

以下正式关系不得存在：

```text
EvidenceFact -> Judgment
SourceDocument -> Judgment
EvidenceBasket -> Judgment
EvidenceFact -> AssetImpact
PolicyInstrument -> AssetImpact
```

合法主路径是：

```text
来源 -> 原始陈述 -> 证据事实
-> 观测/事件/信号 -> 假设 -> 判断单元裁决
-> 规则评估 -> 判断 -> 推理留痕 -> 判断后投影
```

## 9. 失效传播

来源撤回或新证据冲突时，先使相应证据事实和评估失效，再沿正式关系传播到观测、快照、状态变化、信号、规则评估、判断与推理留痕。历史对象不得覆盖；重算形成新对象并通过版本关系替代旧对象。
