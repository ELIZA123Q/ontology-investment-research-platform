# 证据组合使用说明（系统名 Evidence Recipe）

> 研究员只需把 Recipe 理解成“最低证据组合”：为了回答一种判断，至少要拿到哪些互相不能替代的证据。Recipe ID 和 CSV 字段用于系统记录，不影响日常分析。

## 1. 定位

Evidence Recipe 是 `JudgmentUnit` 与具体来源之间的证据组合层，回答：**这类判断至少需要哪几组证据，什么证据用于强验证，必须主动检查什么反证，缺失时如何降级。**

```text
JudgmentUnit
→ EvidenceRequirement（本次需要什么）
→ EvidenceRecipe（这类判断的组合规则）
→ EvidenceBasket（本次实际展开的篮子）
→ Source Mapping（每个篮子适合去哪取）
→ SourceDocument / EvidenceRecord
```

Recipe 不列网站，不保存当期事实，也不直接决定结论。来源只在篮子确定后通过 B 类来源映射选择。

## 2. 最小调用规则

1. 每个 critical / important JudgmentUnit 匹配 1 个主配方。任务可以基于主配方生成 `R-<TASK>-<JU>` 实例，但必须在 `strategy_library_ref` 或 `notes` 中保留父配方 ID。
2. 复杂任务可追加 1 个组合预设，但不重复展开同名篮子。
3. `mandatory` 篮子决定最低准入，`strong_validation` 提高判断强度，`counter` 必须主动检索。
4. 必需篮子缺失时按配方降级，不得用更多背景材料补数量。
5. 来源映射发生在配方之后；数据库、网页、API、MCP 是获取通道，不是证据配方。

## 3. 与 A/B 类资产的分工

| 层 | 回答的问题 | 资产 |
|---|---|---|
| Evidence Recipe | 一类判断需要什么证据组合 | `C_Evidence_Recipe`、`00_strategy_registry.yaml` |
| Acquisition Rule | 每类证据如何取、如何留痕和降级 | `A_取证规则` |
| Source Mapping | 哪类来源最适合某个篮子 | `B_取证来源`、`00_source_registry.yaml` |

Recipe 可以组合多个 A 类规则。例如周期配方以 A03 为主，同时调用 A02 测量变量、A08 检查反证；这不是新增规则。

## 4. 输出要求

匹配结果写入 `01_plan/evidence_recipe_matches.csv`，至少保留：

- `evidence_recipe_id` 与版本；若为任务实例，同时记录父配方 ID；
- 目标 JudgmentUnit 和 `judgment_type`；
- 02 交接的 `default_recipe`、是否沿用默认配方，以及偏离时的 `override_reason`；
- 必需、强验证、反证篮子；
- 最低通过规则、停止规则与降级规则；
- 实际调用的 A 类规则和 B 类来源映射文件。

实际篮子必须展开到 `01_plan/evidence_baskets.csv`，不得只写一个 recipe ID 便开始取数。

匹配顺序必须是：`judgment_type → default_recipe → 任务适用性检查 → Recipe 实例化`。03 不得根据“手头已有材料”重新猜主配方。只有默认配方前置条件明确不成立时才允许 override，且必须保留原因；材料暂时难取不是换配方理由，应形成 gap 或降级。

## 5. Recipe 完整合同

一个可执行 Recipe 至少包含：

| 字段 | 作用 |
|---|---|
| `recipe_id / version / status` | 稳定引用和生命周期 |
| `judgment_type / applicable_conditions` | 适用判断与前置条件 |
| `mandatory_baskets` | 缺失会降低或阻断判断的篮子 |
| `strong_validation_baskets` | 提高到方向性或研报级的验证 |
| `counter_baskets` | 必须主动检索的反证与阻断 |
| `minimum_pass_rule` | 最低允许进入 04 的组合条件 |
| `high_quality_rule` | 方向、独立性、反证和展示的加强条件 |
| `proxy_rule` | 允许代理什么、不能替代什么 |
| `source_rule` | 来源角色、独立组和方法透明度要求 |
| `stop_rule` | 何时停止继续取证 |
| `downgrade_rule` | 每个关键缺口如何限制 04/05 |
| `positive_example / failure_example` | 防止只写抽象原则 |

只列“价格、库存、订单”等指标名称，不算完整 Recipe。

## 6. Recipe 实例化步骤

1. 将通用篮子改写为本次对象、产品、地区、时间和粒度；
2. 为每个篮子创建一个或多个 EvidenceRequirement；
3. 明确主源、交叉源、反证源和回退通道；
4. 指定不能互相替代的篮子，例如价格不能替代需求；
5. 预设 minimum/high-quality/stop/downgrade；
6. 取证后只更新实例状态，不反向修改通用配方来迎合现有材料；
7. 如通用配方确实不适用，记录偏差并进入版本治理，而非静默删篮子。

## 7. 配方组合边界

- 组合预设用于拆 JudgmentUnit，不是把多个配方塞进一个超大单元；
- 前置配方 blocked 时，后续配方停止，例如事件事实未确认就不做公司财务影响；
- 相同篮子只实例化一次，通过多个 requirement 引用，避免重复计数；
- 组合后的整体上限不高于最关键前置 JudgmentUnit 的 readiness；
- 任务配方对通用配方的偏离必须记录 `added_baskets / removed_baskets / parameter_changes / rationale`。
