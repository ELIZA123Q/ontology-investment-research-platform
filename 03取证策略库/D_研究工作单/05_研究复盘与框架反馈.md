## Evidence Pattern Case

> 一次完整任务复盘形成一张案例卡。它记录 Recipe 在真实任务中的有效性，不把后验事实回填到原证据包。

```yaml
case_id: EPC-<YYYY>-<NNN>
case_name: <案例名称>
source_task_ref: <原任务与原证据快照>
judgment_type: <02 JudgmentUnit 的判断类型>
effective_recipe: <实际生效的 Recipe ID 与版本>
most_effective_evidence:
  - <最能改变准入或区分竞争解释的证据组合>
misjudgment_sources:
  - <被高估的代理、错误外推、口径错配或遗漏变量>
added_counter_evidence:
  - <后续发现、但不得回填原快照的反证>
inaccessible_evidence:
  - <结构性不可得、权限受限或长期滞后的关键证据>
downstream_04_consumption_issue:
  - <04 无法直接消费的字段、边界或表达权限>
learning_target:
  - <Recipe | A_rule | B_source | proxy | conflict_protocol | 02_framework>
status: candidate  # candidate | validated | promoted | rejected
```

### 示例：2026 存储周期判断

| 字段 | 示例内容 |
|---|---|
| 判断类型 | 周期判断 |
| 有效 Recipe | `ER-CYCLE-01` |
| 最有效证据 | 价格 + 库存 + 企业 capex 的相互验证 |
| 误判来源 | AI 需求预期被过度外推到全品类与完整周期 |
| 新增反证 | 多层库存周期与产品分化 |

示例只说明记录方式，不自动构成 Recipe 修改依据。

## 案例升级规则

1. 单一案例只能进入 `candidate`；
2. 至少两个独立任务出现同类模式，且覆盖成功与失败/降级两种结果，才可进入 `validated`；
3. 只有验证案例能够明确指出改哪个篮子、来源映射、降级或停止条件时，才可进入 `promoted`；
4. 无法排除后验偏差、范围错配或一次性事件时标记 `rejected`，不得修改稳定方法库。
