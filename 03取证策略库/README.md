# 03取证策略库

> **研究员从这里开始：**阅读 [00_研究员取证工作台](00_研究员取证工作台.md)，然后复制 [取证任务单](D_研究工作单/01_取证任务单.md)。A 类回答“怎样证明”，B 类回答“去哪里找”，C 类回答“最少要哪几类证据”，D 类用于实际工作和复盘。`00_*yaml`、manifest 与脚本属于系统接口，第一版不要求研究员直接维护。

本库用于 03 数据与证据准备阶段，帮助研究员把 02 的判断变成一项可执行的验证任务：需要哪几类证据、先去哪里找、怎样识别冲突、证据够到什么程度、下一次何时更新。

03 的完整能力边界见[能力模型与文件职责矩阵](00_能力模型与文件职责矩阵.md)。对研究员而言，它是“判断验证与更新层”，不是数据源目录或材料收集手册；“证据工程”只作为系统实现概念保留。

本库只回答“需要什么证据、去哪里取、怎样评价证据能否使用”。判断结构由 [`02框架库`](../02框架库/README.md) 负责；合格证据怎样影响路径、反证处理和最终观点由 [`04推理方法库`](../04推理方法库/README.md) 负责。03 可以给出 04 最多能形成的结论，但不计算变量方向、不执行正式规则，也不形成研究结论。

## 研究员只需认识四个目录

| 目录 | 回答的问题 | 什么时候打开 |
|---|---|---|
| A_取证规则 | 这类判断怎样证明、怎样识别误判 | 已知道要验证状态、趋势、传导、比较、财务等哪类问题 |
| B_取证来源 | 哪类来源最适合证明哪类主张 | 准备安排主源、交叉源和反证源 |
| C_Evidence_Recipe | 最少需要哪几类互补证据 | 防止用一种材料替代整个证据组合 |
| D_研究工作单 | 怎样执行、更新和复盘 | 每次任务直接复制使用 |

根目录的 YAML、manifest、能力矩阵和校验脚本由库管理员维护，研究员不必从这些文件开始。

## 使用方式

03 按以下顺序工作：

```text
读取 02 的主判断、竞争解释和改判信号
→ 找出最可能改变结论的“胜负点”
→ 配置最低证据组合和来源顺序
→ 先取阻断/决胜证据，再取交叉验证和表达素材
→ 每拿到一项材料就判断它证明了什么、没证明什么
→ 主动寻找反证并处理冲突
→ 给出“已确认/较支持/条件成立/仅线索”档位
→ 留下下一验证点、更新日期和改判规则
```

## 设计原则

1. 先定要解决的分歧，再取数。
2. 直接事实、机制、结果和反证承担不同作用，不能用同类材料堆数量。
3. 先找最接近事实的主源，再找真正独立的交叉源和反证源。
4. 搜索、数据库、MCP 和 AI 是取得或处理材料的方式，不是事实来源本身。
5. 03 输出的不是材料包，而是“目前能说到哪里、为什么、还缺什么、何时改判”。
6. 取证深度以能否改变判断、解释冲突和支持复盘衡量，不以文件长度或来源数量衡量。
7. Q0—Q4 必须通过 Evidence Permission Matrix 映射为 04 的核心/方向/条件/背景/禁止权限。
8. JudgmentUnit 先继承 `judgment_type + required_evidence_role + default_recipe`，03 不替上游猜主配方。
9. 完整任务经验沉淀为 D05 的 Evidence Pattern Case；不新增第五类目录。

## 库管理员附录：自动校验

在项目根目录运行：

```bash
python3 03取证策略库/validate_strategies.py
```

校验器检查系统注册表、A01—A09、8 个核心证据组合、来源指引和内部链接，不修改任何文件。研究员日常不需要运行。
