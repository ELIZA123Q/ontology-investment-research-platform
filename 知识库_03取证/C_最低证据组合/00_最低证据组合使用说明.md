# 最低证据组合使用说明

> 研究员把这里理解成“最低证据组合”即可：为了回答一种判断，至少要拿到哪些互相不能替代的证据。系统登记名是 Evidence Recipe；Recipe ID 和 CSV 字段用于系统记录，不影响日常分析。

## 1. 定位

最低证据组合是判断单元与具体来源之间的证据组合层，回答：**这类判断至少需要哪几类证据，什么证据用于强验证，必须主动检查什么反证，缺失时如何降级。**

判断类型的默认选用只在 `00_strategy_registry.yaml` 定义；证据类别的稳定 ID 只在 `00_basket_registry.yaml` 定义。02 不输出 `default_recipe`，03 根据 `judgment_type` 自动匹配。

```text
JudgmentUnit（判断单元）
→ EvidenceRequirement（本次需要什么）
→ EvidenceRecipe（这类判断的组合规则）
→ EvidenceBasket（本次实际展开的证据类别）
→ Source Mapping（每个证据类别适合去哪取）
→ SourceDocument / EvidenceRecord
```

最低证据组合不列网站，不保存当期事实，也不直接决定结论。来源只在证据类别确定后通过 B 类来源映射选择。

## 2. 最小调用规则

1. 每个关键或重要判断单元匹配 1 个主组合。任务可以基于主组合生成 `R-<TASK>-<JU>` 实例，但必须在 `strategy_library_ref` 或 `notes` 中保留父组合 ID。
2. 复杂任务可追加 1 个组合预设，但不重复展开同名证据类别。
3. `mandatory` 决定最低准入，`strong_validation` 提高判断强度，`counter` 必须主动检索。
4. 必需证据类别缺失时按组合降级，不得用更多背景材料补数量。
5. 来源映射发生在组合确定之后；数据库、网页、API、MCP 是获取通道，不是最低证据组合。

## 3. 与 A/B 类资产的分工

| 层 | 回答的问题 | 资产 |
|---|---|---|
| 最低证据组合 | 一类判断需要什么证据组合 | `C_最低证据组合`、`00_strategy_registry.yaml` |
| 取证规则 | 每类证据如何取、如何留痕和降级 | `A_取证规则` |
| 来源映射 | 哪类来源最适合某个证据类别 | `B_取证来源`、`00_source_registry.yaml` |

最低证据组合可以组合多个 A 类规则。例如周期组合以 A03 为主，同时调用 A02 测量变量、A08 检查反证；这不是新增规则。

## 4. 输出要求

匹配结果写入 `01_plan/evidence_recipe_matches.csv`，至少保留：

- `evidence_recipe_id` 与版本；若为任务实例，同时记录父组合 ID；
- 目标判断单元和 `judgment_type`；
- 03 生成的 `matched_recipe`、`recipe_version` 和规范化后的 `normalized_judgment_type`；
- 如偏离默认组合，记录 `recipe_override` 与 `override_reason`；
- 必需、强验证、反证证据类别；
- 最低通过规则、停止规则与降级规则；
- 实际调用的 A 类规则和 B 类来源映射文件。

实际证据类别必须展开到 `01_plan/evidence_baskets.csv`，不得只写一个 recipe ID 便开始取数。

匹配顺序必须是：读取并规范化 `judgment_type`，从唯一判断类型词典取得默认组合，检查是否适用于本次任务，再按本次对象和范围展开最低证据组合。03 不得根据“手头已有材料”重新选择主组合。只有默认组合的前置条件明确不成立时才允许替换，并保留原因；材料暂时难取不是替换理由，应记录缺口或降低结论强度。

## 5. 最低证据组合的完整要求

一个可执行组合至少包含：

| 字段 | 作用 |
|---|---|
| `recipe_id / version / status` | 稳定引用和生命周期 |
| `judgment_type / applicable_conditions` | 适用判断与前置条件 |
| `mandatory_baskets` | 缺失会降低或阻断判断的稳定证据类别 ID，必须来自 `00_basket_registry.yaml` |
| `strong_validation_baskets` | 提高到方向性或研报级的验证 |
| `counter_baskets` | 必须主动检索的反证与阻断 |
| `minimum_pass_baskets / minimum_pass_rule` | 最低通过涉及的显式证据类别及其组合条件；前者必须是 mandatory 子集 |
| `high_quality_rule` | 方向、独立性、反证和展示的加强条件 |
| `proxy_rule` | 允许代理什么、不能替代什么 |
| `source_rule` | 来源角色、独立组和方法透明度要求 |
| `stop_rule` | 何时停止继续取证 |
| `downgrade_rule` | 每个关键缺口如何限制 04/05 |
| `positive_example / failure_example` | 防止只写抽象原则 |

只列“价格、库存、订单”等指标名称，不算完整组合。

## 6. 按本次任务展开最低证据组合步骤

1. 将通用证据类别改写为本次对象、产品、地区、时间和粒度；
2. 为每个证据类别创建一个或多个 EvidenceRequirement；
3. 明确主源、交叉源、反证源和回退通道；
4. 指定不能互相替代的证据类别，例如价格不能替代需求；
5. 预设 minimum/high-quality/stop/downgrade；
6. 取证后只更新实例状态，不反向修改通用组合来迎合现有材料；
7. 如通用组合确实不适用，记录偏差并进入版本治理，而非静默删类别。

## 7. 组合边界

- 组合预设用于拆判断单元，不是把多个组合塞进一个超大单元；
- 前置组合受阻时，后续组合停止，例如事件事实未确认就不做公司财务影响；
- 同一必要证据组合在单次任务中只建立一次，通过多个 requirement 引用，避免重复计数；
- 组合后的整体上限不高于最关键前置判断单元的就绪度；
- 任务组合对通用组合的偏离必须记录 `added_baskets / removed_baskets / parameter_changes / rationale`。
