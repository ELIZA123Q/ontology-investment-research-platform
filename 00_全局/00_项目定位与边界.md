# 00_项目定位与边界

## 1. 项目定位

本项目建设一套**面向投研判断问题的统一推理框架**：同一套概念、同一套证据要求、同一套推理规则。

它把研究员提出的事件、变量、材料线索或投资假设，整理成可以验证、可以反证、可以复盘的判断过程。不同问题尽量回到同一套对象、关系、关键变量、证据要求和推理规则中处理，减少临时解释、口径漂移和结论说不清依据。

本项目不以从零生成研究选题为主要目标。对于尚未形成明确判断的问题，可以帮助研究员把已有观察或初步想法收敛为可验证问题；只有当问题能够落到具体对象、关键变量、证据要求和反面证据检查时，才进入后续流程。

本项目重点回答：

> 一个投研判断为什么成立，证据是否充分，是否存在反面证据，结论应说到什么强度，以及后续如何复盘和沉淀。

---

## 2. 项目要解决的问题

1. **把问题变成可执行任务** — 收敛为对象、范围、关键变量、证据要求和反面证据条件明确的判断任务。
2. **统一语义和分析口径** — 用本体统一核心概念，用分析框架组织常见判断机制。
3. **让证据准备和推理过程可检查** — 材料归一为可追溯实例，再逐段验证支持、削弱、失效条件与竞争解释。
4. **让每次判断可留痕、可复盘** — 区分「本体没有定义」「本次实例缺失」和「现有证据不足」。
5. **保留可复用的方法信息** — 区分稳定分析方法与本次事实、结论。

---

## 3. 本项目不做什么

1. 不替研究员从零批量生成选题，也不凭空创造投资判断。
2. 不做通用行情或资讯查询；材料是证据来源，不是最终交付。
3. 不输出直接买卖建议或确定性价格预测。
4. 不追求全行业、全公司、全历史的知识库覆盖；以最小充分范围为原则。
5. 不把单次结果直接等同于稳定方法、本体或 Skill。
6. 不复用旧事实和旧结论代替重新判断；可复用结构与规则，但每次必须刷新实例和证据。
7. 不处理内幕或未授权信息。

不能直接进入流程的问题：纯事实查询、直接交易问题、确定性预测、过大过泛无法落到对象与反证的问题。系统应拒绝、降级或改写（例如将「能不能买」改写为「公开证据是否支持进一步研究价值」）。

---

## 4. 适用问题范围

当前服务于**投研判断推理型问题**，以及能被收敛为此类问题的事件观察、材料线索或初步想法。

| 主任务类型 | 示例 |
|------------|------|
| 状态与趋势判断 | 未来 6—12 个月，存储芯片供需是否会改善？ |
| 事件或变化影响判断 | InP 出口管制是否会影响相关材料、产品或公司？ |
| 传导路径判断 | InP 供应受限是否会传导到光芯片、光模块及相关公司？ |
| 假设验证与更新判断 | “AI 光模块高景气将持续支撑中际旭创业绩”是否仍成立？ |

证据更新与历史复盘都需落到上述某一主类型。本体缺口发现是附带诊断，不是独立任务类型。

## 5. 运行骨架（细则在阶段规范）

本项目以 01—05 为职责边界与质量检查点，不是只能走一次的线性流水线。首次通常按 01→05；证据补充后按对象变化返回受影响阶段。

| 02 | 如何分析，本体能否承接 | [`../02_判断结构/02_判断结构与本体视图规范.md`](../02_判断结构/02_判断结构与本体视图规范.md) |
| 03 | 证据是否够用，交付素材是否就绪 | [`../03_数据与证据/03_数据与证据准备规范.md`](../03_数据与证据/03_数据与证据准备规范.md) |
| 04 | 判断定稿到什么强度，允许 05 表达什么 | [`../04_推理/04_推理输出规范.md`](../04_推理/04_推理输出规范.md) |
| 05 | 如何写成指定原型的研究稿 | [`../05_表达交付/05_投研表达与交付规范.md`](../05_表达交付/05_投研表达与交付规范.md) |

- **跨阶段 ID 与主链**：机器约定以 [`contracts/public_contract.yaml`](contracts/public_contract.yaml) 的 `trace_id_patterns` / `cross_stage_references` 为唯一权威；阶段规范只解释本阶段如何使用。
- **结构化主链（业务读法）**：研究问题 → 核心判断（`JudgmentUnit`）→ 证据要求 → 证据与就绪评价 → 规则评价与判断 → 报告表达 → 事后复盘。几类 Claim 不可混用：`CandidateClaim`（待验证）、`EvidenceClaim`（来源说法）、`Judgment`（04 判断）、`ReportClaim`（获准表达）。
- **事后复盘**不是第 06 阶段，不阻塞当次交付。
- 全库自检：`python3 validate_project.py`。

## 6. 两类结果

| 结果类型 | 回答的问题 | 主要内容 |
|----------|------------|----------|
| 任务判断结果 | 本次问题得到什么判断？ | 本次对象、实例、证据、路径状态、结论、限制和留痕 |
| 分析方法信息 | 这类问题通常应该怎样分析？ | 问题拆解、分析顺序、关键变量、证据要求、反面证据方向和适用边界 |

历史事实和历史结论不能直接代替下一次判断。沉淀与版本化机制不在本总纲规定。

## 7. 核心资产分层

| 资产 | 回答的问题 | 不应保存 |
|------|------------|----------|
| 本体 | 有哪些稳定对象、关系、变量和规则？ | 单次观测、来源说法、任务结论 |
| 02 分析框架 | 某类机制通常怎样拆问题与路径？ | 本次证据状态与最终观点 |
| 03 取证策略 | 需要什么证据、从哪来、如何验收？ | 变量方向与研究结论 |
| 04 推理方法 | 合格证据怎样形成、削弱或改判？ | 新问题树、新证据、单次结论 |
| Skill | 成熟流程如何稳定执行？ | 未经评测的一次性做法 |
| 运行结果 | 截至某时点本次得到什么判断？ | 被默认当成永久方法或事实 |

三库边界：**02 决定判断什么，03 决定什么证据可以用，04 决定合格证据怎样形成判断。** 正式本体、任务视图与本次记录的分工见 [`../一级通用本体规范/00_投研本体框架概述.md`](../一级通用本体规范/00_投研本体框架概述.md) 与 02 规范；关键判断编号在 02 创建并由下游原样继承。

## 8. 方法论有效性原则

1. **问题可判断** — 落到对象、范围、关键变量与可支持/推翻的信息。
2. **逻辑可解释** — 说明变量如何变化、影响如何传导。
3. **证据可对应** — 每项关键判断有证据要求；不足时保留未知。
4. **变量不断链** — 02 选中的变量在 03/04 得到交代，不静默消失。
5. **结论有边界** — 说明范围、强度、限制、失效条件与跟踪信号。
6. **方法与事实分离** — 可复用结构 vs 本次时点事实与结论。
7. **产出可交付** — 未达高质量只能作草稿、返工或缺口说明。
8. **规范不膨胀** — 核心规范固定为 00、00A、01—05；新对象进本体，新结构进模板，成熟流程进 Skill。

## 9. 文档职责与表达原则

### 9.1 四类文档各自保存什么

| 文档类型 | 应保存 | 不应保存 |
|---|---|---|
| 阶段规范 | 输入、顺序、交付物、质量与退回、上下游交接 | 某类问题的完整方法、来源大全、当期事实 |
| 知识库 | 可复用的拆解、变量、路径、证据组合、判断方法 | 阶段流程复述、单次状态与结论 |
| 正式本体 | 稳定定义、类型、关系、约束与机器标识 | 写作教程、来源清单、临时观点 |
| 单次产物 | 本次范围、数据、证据、判断、限制与审计 | 被默认当作长期有效的方法或事实 |

同一规则只保留一个权威出处，其他文件只链接。机器枚举与值域以 YAML / CSV schema / registry 为准；Markdown 解释业务含义，不平行维护另一套机器合同。

### 9.2 三个知识库怎样分工

- **知识库_02框架**：一类问题通常判断什么、怎样拆解。
- **知识库_03取证**：需要哪些证据组合、来源与停止规则。
- **知识库_04推理**：合格证据怎样形成、削弱、阻断或修改判断。

各库以 `README.md` 为唯一入口。

### 9.3 研究员正文与系统记录

正文让不读 YAML 的读者理解问题、依据、边界与跟踪；优先用业务语言（关键判断、待验证观点、必要证据组合、证据能支持的结论强度、改判信号）。

系统对象名、状态码、内部 ID、路径编号与机器字段留在 YAML / CSV / 审计中。正文不得用「门禁」「放行」「证据篮子」「取证配方」「使用上限」「强绑定」「硬桥接」「阶段包」「本体同源」「机器事实」「派生矩阵」等工程化表达替代研究语言。

写法：先判断再依据与限制；事实、来源观点、推论与未决分开；一句一层因果；表格用于比较不重复正文；流程状态不能代替研究结论。
