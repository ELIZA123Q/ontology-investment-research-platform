## 1. 文档定位

## 2. 高质量的总体定义

高质量产出必须同时满足以下原则：

1. **不偷换问题**：对象、比较范围、时间口径、范围、用途、前提约束、结论粒度和最终要回答的问题与 01《投研需求说明》一致。
2. **有判断价值**：产出能够识别关键分歧、主导机制、竞争解释和影响判断的信号，不是材料堆砌或模板拼贴。
3. **证据不越权**：每条重要观点不超过对应证据最多能支持的强度，反面证据、冲突和限制得到处理。
4. **读者可使用**：研究员不阅读 YAML 或审计字段，也能理解当前判断、依据、边界和下一步跟踪。05 正式稿必须使用研究语言表达边界；不得把 04 的权限否定句、禁止项原文抬成标题或投资要点。
5. **可复核、可返工**：上游输入、证据、路径、观点和表达能够对应，失败时可以定位到具体阶段。

高质量不等于必须形成方向性结论。证据不足时，边界清楚、缺口明确、没有强行下结论的“暂不可判断”可以是高质量结果。

## 3. 权威状态字段

执行端只允许人工维护下列权威字段。字段可以出现在不同层级，但同一对象、同一运行、同一层级只能有一个权威值；其他带 `status`、`level` 或 `permission` 的字段只能是过程观测、规则输入或按规则展示的结果，不能反向覆盖这些字段。

| 维度 | 唯一权威字段 | 回答的问题 |
|---|---|---|
| 阶段是否完成 | `stage_status`（阶段状态） | 当前阶段是否仍在执行、已完成、阻断或退回 |
| 本阶段输出质量 | `quality_status`（质量状态） | 当前本阶段输出是否通过本阶段规则校验 |
| 证据质量 | `evidence_grade`（证据等级） | 当前核心判断的最终证据质量，取值 `Q0`—`Q4` |
| 判断强度 | `judgment_level`（判断强度） | 04 实际形成的观点强度，取值 `J0`—`J4` |
| 路径是否够用（03） | `path_readiness_status`（路径就绪） | 路径是否具备推理条件：`ready`、`restricted`、`blocked`、`not_applicable` |
| 路径推理结果（04） | `path_result_status`（路径结果） | 路径推理业务结果：`established`、`partially_established`、`weakened`、`blocked`、`insufficient_evidence`、`contested`、`not_applicable` |

`path_readiness_status` 与 `path_result_status` 回答的是两个不同问题，必须分开填写。前者回答“能不能推”，后者回答“推出来是什么”。

`stage_status` 统一使用 `not_started`、`in_progress`、`complete`、`blocked`、`returned`。它只回答阶段执行是否完成或阻断，不得混入业务处置结果（例如“需澄清”“超范围”）。阶段可否发布不写入该字段：阶段完成、本阶段输出高质量与观点强度是三个不同问题。03 阶段完成与否只看 `stage_status`；证据是否够用、可否进入下一步，按每个核心判断分别评价，不对整份材料包一刀切给出单一“准入”标签。

01 另用 `task_disposition`（任务处置）记录任务处置结果，取值 `accepted`、`needs_clarification`、`out_of_scope`、`split_required`。该字段仅作用于 01，不进入上述全局权威字段，也不得回写为 `stage_status` 的扩展枚举。进入 02 要求 `stage_status=complete` 且 `task_disposition=accepted`；`out_of_scope` 可与 `stage_status=complete` 并存，表示处置已完成但不进入后续阶段。

以下字段只能由规则计算，不得出现在人工填写模板中，也不得作为另一套限制来源：`evidence_permission`（证据权限）、`allowed_04_output`（04 允许表达）、`maximum_judgment_level`（结论强度上限）、`publishable`（可否发布）。`claim_mode`（主张模式）由 `conditions`（条件）是否为空确定；判断是否仍成立，由反证记录和路径结果表达，不另设人工字段。

### 3.1 本阶段输出质量

| 状态 | 含义 | 正式发布 |
|---|---|---|
| `draft` | 尚未完成检查 | 不允许 |
| `minimum_pass` | 达到最低内部流转条件 | 不允许 |
| `high_quality_pass` | 本阶段规则校验通过 | 允许进入全链发布检查 |
| `return_required` | 存在必须修正的问题 | 不允许 |
| `stop_with_gap_report` | 当前条件不足，只能形成缺口说明 | 仅可发布高质量缺口结果，不得包装成方向性判断 |

内部过程可以出现 `draft` 或 `minimum_pass`，正式交付只能接受经全链校验确认的高质量结果。

### 3.2 证据质量

`evidence_grade`（证据等级）是综合必需证据、口径、时效、代理依赖、冲突与适用范围后，对一个核心判断给出的最终 Q 等级。来源层级、单项证据可靠度或材料数量不能替代它。

### 3.3 结论强度

结论强度回答具体观点能够说到什么程度，与阶段状态和本阶段输出质量无关。04 必须为每条重要观点单独确定强度，不能用整体通过替代逐条判断，也不能用结论方向倒推证据质量。

### 3.4 结论强度上限怎么确定

项目只在 [`../运行校验/status_derivation.py`](../运行校验/status_derivation.py) 维护一套规则：根据证据等级、反证检查结果、路径是否够用，按规则给出该核心判断的结论强度上限（最大 J）以及允许的表达方式。规范、策略库、模板和示例不得另建第二套可编辑对照表。

规则按三个输入分别给出上限，再取其中最低值：

| 输入（业务含义） | 取值 | 对最大 J 的上限 |
|---|---|---|
| 证据等级 `evidence_grade` | `Q0 / Q1 / Q2 / Q3 / Q4` | `J0 / J1 / J2 / J3 / J4` |
| 反证检查结果（机器归一化） | `cleared / weakened / contested / decisive / not_checked / not_applicable` | `J4 / J2 / J1 / J0 / J1 / J4` |
| 路径是否够用 `path_readiness_status` | `ready / restricted / blocked / not_applicable` | `J4 / J2 / J0 / J4` |

展开后共有 120 种组合。系统对三个上限取最低值一次，得到唯一的最大 J，并同时给出允许表达方式：

| 结论强度上限 | 允许表达方式 |
|---|---|
| `J0` | 只说明缺口，不形成方向 |
| `J1` | 只作事实观察或线索 |
| `J2` | 保留条件的方向判断 |
| `J3` | 方向判断或高概率判断 |
| `J4` | 在明确对象、时间和范围内形成确认判断；必须额外通过方法门槛、两条独立证据链、竞争解释、反证、失效条件与语义审核 |

反证检查结果不是独立人工权威状态，必须由反证记录、冲突记录及其裁决动作自动归一化；主张是否带条件也不作为上述规则的输入。路径推理结果 `path_result_status` 本身要通过 04 推理才能得到，不得拿来反推最大 J，否则会形成循环。04 只填写实际 `judgment_level` 与 `path_result_status`，校验器负责确认判断强度未超过规则给出的上限。

## 4. 规则校验

规则校验处理能够无歧义执行的要求，包括：

- 文件、版本、字段和枚举是否合法；
- 任务 ID、运行 ID、时间、对象和范围是否一致；
- 上下游引用、证据文件和内容哈希是否可解析；
- 最小跨阶段主链是否可对账：`C→JU`、`JU→ER`、`ER→EV/缺口`、`EX→C`（约定见 [`00_项目定位与边界.md`](00_项目定位与边界.md#51a-最小跨阶段引用约定)）；
- 证据、判断和表达是否超过上游允许范围；
- 是否缺少必需本阶段输出或正式交付引用；
- 应返回哪个阶段重新处理。

规则校验由 `validate_01_outputs.py` 至 `validate_05_outputs.py` 和 `validate_publish.py` 执行。规则未通过时不得发布。

03 必须维护两个正交结果：`evidence_readiness`（证据是否够用）回答“是否可以形成判断”，`delivery_readiness`（交付素材是否就绪）回答“是否足以支撑指定 05 交付”。03 的 `high_quality_pass` 只评价证据准备过程、证据质量和可否进入推理的边界，不得因缺少图表、排序表或研报素材而失败；相关缺口只影响 `delivery_readiness`。一份证据可靠但不天然适合量化制图的政策、公告、事故或访谈型证据归档，可以是证据高质量且交付部分就绪。

## 5. 正式发布条件

正式发布必须同时满足：

1. 01—05 所需本阶段输出完整，且属于同一次任务和运行；
2. 每阶段规则校验通过；
3. 每阶段达到 `high_quality_pass`，或形成符合阶段规范的高质量缺口结果；
4. 03 明确证据能够支持到什么程度；
5. 04 每条观点未超过 03 的证据上限；
6. 05 未新增未经 03/04 支撑的事实、判断或更强表达；
7. 全链不存在未说明的范围漂移、引用断裂或越权结论。

`validate_run.py` 是新 run 的正式发布入口，内部继续复用 `validate_publish.py` 的 01—05 阶段校验。本阶段输出中填写的 `quality_status` 只是阶段记录，不能单独证明可以发布；任何交付物不得人工填写 `publishable`。总校验必须分别返回 `quality_pass`、`publishable`、`judgment_level` 与 `directional_conclusion_available`。高质量的 J0/J1 缺口或观察结果可以发布，不能把“没有方向性结论”误判为研究失败。

## 6. 返工原则

质量问题必须回到最早产生问题的阶段，不得只在下游改写措辞掩盖上游缺陷。

| 问题来源 | 返回阶段 |
|---|---|
| 问题、用途、对象、时间或范围不清 | 01 |
| 核心待验证命题、问题拆解、变量、路径或竞争解释有误 | 02 |
| 数据、来源、口径、证据质量、反证或展示素材不足 | 03 |
| 证据已经具备，但推理、观点强度、分化判断或审计有误 | 04 |
| 上游判断正确，但报告结构、表达、图表组织、审计腔未改写或追溯关系不合格 | 05 |

返工记录必须说明具体问题、影响对象、返回阶段、需要修改的内容和重新检查方式。返回上游后，下游依赖本阶段输出必须重新校验。

## 7. 唯一发布原则

项目可以保存草稿、内部流转件和历史版本，但不能把它们作为正式结果交付。正式目录中一次运行只能有一份正式 05 交付物；任何未达到高质量要求的环节都必须继续修正、返回上游或形成高质量缺口说明，不能通过降低发布标准结束流程。
