# 投研本体 3.0 框架概述

版本：3.0.0

元模型：Ontology Meta-schema 1.0

状态：active

机器权威：`meta_schema.yaml` 与 `models/*.yaml`

## 1. 唯一建模边界

正式投研本体只回答三类问题：投研世界中有什么对象、对象如何关联、哪些稳定约束始终成立。研究步骤、阶段编排、方法调用、程序执行、权限与任务状态不属于正式本体，分别由方法资产、公共合同、治理规则和运行层管理。

核心本体固定为五个职责独立、允许交叉引用的模型：

1. `semantic.yaml`：身份稳定的对象、研究范围与结构关系。
2. `state_event.yaml`：状态变量、观测、快照、状态变化与事件。
3. `evidence.yaml`：来源、原始陈述、证据事实、证据要求、评估和证据组合。
4. `judgment.yaml`：研究问题、判断单元、信号、假设、竞争解释、阻断因素、规则评估、判断与推理留痕。
5. `scenario.yaml`：公司、行业、产业链、技术路线和事件影响研究场景。

行业扩展只能继承或投影核心对象，不能覆盖核心 ID。`Segment` 不是核心类型，历史含义统一迁移为 `ValueChainSegment`；需要保留外部别名时写入对象的 `aliases`。

## 2. 对象、属性、关系和约束分离

- 对象表示具有独立身份、属性和生命周期的事物。
- 属性只描述对象自身，引用其他对象时使用强类型 `object_ref`。
- 关系表达两个对象之间可验证的语义，必须声明端点、双端基数、逆关系、时间性、证据要求和失效策略。
- 正式规则只允许语义约束、证据约束和状态一致性约束。

每个正式元素必须具备稳定 ID、命名空间、中英文名称、定义、版本、状态、有效期、替代项、来源、正例和反例。实例可使用 UUID，但不能用 UUID 替代稳定语义 ID。

## 3. 可遍历的研究闭环

正式关系图至少能够沿下列路径双向遍历：

```text
ResearchScope -> 语义对象
ResearchQuestion -> JudgmentUnit
  -> EvidenceRequirement -> EvidenceBasket
  -> EvidenceAssessment -> EvidenceFact
  -> EvidenceClaim -> SourceDocument

EvidenceFact -> Observation/Event
Observation -> StateVariable -> StateChange/StateSnapshot
EvidenceFact/StateChange -> Signal -> Hypothesis
JudgmentUnit -> CompetingExplanation/BlockingFactor
Hypothesis -> Judgment -> RuleEvaluation/ReasoningTrace
```

`ResearchScenario` 与资本市场侧若干对象当前为 `draft`：已定义但不写入 Runtime 实例图。任务文件中的 `research_scenario` 只是 `scenario_types` 枚举标签。判断链引用完整性由 `judgment_reference_integrity` 约束；关系端点兼容仍是 `semantic_endpoint_compatibility`，在实例图物化时执行。

其中 `EvidenceFact -> Judgment` 是禁止边。证据只能先形成状态、事件或信号，再经过判断单元、假设和正式约束形成判断。表达层只能投影既有判断。

## 4. 时间语义

模型区分四种时间：

- 观察时间：对象或数值被观察的时间。
- 有效时间：事实、状态或事件在业务世界开始和停止适用的时间。
- 公布时间：信息首次对研究者可获得的时间。
- 研究截止时间：本次研究允许使用信息的最晚时间。

任何观测、事件、证据事实或判断都不得使用截止时间之后才公布的信息。快照和推理留痕不可覆盖，只能通过新版本替代并保留历史。

## 5. 通用语义对象

除公司、产品、技术、行业、产业链环节、地区、指标和研究范围外，核心语义模型还统一定义：

- `Application`：产品或技术的稳定下游用途。
- `Material`：进入制造过程的材料类产品。
- `ProcessStep`：具有明确输入、输出和功能边界的工艺步骤。
- `PolicyInstrument`：对对象行为或准入形成稳定约束的政策工具。
- `Asset` / `FinancialInstrument` / `TradingVenue` / `Listing`：资本市场骨架，当前 `draft`，未纳入运行投影。

除 draft 预留项外，其余类型是通用核心，不属于半导体专用概念。领域扩展可以增加子类，但不能重定义它们。

## 6. 状态变量定义与任务绑定

`StateVariable` 可先作为稳定变量定义存在，记录类别、定义、允许锚点和证据画像；此时 `metric_ref` 和 `scope_ref` 可以为空。进入具体研究任务后，必须通过 `stateVariableForObject` 绑定具体对象，并在观测或快照中绑定指标、范围与截止时间。这样领域变量库不需要伪造任务实例，同时任务实例仍保持强约束。

## 7. 判断状态

`Judgment.decision_status` 使用 `draft / supported / contested / blocked / indeterminate / invalidated`。未解决冲突必须得到 `contested`；决定性反证或阻断必须得到 `blocked` 或 `indeterminate`；后二者必须填写 `not_judgeable_reason`。结论等级不得超过证据门槛允许的上限。

## 8. 场景与工作流分离

`scenario_types`（如 IndustryResearch）是任务侧场景分类与设计清单：声明常见所需对象/证据/判断类型，**不**作为 Runtime 入口或完成校验关口。`ResearchScenario` 对象实例化路径保留为 draft。01—05 仍是公共合同中的任务编排，不成为本体对象或关系。

## 9. 版本与变更

- active 元素的 `replaced_by` 必须为空。
- deprecated 元素必须给出真实存在的替代 ID。
- 语义变更通过版本升级完成，不得静默改名。
- 新证据使上游事实失效时，沿正式关系使观测、快照、信号、规则评估、判断和推理留痕进入失效或重算范围。

## 10. 发布门槛

正式发布至少满足：所有引用可解析、逆关系成对且端点镜像、属性具有类型和基数、规则具备结构化正反例（当前 `test_case_role=design_intent`，冻结门做结构检查；是否 Runtime 挡门以 `rule_authority_registry.execution_surface` 为准）、五模型存在跨模型关系、证据不能直达最终判断、场景与范围及研究问题可遍历、正式本体中不存在研究方法和运行控制参数。
